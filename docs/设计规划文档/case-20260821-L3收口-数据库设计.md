## 1. 存储选型决策矩阵

| 数据类型 | 推荐存储 | 理由 |
|---|---|---|
| 风险登记册/合规检查/商业案例（结构化治理资产，CRUD+租户隔离+审计+计算列落库） | MySQL 8.0 既有库（3 新表） | 平台单一存储现状，强一致 + 租户拦截器复用；量级 ≤5000/5000/500 行/租户（PRD §6.5）远低于分库分表阈值 |
| 风险关联对象 / 案例关联战略（可空多选展示级引用） | JSON 列（非关联表） | 无行级启停/独立生命周期诉求，详情解析 + 存在性应用层校验；不建关联表避免过度设计（V5/V6 JSON 论证先例） |
| 风险看板 / 投资组合（聚合视图） | 零 DDL：单聚合读 API | 实时聚合（GROUP BY/排序/汇总）在租户量级下毫秒级；物化表会引入刷新一致性负担与写放大，PRD §6-5 性能水位内无必要 |
| 计算列（risk_value/risk_level/net_benefit/payback_years/roi_percent/rice_score） | 落库列（Service 保存时重算覆盖） | 裁决 Q1：列表默认排序（risk_value/rice_score 降序）与聚合直接用列；客户端提交值一律忽略（AC-F1.5/F2.4 防伪造）——读时计算无法表达"忽略客户端"且每次列表全量重算 |

## 2. 表清单（3 张新表，全部租户级业务表，不进 IGNORE_TABLES，不限层）

### 2.1 t_risk 风险登记册（20 列 = 15 业务 + 5 审计，F1.1）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id / tenant_id | BIGINT | PK / NOT NULL | 雪花 ID / 租户隔离 |
| risk_name | VARCHAR(200) | NOT NULL，uk 列 | 租户内唯一（uk_gate_tenant_name 先例） |
| category | VARCHAR(16) | NOT NULL | strategy/compliance/operations/technical/security，应用层校验（P6 裁决） |
| probability / impact | TINYINT | NOT NULL | 各 1~5，越界/非整数应用层 400（AC-F1.3） |
| risk_value | INT | NOT NULL | =P×I（1~25），Service 重算落库（裁决 Q1） |
| risk_level | VARCHAR(16) | NOT NULL | low/medium/high/critical，四段闭区间 [1,6]/[7,12]/[13,19]/[20,25]（PRD §4.1.2 唯一口径）。**提示稿给 VARCHAR(8)，此处放宽为 16**：critical 恰 8 字符零余量，按 V5 FAIL_WARN 宽度纠偏教训执行（枚举域 PRD 冻结，存储成本可忽略），已在脚本注释标注 |
| mitigation / contingency_plan | TEXT | NULL | 缓解措施/应急预案（计划类自由文本） |
| owner | VARCHAR(64) | NULL | 自由填写，不联动 t_user（V6 先例） |
| status | VARCHAR(16) | NOT NULL DEFAULT 'open' | 状态机应用层校验：open→mitigating→closed（closed 必填处置说明、终态不可 reopen——裁决 Q3）；mitigating→open 回退合法（PRD §4.1.3/Q2-①）；其余 400 |
| resolution_note | VARCHAR(500) | NULL | closed 必填（应用层校验，宽度同 V6 deprecate_reason 先例） |
| related_objects | JSON | NULL | [{type: program/project/case, id}]——存 id（裁决 Q4：三表均无 code 列，t_program.strategy_id 存 id 先例）；存在性应用层校验，逻辑删对象展示层占位 |
| review_date | DATE | NULL | 逾期=review_date < CURRENT_DATE 且 status≠closed，展示层红标不落库（裁决 Q9） |

### 2.2 t_compliance_check 合规检查（17 列 = 12 业务 + 5 审计，F1.2）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| check_name | VARCHAR(200) | NOT NULL，uk 列 | 租户内唯一 |
| framework | VARCHAR(16) | NOT NULL | djba2.0/iso27001/gdpr/custom，应用层校验（djba2.0 展示名=等保 2.0，前端集中映射） |
| framework_name | VARCHAR(128) | NULL | custom 必填、非 custom 必空（应用层 400，防脏数据 AC-F1.9） |
| clause_ref | VARCHAR(128) | NULL | 条款引用（自由填写，不做符合性自动判定） |
| description | TEXT | NULL | 检查描述 |
| result | VARCHAR(8) | NOT NULL | pass/fail/partial/na；覆盖式单值当前态，历史唯一留痕=审计 detail（AC-F1.10，V6 last_result 先例） |
| evidence_note | VARCHAR(1000) | NULL | 证据说明（手动登记制；较 V6 remark 500 放宽——证据常含多条线索引用） |

### 2.3 t_business_case 商业案例（24 列 = 19 业务 + 5 审计，F2.1）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| case_name | VARCHAR(200) | NOT NULL，uk 列 | 租户内唯一 |
| related_strategy_ids | JSON | NULL | 存 t_strategy.id 数组（裁决 Q4；与 V5 ADR 存 code 有意不同——被引实体无稳定业务键，PRD 经验沉淀 #3） |
| onetime_cost / annual_op_cost / annual_benefit | DECIMAL(14,2) | NOT NULL | 单位=元（裁决 Q2），≥0 应用层校验（负值 400，=0 合法触发边界） |
| net_benefit | DECIMAL(14,2) | NOT NULL | =benefit−op_cost 可负；**裁决列举五计算列之外 DBA 增补落库**：投资组合 Σ(net) 与 Σ(net×3) 直接用列（裁决 Q1"聚合直接用列"精神），两输入同宽差值不越界 |
| payback_years | DECIMAL(16,1) | NULL | =onetime÷net，1 位小数 HALF_UP；**NULL=N/A**（net≤0 含 0）；成本 0 且净>0 → 0.0（AC-F2.2） |
| roi_percent | DECIMAL(20,2) | NULL | =(net×3−onetime)÷onetime×100，2 位 HALF_UP，负值合法；onetime=0 → NULL=N/A（AC-F2.3） |
| reach / impact / effort | INT | NOT NULL | 各 1~10 应用层校验（impact 与 t_risk.impact 同名不同义，表内自洽） |
| confidence | DECIMAL(2,1) | NOT NULL | 0.1~1.0 恰 10 档 0.1 步进离散，非步进值 400（AC-F2.4，PRD 契约精度） |
| rice_score | DECIMAL(10,2) | NULL | =R×I×C÷E，2 位 HALF_UP；无 N/A 路径（E≥1 恒正），可空仅为三计算列统一防御 |
| status | VARCHAR(16) | NOT NULL DEFAULT 'draft' | draft→approved→executing→done；draft→rejected（必填原因）；rejected/done 终态；不允许回退/撤销（裁决 Q3）。**注意：裁决 Q3 五态线性串写与 PRD 图不一致，以 PRD §4.4.2 图/AC-F2.6 为准——executing 唯一合法出边=done**，脚本注释已标注 |
| rejected_reason | VARCHAR(500) | NULL | rejected 必填（应用层 400） |
| decision_note | TEXT | NULL | 决策记录随流转可更新（approved/executing 只读期仍可更新，AC-F2.7）；旧值留痕=审计 |

计算列宽度按最坏值预算（V6 经验"按最坏字节算"泛化到十进制位）：payback 最坏 14,2 成本 ÷ 0.01 净 ≈ 1e14 → DECIMAL(16,1)；roi 最坏 ≈ 3e16 → DECIMAL(20,2)；rice 值域 [0.01,100.00] → DECIMAL(10,2)。

## 3. 索引策略总表（全部按拦截器改写后真实 SQL 设计：tenant_id 等值打头）

| 表 | uk | 二级索引 | 克制论证 |
|---|---|---|---|
| t_risk | (tenant_id, risk_name) | (tenant_id, status) | 不加 (tenant,risk_value) 排序索引（≤5000 行 filesort 毫秒级）；不加 (tenant,probability,impact)——热力图 GROUP BY 仅 25 格低区分度，未 closed 子集临时表聚合毫秒级（AC-F1.12 路径）；类别/等级基数 5/4、逾期非等值比较均不索引 |
| t_compliance_check | (tenant_id, check_name) | — | 框架/结果基数 4/4 区分度极差；逾期非等值；≤5000 行前缀扫描毫秒级（V6 t_data_asset 四维筛选不索引先例） |
| t_business_case | (tenant_id, case_name) | — | ≤500 行/租户（三表最小），rice 排序/状态分布/投资口径汇总全为租户内扫描聚合毫秒级（V6 t_template 仅 uk 先例）；uk 前缀用 bizcase 避免与 L1 t_case 索引名（idx_case_project）语义混淆 |

- 三表 uk 均含 tenant_id：名称类列是租户自由命名无全局语义，跨租户同名是常态，丢 tenant_id 会误伤合法数据（V4 uk_gate_tenant_name 同权衡）。
- (tenant_id, status) 仅 t_risk 有：列表状态筛选 + 看板/逾期口径"未 closed"过滤（应用层写 IN(open,mitigating) 走索引范围）是热路径；对齐 V4 t_strategy/t_program、V6 t_standard 惯例。

## 4. 高并发策略

单租户量级 ≤5000/5000/500 行（PRD §6.5），无读写分离/分库分表/缓存诉求；列表分页走 uk 前缀，两个聚合 API 单查租户内扫描，P95 < 500ms 水位内。计算列为行内算术，无额外查询开销。

## 5. seed 与 ID 区间

- **权限原子 10 条：id 1071~1080**（V6 用毕 1070）：risk/compliance/bizcase × view/create/edit + **bizcase:approve 独立原子**（裁决 Q7——审批高频可配置可审计，403 走权限链，区别于 V6 F3.2 应用层判断先例）。
- **授权行 33 行：id 2170~2202**（V6 用毕 2169）：platform_admin×10、tenant_admin×10（裁决 Q5：GRC/Strategy 缺位兼任）、**PM×7 = risk×3 + compliance:view + bizcase×3**（裁决 Q6：一线上报+起草，无 compliance create/edit 防自查自登、无 approve 防自我批准；**PM 的 compliance:view 以 PRD §4.6 矩阵为准——矩阵明确 PM 合规只读，与提示稿"缺省则给 view"结论一致**）、engineer×3、executive×3（三域 view）。

## 6. 迁移脚本与幂等性

- V7 对既有表**零 ALTER / 零 UPDATE / 零存储过程**，仅 3×CREATE TABLE IF NOT EXISTS + 6×INSERT IGNORE——天然幂等，无 1060/1061 风险面（#20 教训最彻底规避，V6 同形式延续）。
- 枚举合法性与状态机均应用层校验、DB 不加约束（V5/V6 先例，PRD §0 P6 裁决）。
- 回滚：仅新增对象，回滚 = DROP TABLE t_risk/t_compliance_check/t_business_case + DELETE seed（id 1071~1080 / 2170~2202）；生产不建议回滚，Flyway 不自带 down。
- H2 已同步：3 表简化 DDL（DATETIME→TIMESTAMP、JSON/TEXT→CLOB、TINYINT→INT）+ 4 索引 + seed MERGE INTO KEY(id)（33 授权三元组与 V7 逐条一致，脚本校验通过）。
- python 逐行自查通过：`--` 后空格全文合规、语句块括号/单引号/反引号配对、permission 1071~1080 与授权 2170~2202 连续无重、角色分布 10/10/7/3/3、role3 权限集恰为 {risk×3, compliance:view, bizcase×3}（无 1075/1076/1080）、V1~V6 零改动（时间戳核对）。

## 本次经验沉淀

1. **计算列"N/A 语义"要在 schema 层就有唯一表达**：除零/零值/负值等不可计算边界统一映射为 NULL（区别于 0.0 这类合法值），列可空 + COMMENT 写死边界表——否则应用层各处各自发明哨兵值（-1/0/空串）会污染排序与汇总；PRD 的边界四件套（公式+舍入+除零+构造数值）应原样搬进列 COMMENT。
2. **十进制宽度按"最坏商"预算**：DECIMAL(m,n) 之间的除法结果位宽由"最大被除数 ÷ 最小正除数"决定（14,2 ÷ 0.01 ≈ 1e14），不是输入列宽的量级——回收期/ROI 这类衍生比率列若按直觉给 DECIMAL(10,x) 会在极端输入下溢出报错，与 V6"字符按最坏字节算"同一条原则的数值版。
3. **裁决文档的线性状态串写要与 PRD 状态图交叉核对**：本次裁决 Q3 把五态写成一串"draft→approved→rejected→executing→done"并称三者终态，直接照抄会让 executing 不可流转到 done（与 AC-F2.6 矛盾）；DB 注释是终稿契约的落点，发现两文档冲突时必须在注释里显式写"以 PRD 图/AC 为准"并回标注释，不能静默择一。
