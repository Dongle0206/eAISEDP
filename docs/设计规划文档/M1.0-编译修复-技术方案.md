## 1. 根因与方案概述

### 1.1 根因（已诊断，磁盘事实核对完毕）

| 层 | 根因 | 证据 |
|---|---|---|
| 直接（机制）| 父 POM `pluginManagement/spring-boot-maven-plugin` 含 `<executions><execution><id>repackage</id>...`（pom.xml:131-136），导致所有引用该 plugin 的子模块（含 capability/adapter/data 三个 library）被 repackage 成 fat jar，class 重定位到 `BOOT-INF/classes/`，runtime 编译期找不到 `com.eaiselp.capability.loader.CapabilityLoader` 等符号 | 父 pom.xml 第 122-139 行（本次已 Read）|
| 深层（架构）| 模块边界未定义清楚：capability/adapter/data 既有独立 Application + Nacos 注册（service 特征），又被 runtime 当 Maven 库同进程注入（library 用法）—— "既是库又是服务"，repackage 一刀切必然炸 | ADR-001 §1.3 |

### 1.2 方案（ADR-001 §5.1 裁决：方案 B - 模块化单体）

M1 阶段 capability/adapter/data **定性为 library**：
- 删除三者的 Application 类（含 main / @SpringBootApplication / @EnableDiscoveryClient）
- 三者 POM 移除 spring-boot-maven-plugin 与 nacos-discovery 依赖
- 三者的 Controller 类**保留**，端点由 runtime 的 `scanBasePackages` 接管，合并到 runtime 进程暴露
- runtime（host service）继续用 bean 注入同进程调 capability/adapter（DerivationEngine 零改动）
- repackage execution 下沉到 5 个 service 模块各自的 POM（P4：显式优于隐式）

### 1.3 改动影响面（总览）

| 类别 | 文件数 | 动作 |
|---|---|---|
| 父 POM | 1 | 移除 pluginManagement 内 executions 段 |
| library 模块 POM | 3 | 移除 spring-boot-maven-plugin + nacos-discovery 依赖（capability/adapter/data）|
| library 模块源码 | 3 | 删除 EaiselpCapabilityApplication / EaiselpAdapterApplication / EaiselpDataApplication |
| service 模块 POM | 5 | runtime/gateway/auth/observability/admin 各补 spring-boot-maven-plugin 的 executions |
| runtime Application | 1 | 新增 @EnableScheduling（迁移自 capability）|
| **合计** | **13** | （common 的 POM 与 Application 均已合规，不动）|

### 2.7 【删-3】删除 EaiselpDataApplication.java

**文件**：`D:\AI\mywork\platform\eaiselp-data\src\main\java\com\eaiselp\data\EaiselpDataApplication.java`

```java
package com.eaiselp.data;

import org.mybatis.spring.annotation.MapperScan;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication(scanBasePackages = {"com.eaiselp.data", "com.eaiselp.common"})

public class EaiselpDataApplication {
```

**注解迁移去向**：

| 注解 | 迁移去向 | 原因 |
|---|---|---|
| `@SpringBootApplication` | 删除 | ES-001 §3.1 |
| `@EnableDiscoveryClient` | 删除 | ES-001 §3.1 |
| `scanBasePackages` | 删除 | runtime 当前不依赖 data，无需扫 |

**`@MapperScan` 决策**（关键）：

- **现状**：runtime/pom.xml 第 17-19 行只依赖 common + capability + adapter，**未依赖 data**；5 个 service 模块的 pom 全部 grep 过，**均无 eaiselp-data 依赖**。

- **迁移时机**：当 M2/M3 runtime（或新的 host service）真正引入 `<dependency>eaiselp-data</dependency>` 时，在那个 host 的 Application 类加 `@MapperScan("com.eaiselp.data.mapper")`。
- **action item**：在 runtime/EaiselpRuntimeApplication.java 上方加一行注释标记 TODO，避免未来漏配（见改-13）。

**对应门禁**：QG G3 + G4（阻断）。

## 3. 改动顺序（关键——避免编译中途失败）

### 3.1 推荐顺序（每步之后都能独立通过 `mvn clean package -DskipTests`）

```
第 1 步：改父 POM（改-1）              ——移除 pluginManagement executions
第 2 步：补 5 个 service 模块的 POM（改-5~改-9）——显式补 executions
第 3 步：改 runtime Application（改-10）——加 @EnableScheduling
第 4 步：删 3 个 library Application 类（删-1~删-3）
第 5 步：改 3 个 library 模块的 POM（改-2~改-4）——移除 plugin + nacos
```

### 3.2 为什么是这个顺序（安全性论证）

| 步 | 步后状态 | mvn 还能编译/启动？ | 论证 |
|---|---|---|---|
| 第 1 步 | 父 POM 不再自动触发 repackage | **能编译，但 service 不能独立启动** | service 此时 POM 还没补 executions，runtime/gateway 等打出来是 thin jar，但 `mvn package -DskipTests` 仍 BUILD SUCCESS（repackage 只是 packaging 阶段的附加 goal，不是 compile 的依赖）。**关键收益：library 模块从此不再被错误 repackage，runtime 编译期能找到 capability/adapter 的符号** |
| 第 2 步 | service 显式补 executions | **能编译且能启动** | service 重新具备 repackage 能力，恢复 fat jar |
| 第 3 步 | runtime 加 @EnableScheduling | **能编译且能启动** | capability Application 还在，capability 自己也 @EnableScheduling，注解重复不影响（Spring 容忍）。本步只是为下一步删除做铺垫 |
| 第 4 步 | 删 library Application 类 | **能编译且能启动** | library 模块再无 main，但作为 library 这是正确的；runtime 进程是唯一入口，启动时通过 scanBasePackages 接管 capability/adapter 的 Controller/Bean。runtime 已在第 3 步加了 @EnableScheduling，CapabilityLoader 的 @Scheduled(30s) 继续工作 |
| 第 5 步 | library POM 移除 plugin + nacos | **能编译，library 是 thin jar，service 是 fat jar** | 最终目标态达成。门禁全绿 |

**反例（错误顺序）**：

- ❌ 先删 Application 类（第 4 步）再改父 POM（第 1 步）：删了 Application 但父 POM 还在 repackage，capability 编译产物仍是 fat jar，runtime 编译失败——回到原点。
- ❌ 先改 library POM（第 5 步）再删 Application 类（第 4 步）：library POM 已无 spring-boot-maven-plugin，但 Application 类还在，编译时 IDE 会标黄 "main 方法在 library 模块无意义"，虽不致命但不干净。
- ❌ 不补 service executions（跳过第 2 步）就改父 POM：service 不再 repackage，最终 jar 无法 `java -jar` 启动，QA 启动验证失败。

### 3.3 单次提交策略（建议）

- **建议 1 个 PR 完成 5 步全部改动**（13 个文件），保证门禁只跑一次全绿。如果分多个 PR，中间状态会触发门禁 FAIL（如先合第 1 步，G6 必然 FAIL：service 没补 executions）。
- **如果必须拆**：按"第 1+2 步"（service 侧先自洽）→ "第 3+4+5 步"（library 侧落地）两个 PR，每个 PR 内部门禁都能临时全绿。但本质上这是一次原子改造，不建议拆。

## 本次经验沉淀

1. **pluginManagement 是"配方"不是"执行"**：Maven 的 pluginManagement 只是声明"如果子模块引用这个 plugin，按此配置"，本身不触发任何 goal；但一旦配方里含 executions，子模块只要 `<plugin>xxx</plugin>` 一行就触发 execution。这种"隐式触发"是大型多模块项目的常见陷阱，**带副作用的 execution 必须下沉到具体模块显式声明**（P4 的本质）。
2. **删 Application 类时要列"横切注解迁移清单"**：本次 capability 的 Application 类上有 @EnableScheduling，data 上有 @MapperScan，如果删时不列迁移表，必然漏迁导致运行时静默失效（编译不报错）。ES-001 C13 已把这条固化为阻断项，是本次实战教训的标准化沉淀。
3. **M1 模块化单体的 scanBasePackages 是 host 接管 library 端点的关键开关**：runtime 通过 scanBasePackages 把 capability/adapter 的 Controller/Bean "拉进"自己的 Spring 容器，这是模块化单体最优雅的端点合并方式（vs 把 Controller 复制到 runtime / 用 Feign 远程调用）。删 library 的 Application 类后，这个开关变得至关重要——一旦漏配就是 404 + NoSuchBeanDefinition。
4. **改动顺序的"扳机点"识别**：本次修复的扳机点是第 1 步（改父 POM）——一旦 executions 从父 POM 移除，library 立即不再被 repackage，runtime 编译期符号立即恢复。后续步骤都是配套（service 补 executions、删 Application、迁注解），不会影响"编译能否通过"这个核心判据。识别扳机点能让 Dev 在调试时知道"先确保哪一步生效"。
5. **磁盘事实核对是 SE 的硬约束**：编排者转述的现状（@EnableScheduling 在 capability 第 10 行、scanBasePackages 含 capability/adapter）我全部用 Read + grep 二次验证，发现其中一处细节（@MapperScan 在 data 上）编排者未提及——若不亲自核对，方案就会漏掉"暂不迁移 @MapperScan"的决策，Dev 改时会疑惑。SE 必须基于磁盘，不基于转述。
