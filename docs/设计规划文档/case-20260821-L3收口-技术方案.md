**uk/索引**（按拦截器改写后真实 SQL 论证）：
- `uk_risk_tenant_name(tenant_id, risk_name)`——uk + 名称筛选前缀；
- `idx_risk_tenant_value(tenant_id, risk_value)`——列表默认排序 `ORDER BY risk_value DESC, id DESC`：InnoDB 二级索引叶节点隐含 PK，tenant 等值 + 倒扫天然给出 (value DESC, id DESC) 全序，免 filesort；
- **不建热力图专用聚合索引**：`GROUP BY probability, impact WHERE tenant_id=? AND status<>'closed'` 走 tenant 前缀扫描后内存聚合——风险 ≤5000 行/租户（PRD §6.5）毫秒级，且 `status<>'closed'` 非等值使 (tenant,status,prob,impact) 复合索引的分组前缀失效，建了也用不上（V6"按需加列不按需加索引"先例）；等级/类别筛选低基数（4/5 值）同先例不建。

| effort | TINYINT NOT NULL | RICE E，1~10 整数（≥1 恒正，无除零路径） |
| net_benefit | DECIMAL(14,2) NOT NULL | **计算列** = annual_benefit − annual_op_cost，可负（D-2） |
| payback_years | DECIMAL(20,1) NULL | **计算列**，NULL=N/A（net≤0 或语义见 §4.2） |
| roi | DECIMAL(20,2) NULL | **计算列**（百分数值，如 20.00 表示 20.00%），NULL=N/A（onetime=0） |
| rice_score | DECIMAL(5,2) NOT NULL | **计算列**，域 [0.01,100.00] |
| status | VARCHAR(16) NOT NULL DEFAULT 'draft' | draft/approved/rejected/executing/done（D-5） |
| rejected_reason | VARCHAR(500) NULL | rejected 必填（流转校验） |
| decision_note | TEXT | 决策记录，随流转可更新（B6 端点） |

索引：
- `uk_bc_tenant_name(tenant_id, case_name)`——uk + 名称筛选；
- `idx_bc_tenant_rice(tenant_id, rice_score)`——案例列表/组合视图 `ORDER BY rice_score DESC, id DESC`（隐含 PK 同 §3.1 倒扫论证）；
- 组合汇总（`SUM(...) WHERE status IN (approved,executing,done)`）与状态分布（`GROUP BY status`）走 tenant 前缀扫描——案例 ≤500 行/租户（PRD §6.5），不建聚合索引；strategyId 筛选 = JSON 列**内存过滤**（分页后过滤同 V6 principleCode 口径），不索引。

### 3.4 计算列落库与重算时机（裁决 Q1 落地）

- **重算时机 = create 与 update（含仅 P/I 或成本收益变更）**：Service 在写库前调 Calculator 重算并覆盖实体值；update 走全量字段 PUT（draft 专属），不存在"改了 P 没重算"的路径。
- 客户端提交计算字段：**入参 DTO 无该字段**（D-4/§2.2），提交 `risk_value=999` 被反序列化直接丢弃——AC-F1.5/F2.4"重算覆盖"断言由"不可提交"更强满足。
- 计算列与输入列同表同行：无异步/无定时重算，行内算术零额外查询（PRD §6.5）。

## 4. 计算引擎设计（唯一实现口径；QA 构造值照 PRD §4.1.2/§4.4.1）

### 4.1 RiskCalculator（静态纯函数）

```java
public final class RiskCalculator {
    /** 校验并计算：P/I 为 1~5 整数（BigDecimal.stripTrailingZeros 判整），否则 BizException(400, 字段名+合法值提示)。 */
    public static int riskValue(BigDecimal probability, BigDecimal impact);
    /** 等级映射（闭区间四段）：v∈[1,6]→low；[7,12]→medium；[13,19]→high；[20,25]→critical。返回 RiskLevel 枚举。 */
    public static RiskLevel riskLevel(int riskValue);
}
```

边界要点：**先校验后计算**（0/6/1.5 在计算前 400 指名，AC-F1.3）；P=1,I=5→v=5→low 为**已知语义非缺陷**（PRD 写入口径，代码注释锚定防质疑工单）；边界值 6/7/12/13/19/20 由四段闭区间映射自然命中（AC-F1.2）。

### 4.2 BizCaseCalculator（静态纯函数；BigDecimal + HALF_UP）

```java
public final class BizCaseCalculator {
    public static BigDecimal netBenefit(BigDecimal annualBenefit, BigDecimal annualOpCost);   // b−o，可负
    /** 回收期：net≤0 → null（N/A，含 0 防除零）；onetime=0 且 net>0 → 0.0；否则 onetime/net 保留 1 位 HALF_UP。 */
    public static BigDecimal paybackYears(BigDecimal onetimeCost, BigDecimal netBenefit);
    /** ROI(3年口径)：onetime=0 → null（N/A 防除零）；否则 (net×3−onetime)/onetime×100 保留 2 位 HALF_UP，负值合法。 */
    public static BigDecimal roi(BigDecimal onetimeCost, BigDecimal netBenefit);
    /** RICE：reach×impact×confidence÷effort 保留 2 位 HALF_UP（effort≥1 无除零）；域 [0.01,100.00]。 */
    public static BigDecimal riceScore(int reach, int impact, BigDecimal confidence, int effort);
    /** confidence 离散校验：value×10 ∈ {1..10} 整数（0.1~1.0 恰 10 档）；否则 400。 */
    public static void validateConfidence(BigDecimal confidence);
}
```

**边界与舍入清单（Dev 实现锚点 = QA 断言基线）**：

| 项 | 口径 | 构造值（PRD） |
|---|---|---|
| payback 正常 | 100÷40=**2.5**；100÷30=3.333→**3.3**（HALF_UP 1 位） | AC-F2.2 |
| payback N/A（两种语义不同） | net=0（收益20/运营20）→ null；net=−10 → null（**不可投**）；onetime=0、net=30 → **0.0**（**零成本**） | AC-F2.2 |
| roi 正常/负 | (40×3−100)/100=**20.00**；(10×3−100)/100=**−70.00**（负值合法展示） | AC-F2.3 |
| roi N/A | onetime=0 → null（除零防御，与 payback 的 net≤0 N/A 语义来源不同） | AC-F2.3 |
| rice | 10×10×1.0÷1=**100.00**；5×3×0.8÷6=**2.00**；最小 1×1×0.1÷10=0.01 | AC-F2.4 |
| confidence 离散 | 0.1~1.0 共 10 档全合法；**0.05/0.15/0.85（合法小数但非步进）**、0、1.1 → 400 | AC-F2.4 |
| 金额 | 任一为负 → 400；三金额均 0 合法（触发 payback=0.0 + roi=null 边界态） | AC-F2.5 |
| 数值域 | 全 BigDecimal 运算；列宽 (20,x) 兜底极端比值（onetime=0.01、net≈1e12 时 roi%≈3e16 不溢出 500） | D-11 |

### 4.3 计算字段防伪造链（AC-F1.5/F2.4）

入参 DTO 无计算字段（§2.2）→ Service 写库前重算覆盖（§3.4）→ 落库值恒等于公式值。测试断言三段：提交伪造值返回 200、库中值为公式值、VO 回显=库值。

## 本次经验沉淀

1. **"计算类需求"的工程锚点是先写纯静态计算器 + 边界单测，再写 CRUD**：PRD 已沉淀"公式四件套"，工程侧对应物是"计算引擎独立成类、单测先行"——本 case 12+ 条数值 AC 全部指向同一组公式，若公式散在 Service 里，QA FAIL 后定位是 O(文件) 而非 O(函数)。拆解序把计算器放批A 第一位（先锁口径再铺功能），可让后续所有批次的口径争议归零。
2. **写数值边界 AC 前先查全局异常处理器的反序列化兜底**：`HttpMessageNotReadableException` 是否有专项处理决定了"非整数入参"落在 400 还是 50000——这是 PRD/QA 写不出、只有读代码才知道的断言陷阱。SE 方案里"DTO 数值字段一律 BigDecimal"应成为平台惯例（未来有理数/区间校验需求同此），并考虑后续在 GlobalExceptionHandler 补 HttpMessageNotReadableException → 400 的平台级兜底（记为 V7+ 债务，不在本 case 扩面）。
3. **裁决记录与 PRD AC 冲突时，SE 的义务是产出"消解表"而非择一执行**：本 case 裁决 Q3"单向"与 AC-F1.4"回退合法"字面冲突——按"裁决针对终态回退、AC 是 QA 基线"消解并写入 §0.3 随方案下发。判断准则：AC 是 PRD 权威性条款（"验收标准即 QA 用例基线"），裁决措辞应尽量向 AC 收敛解释；无法收敛时上报编排者改 AC，而非让 Dev/QA 各执一词。
