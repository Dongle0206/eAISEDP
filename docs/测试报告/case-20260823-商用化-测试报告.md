## 8. 本次经验沉淀

1. **"勘误/裁决改口径"类需求的验收锚点必须双向钉死**：本 case 386.71 覆盖 PRD 原文整月口径，QA 侧若只读 PRD 会把正确实现判 FAIL（假缺陷）、只读勘误会漏掉 PRD 其余仍有效断言（9,015.00/101.00 不变）。做法：以"勘误声明的不变部分"清单逐条比对测试断言，且测试源码注释里必须留"不得按 PRD 原文断言"的反向提示（BillingCalculatorTest.java:15-16 即此形态，值得沿用为计费类 case 模板）。
2. **Controller 分叉型向后兼容（老入参路径 + 新模式互斥）是三方测试盲区**：存量 ControllerTest 只测老路径、新 Service 测试只测新逻辑，分叉判定（互斥 400/全空 400/"裸通道不动新列"）两头都不覆盖——QA 应把"分叉点"本身当独立被测对象补 Controller 层用例（本次 U2CompatForkTest 补位即此模式；判断方法：grep 新旧两条路径各自的调用方测试，交集为空即缺口）。
3. **按 surefire 报告文件求和统计前必须按时间戳过滤**：target 目录会残留已删除测试类的历史报告（本次 ScratchProbeTest 虚增 1 例），多轮增量复跑的统计口径会被污染；先例报告的"总数对账"环节应加这一步，否则基线数字对不上时会误判为漏跑。
