下行链（约束注入）：t_architecture_principle →（t_project_principle 解析）→ t_orchestration.injected_json → 编排各角色 LLM 上下文。
上行链（进度汇总）：t_case.status=done / 挂接变化 / 逻辑删 → 重算 t_project.case_total/case_done/progress（项目群/战略进度展示层实时聚合，不落库）。

## 3. 注入解析语义（t_project_principle 的使用契约，对齐 PRD F7/Q2）

```
resolvePrinciples(case):
  project = case.project_id          # 为空 → 不注入任何下行约束（场景C，AC-F4.3）
  bindings = t_project_principle WHERE project_id=project AND is_deleted=0
  if bindings 为空:                  # 判定条件是"无绑定行"，不是"无启用绑定行"
      return 租户全部 enabled=1 原则   # 全局强制默认（AC-F7.2）
  return [b.principle FOR b IN bindings
          WHERE b.enabled=1          # 项目级覆盖位（本项目单独停用）
            AND b.principle.enabled=1]  # 租户级启停（AC-F5.2，停用即退出注入，绑定保留）
```

边界语义（写死在文档，防实现歧义）：绑定行全为 enabled=0 → 注入空集（项目显式豁免，**不**回退租户默认）。审计要求：绑定变更进审计日志（AC-F3.3）。

## 4. 关键决策与理由

### D1 直接修订 V4，不建 V5 补丁 ✅

- **证据**：V4 为今日草案，无任何环境应用记录（构建日志无 V4 条目；hierarchy 包仅 Strategy.java 实体骨架，无 Mapper/Service，开发未基于草案落持久层）；PRD 仍为"待评审"状态。
- **团队先例**：V1 基线已把 V2 的 t_orchestration 吸收进基线（V1 第 477 行），说明团队惯例是"修订保持迁移干净"而非补丁叠加。
- **收益**：一个 feature 一个迁移——三层贯通是 PRJ-002 单一交付单元，修订后 V4 自洽完整；避免"V4 建错索引、V5 再删了重建"的往返和未来读迁移历史时两文件拼接。
- **兜底**：若个别开发者本地库已手跑 V4 草案，处理 = `flyway repair`（接受校验和变化）或重建开发库（V1 本身是 DROP+CREATE 重建型基线，开发期重建可接受）。正式发布（任何共享环境应用）后本文件即冻结，后续变更一律走 V5+。

### D2 项目-原则关联用关联表（t_project_principle），不用 JSON 字段 ✅

- **反向查询**：F5.4 要求"原则删除时同步清理绑定关系"（`WHERE principle_id=?`），JSON 字段无法索引反向查，只能全表 JSON_OVERLAPS/LIKE 扫描。
- **约束与完整性**：JSON 无法建唯一约束防重复绑定；绑定行需要独立生命周期（enabled 覆盖位 + 审计字段 + 逻辑删），JSON 数组元素承载这些会把"行级状态"压成"文档内嵌状态"，MyBatis-Plus 标准 CRUD 不适用（需 TypeHandler + JSON_CONTAINS 定制查询）。
- **契约一致**：PRD Q3 默认处理即"新增多对多关联表（语义最清晰）"，DBA 确认该默认。
- **JSON 方案的合理场景**（记录取舍依据）：若绑定是无状态的纯 ID 集合且永不需要反向查询/行级覆盖，JSON 更省一张表——但本需求恰好两者都要（AC-F3.3 覆盖语义 + F5.4 清理联动），故排除。
- `enabled` 覆盖位实现"租户全局默认 + 项目级覆盖"：默认语义靠"**无绑定行→租户默认**"的 fallback 实现（不是给每个项目复制全量原则），覆盖语义靠绑定行自身 enabled=0——避免每新建原则都要给所有项目补绑定行的扇出写放大。

### D3 分层开关放 t_tenant 加列，命名 strategy_enabled / program_project_enabled，DEFAULT 1 ✅

- **加列 vs 独立配置表**：开关是租户的 1:1 固有属性而非配置集合，独立表带来 JOIN 与"一租户一行"唯一约束维护成本，无收益；PRD Q8 授权 SE 定。t_tenant 在 IGNORE_TABLES，读写按 id 直查，无拦截器干扰。
- **默认 1（全部启用），理由**：(a) AC-F10.4 明确"存量租户升级后默认全开，不改变 dogfooding 现状"——`ADD COLUMN ... DEFAULT 1` 恰好把存量行一次性回填为 1；(b) P12 的语义是**可以选择性关层**（opt-out），不是默认关层——场景B/C 由实施人员显式关闭（US-5）；若默认 0，升级瞬间所有租户的战略/项目群功能消失，违反 §6.3"升级不改变现有行为"；(c) L1 恒开不设列（F10：L1 不可关），三场景中场景A/现状 dogfooding = 全 1。
- **命名**：沿用 PRD §4.10 配置模型命名与 AC-F10 断言用词（strategy_enabled/program_project_enabled），而非任务书建议的 l3_enabled/l2_enabled——l3/l2 是平台内部行话，实施/运维人员读库排障时"直指功能层"的命名更可诊断；且与 PRD 契约同词，QA 断言、API 字段、DB 列三者一致，减少一层映射。L2 一体开关（项目群+项目不拆）按 PRD Q8 默认处理。

### D4 索引策略：跨表关联索引统一 tenant_id 打头 ✅

租户拦截器把所有查询改写为 `WHERE tenant_id=? AND <关联列>=?`，复合索引 `(tenant_id, 关联列)` 等值+等值完全命中；原草案的单列关联索引（strategy_id/program_id/project_id）需索引定位后回表再过滤租户。涉及：`idx_program_strategy`、`idx_project_program`、`idx_case_project`（均改复合，与 V1 的 idx_tenant_status 风格一致）。`t_quality_gate_rule` 特殊：主路径是"编排启动加载启用规则按优先级排序"，改 `(tenant_id, enabled, priority)`（原草案 stage 在中间，enabled 过滤与 priority 排序都无法用上索引）。

### D5 其他修正（r2 一并落入 V4）

- `t_quality_gate_rule` 加 `uk(tenant_id, name)`：管理页防重 + seed 幂等重放依赖。
- `t_orchestration.injected_json`：F7 注入留痕是 **P0 且 QA 验收依据**（AC-F7.1 三处落点之一），V4 草案未覆盖——这是盘点发现的第三个缺口（任务书只列了两个），加一列快照即可，避免再造"等价载体"表。
- 无物理外键：全库逻辑外键风格（V1 先例），联动清理在应用层（F2 删除置空 program_id / F5.4 原则删除清绑定 / F4.2 解除挂接重算）。
- ALTER 幂等：沿用 V3 注释确立的约定——MySQL 8.0 ADD COLUMN 不支持 IF NOT EXISTS，由 Flyway run-once 保证；建表 IF NOT EXISTS、seed INSERT IGNORE，脚本可安全重放。

## 5. 回滚方案

**发布前（当前状态）**：无环境应用过 V4，无需回滚动作；个别本地库若手跑过草案 → `flyway repair` 或重建库（dev 可接受）。

**发布后回滚**（V4 为纯增量：新表 + 可空列/默认列 + seed，删除不影响 L1 既有功能）：

```sql
-- 逆序手工回滚（Flyway 无 down 概念，DBA 执行）
DELETE FROM `t_quality_gate_rule`  WHERE create_by = 'system';   -- seed 行
DELETE FROM `t_architecture_principle` WHERE create_by = 'system';
DROP TABLE IF EXISTS `t_project_principle`;
ALTER TABLE `t_case` DROP INDEX `idx_case_project`, DROP COLUMN `project_id`;
ALTER TABLE `t_orchestration` DROP COLUMN `injected_json`;
ALTER TABLE `t_tenant`
  DROP COLUMN `strategy_enabled`,
  DROP COLUMN `program_project_enabled`;
DROP TABLE IF EXISTS `t_quality_gate_rule`;
DROP TABLE IF EXISTS `t_architecture_principle`;
DROP TABLE IF EXISTS `t_project`;
DROP TABLE IF EXISTS `t_program`;
DROP TABLE IF EXISTS `t_strategy`;
-- 清 flyway 历史：DELETE FROM flyway_schema_history WHERE version = '4';
```

回滚安全性说明：所有新增列均可空或带默认值，删除无损；分层开关列删除后应用侧"读不到列→视为全开"的兼容由 SE 在代码层兜底（读取失败降级为启用）。

## 本次经验沉淀

1. **草案期迁移直接改、发布后迁移只追加**——判断依据要查证据而不是猜：本次确认了"无构建日志记录 + 实体层只有骨架无 Mapper/Service + V1 基线吸收 V2 表的团队先例"三个事实，才敢直改 V4；三者缺一（尤其有任何共享环境已应用）就应走 V5 补丁，因为 Flyway checksum 冻结是硬约束。
2. **多租户库的关联索引一律 tenant_id 打头**，这不是风格问题而是正确性问题：租户拦截器把每条查询都改写成 `tenant_id=? AND 关联列=?`，单列关联索引意味着每次都回表后再过滤；同时"中间列不在查询条件里"的复合索引（如草案的 (tenant_id, stage, enabled) 配 `enabled=?` 查询）等于半根索引——设计索引时要按"拦截器改写后的真实 SQL"推演，不是按业务原始查询。
3. **"默认值"是升级兼容性的数据层开关**：给存量表加行为开关列时，DEFAULT 的取值等于对全部存量行的一次性表态（回填）。本例 DEFAULT 1 对应"升级不改变现有行为"铁律 + P12 的 opt-out 语义；反过来若语义是"新能力默认关、白名单放开"，就应 DEFAULT 0 且只对新租户写 1——先定语义再定默认值，别让 DEFAULT 跟着感觉走。
