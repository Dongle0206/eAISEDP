## 1. 总体架构：四条改造线

```
┌────────────────────────── L3 战略层（可关） ──────────────────────────┐
│ t_strategy ──┐                                                        │
└──────────────┼────────────────────────────────────────────────────────┘
               ↓ strategy_id（可空）
┌──────────────┴──────────── L2 项目群/项目层（可关） ───────────────────┐
│ t_program ──→ t_project ←──→ t_project_principle（新） ←→ t_architecture_principle │
│                  │ ▲                    t_quality_gate_rule            │
└──────────────────┼─┼───────────────────────────────────────────────────┘
                   │ │ project_id（可空，BIGINT）
        ①下行注入  │ │ ②上行汇总          ③门禁快照         ④分层开关
                   ▼ │
┌──────────── L1 执行层（恒开） ────────────────────────────────────────┐
│ t_case.project_id ─→ GovernanceInjectionService（编排启动解析一次）    │
│ OrchestrationService.runAsync：                                     │
│   ①约束章节 → DerivationContext.governanceContext → 每角色 prompt     │
│   ③QualityGateRuleService 启动快照 → 替换 GATE_ROLES/团队检查点硬编码   │
│ CaseStateServiceImpl.transit →②发布事件 → ProjectProgressListener     │
│   → ProjectProgressService 原子重算 t_project.progress（失败不阻塞）    │
└──────────────────────────────────────────────────────────────────────┘
```

三条原则贯穿全部设计：
- **P12 单向依赖**：L1 编排代码（OrchestrationService/ContextAssembler/DerivationEngine）**不 import** 任何 hierarchy 实体，只认 `DerivationContext.governanceContext`（String）与 `GateRuleSnapshot`（编排包内纯数据类）——依赖方向 L1 永远不知道 L3 存在；
- **P6 零硬编码**：门禁角色集合、部署检查点触发、注入内容全部数据驱动，Java 常量删除后无任何隐藏兜底；
- **P11 多租户**：所有新表/新查询走 MyBatis-Plus 租户拦截器自动注入，跨租户直达靠拦截器过滤返回 404。

## 4. 下行注入机制（核心难点一）

### 4.1 决策 D-1：注入点选在哪

**决策：在 `OrchestrationService.runAsync` 开头（TenantContext.set 之后、LLM 智能规划之前）解析一次，快照存入 `OrchestrationState`，每步构建 DerivationContext 时复用同一份；渲染好的章节文本通过 `DerivationContext.governanceContext` 传递，由 ContextAssembler 统一拼接。**

否决的备选：
- **否决"ContextAssembler 内取数"**：ContextAssembler 是无状态 @Component、被 DerivationEngine 同步调用，若在 assemble 里查 DB 则①引擎层反向依赖 hierarchy 数据源（违反 P3 单向依赖）；②每个角色步骤重复解析（PRD §6.2 要求解析一次 ≤100ms，且编排线程内每步重复查库放大延迟）；③单角色派生（POST /api/runtime/derive）也会被牵连注入，超出 PRD F7 范围（PRD 明确注入对象是"编排中每个角色"）。
- **否决"start()（web 线程）解析"**：start 只建内存态，从 start 到 runAsync 真正执行之间项目配置可能变化；且 runAsync 是断点续跑（runFromStep）也能走到的统一入口之外——runFromStep 从 state 重建，state 里已有快照，天然复用。

注入文本是**预渲染的最终字符串**（GovernanceInjectionService.render 产出），ContextAssembler 只做拼接不取数——L1 组件保持零数据源依赖。

### 4.2 runAsync 改造伪代码

```java
@Async("orchestrationExecutor")
public void runAsync(Long id, Long tenantId) {
    TenantContext.set(tenantId);
    // ★ D-1 注入点：解析一次（caseId→project→原则），失败降级为"无注入"（warn 日志），绝不中断编排
    try {
        InjectionResult inj = governanceInjectionService.resolve(state.getCaseId()); // §4.4
        state.setGovernanceContext(inj.getRenderedSection());  // 章节正文（null=整体省略）
        state.setInjection(inj.getSummary());                  // 留痕清单
        log.info("[Inject] 下行注入解析 caseId={}, projectId={}, 原则={}, 含项目约束={}, 字符={}",
                state.getCaseId(), inj.getProjectId(),
                inj.getPrincipleCodes(), inj.hasProjectDescription(), inj.getRenderedChars());
    } catch (Exception e) {
        log.warn("[Inject] 下行注入解析失败（降级为无注入，不阻塞编排）caseId={}", state.getCaseId(), e);
    }
    // ★ 决策 D-3：门禁规则快照（§6.2）
    state.setGateRules(qualityGateRuleService.loadEnabledSnapshot(tenantId));
    boolean planned = planPipelineWithLlm(state);   // 既有智能规划
    applyGateRulesToSteps(state);                    // 新：规则附着/插入到步骤（§6.3）
    persistState(state, tenantId);                   // 快照（含 injection_json）随首次持久化落库
    ... // 既有 while 循环；每步 DerivationContext.builder().governanceContext(state.getGovernanceContext())...
}
```

## 5. 上行汇总机制（核心难点二）

### 5.1 触发点总览（PRD F8 三处）

| 触发 | 位置 | 机制 |
|---|---|---|
| Case 状态变 done | `CaseStateServiceImpl.transit` | 发布 `CaseDoneEvent` → 监听器异步重算（§5.2） |
| 挂接/解除挂接（含创建带 projectId） | `CaseProjectService`（新增，挂 CaseController） | 更新 t_case.project_id 成功后直接调 `progressService.recalculateAsync(projectId)`；解除时新旧项目都重算 |
| Case 逻辑删除 | `CaseController.delete`（新增端点） | 同上 |

### 5.2 决策 D-2：事件监听而非 transit 内同步调用

**决策：transit 成功后用 Spring 应用事件（CaseDoneEvent）解耦，`ProjectProgressListener` 在独立线程池 `@Async("progressExecutor")` 消费；发布与消费全程 try-catch，任何异常只记 ERROR 日志。**

理由：
1. **失败不阻塞（AC-F8.4 硬约束）**：casestate 包是状态机纯逻辑，若直接注入 ProjectProgressService，汇总抛错会沿调用栈打断 transit——必须隔离。异步事件天然隔离，且监听器 `catch (Throwable)` 后状态保存早已完成。
2. **依赖方向**：casestate（L1 基础设施）不应 import hierarchy 服务；事件类 CaseDoneEvent 放 hierarchy/support，casestate 只依赖 Spring 的 ApplicationEventPublisher 与该 POJO（允许：事件是数据类非服务）。
3. **为什么不用 @TransactionalEventListener(AFTER_COMMIT)**：transit 无外层事务（单条 update 自动提交），普通 @EventListener 即可；幂等性由全量重算保证（§5.3），事件晚到/重放都安全。

```java
// CaseStateServiceImpl.transit 尾部（updated==true 且 target==DONE 且 c.getProjectId()!=null）
try {
    publisher.publishEvent(new CaseDoneEvent(caseId, c.getProjectId(), "status_done"));
} catch (Exception e) { log.error("[Progress] 事件发布失败（不影响状态流转）caseId={}", caseId, e); }

// ProjectProgressListener
@Async("progressExecutor")
@EventListener
public void onCaseDone(CaseDoneEvent ev) {
    try { progressService.recalculate(ev.getProjectId()); }
    catch (Throwable t) { log.error("[Progress] 汇总失败（不阻塞主流程，待重算修复）projectId={}", ev.getProjectId(), t); }
}
```

### 5.3 汇总算法：全量重算（幂等）+ 标准三段写

```java
// ProjectProgressService.recalculate(projectId) —— 全量重算而非增量加减
long total = caseMapper.selectCount(wrapper.eq(Case::getProjectId, projectId));                    // is_deleted 自动过滤
long done  = caseMapper.selectCount(wrapper.eq(Case::getProjectId, projectId).eq(Case::getStatus,"done"));
int progress = total == 0 ? 0 : (int) Math.floor(done * 100.0 / total);
projectMapper.update(null, new LambdaUpdateWrapper<Project>()          // 拦截器自动加 tenant_id
    .eq(Project::getId, projectId)
    .set(Project::getCaseTotal, total).set(Project::getCaseDone, done).set(Project::getProgress, progress));
log.info("[Progress] 重算 projectId={}, total={}, done={}, progress={}", projectId, total, done, progress);
```
- **幂等**：读的是 DB 当前真值，事件重复/并发最终写回的都是正确值（最后写胜出=正确值），AC-F8.1/8.2/8.3 数值口径一致（⌊done/total×100⌋，total=0 → 0）。
- **毫秒级并发交错窗口**（读后写前他人提交）接受：事件低频、窗口 <10ms；PRD P1"手动重算"按钮兜底（本期仅留 Service 方法 `recalculate`，按钮 P1 接线）。
- **项目群/战略聚合不落库**（PRD 明确展示层实时）：`ProgramService.aggregateProgress(programId)` 批量查成员项目内存平均（⌊Σprogress/n⌋），单条 listMaps 查询避免 N+1；战略看板同理再聚合一层。P95 目标 500ms 内（500 项目量级两条聚合 SQL）。
- 项目状态与进度独立：progress=100 不改 status（PRD §7.11 范围外声明）。

## 6. 门禁规则可配置化（核心难点三）

### 6.1 决策 D-3 总纲：启动快照 + 无缓存直查 + 三类型分派

**决策：编排启动时（runAsync 内）`loadEnabledSnapshot(tenantId)` 一次性读库生成不可变快照存入 OrchestrationState，整个编排生命周期（含门禁打回回跳、断点续跑）只用快照；不做运行期缓存（每次编排启动一条 SELECT，开销可忽略，换取消除了缓存一致性这一整类问题——规则改完对"新编排"立即生效、对"在跑编排"零影响，AC-F6.2 快照语义天然满足）。**

删除清单（P6 合规，AC-F6.3 的证明）：`GATE_ROLES` 常量、`isGateStep(role)`、`"team-ops".equals(role)` 检查点硬编码——全部替换，无任何隐藏兜底角色集合。

### 6.2 快照结构

```java
// 编排包内纯数据类（L1 不依赖 hierarchy 实体）
public record GateRuleSnapshot(Long id, String gateType, String gateRole, String checkKey,
        String appliesTo, String stage, Integer maxRetries, String failAction, int priority) {}
// QualityGateRuleService.loadEnabledSnapshot: SELECT WHERE enabled=1 AND is_deleted=0 ORDER BY priority
// （规则级 maxRetries 为 null → 使用 yml eaiselp.orchestration.gate-max-retries 兜底，PRD F6.4）
```

### 6.3 规则→步骤的绑定："附着优先、插入兜底"

stage 边界定义（基于步骤产物类型探测，规划完成后计算）：
- `post_dev` = 最后一个 `code` 类型步骤之后；`post_test` = 最后一个 `test` 类型之后；`pre_deploy` = 第一个 `deploy` 类型之前；
- 边界不存在（LLM 智能规划出了无 code/test 的精简流水线）→ 该 stage 门禁跳过 + WARN 留痕（保守放行，PRD 未定义此场景，记入 §11 R10）。

`applyGateRulesToSteps(state)` 算法：
1. **llm_review**：对每条规则，在其 stage 边界**向前**找最近的 `role == gateRole` 步骤——找到则**附着**（该步骤追加 GATE_INSTRUCTION_SUFFIX + 记 gateRuleId，继承既有判定/打回/重做计数逻辑）；找不到（或该角色步骤在边界之前已消费）则**插入**一个新门禁步骤（index 重排，artifactType=review）。默认 FAST_PIPELINE 的 team-reviewer 恰在 post_dev 边界前 → 附着 → **与现状行为完全等价**（token 不翻倍）；智能规划精简掉 reviewer 时 → 插入 → 企业治理强制生效。
2. **human_approval**：在 stage 边界标记"审批闸"（不新增步骤）。同一 stage 多条 human_approval 合并为**一次**检查点等待（防多次 30 分钟阻塞，§11 R3）。
3. **auto_check**：登记到收尾检查清单，编排结束后、Git push 前执行（§6.4）。

### 6.4 三种 gate_type 执行期分派（while 循环内改造）

| gate_type | 执行时机 | 行为 |
|---|---|---|
| `llm_review` | 附着/插入步骤产出返回后 | 复用既有 `parseGateResult/extractGateReason/findRerunTarget`：FAIL 且 fail_action=block → 打回重做（超过规则级 max_retries → 该步 failed + 后续步骤 skipped + 编排不部署，现状语义）；FAIL 且 warn → gateResult=FAIL_WARN 记录放行；PASS/无标记 → 放行（现状"忘输出判定视为 PASS"告警语义保留）。max_retries=0 → 首次 FAIL 即终判（AC-F6.4） |
| `human_approval` | 执行到审批闸位置 | 复用 `awaitApproval`（改造：入参从无到 ruleIds+stage；检查点 operation=`orchestration_gate_{stage}_{orchId}`，消息注明命中的规则名）。APPROVED→继续；REJECTED/TIMEOUT→ 跳过其后 deploy 类步骤（等价现状"跳过部署"，其余成果保留）；检查点服务异常降级放行 + ERROR（现状语义）。现状 team-ops 检查点由 seed 规则 c) 承接（AC-F6.5 复用检查点页面与 30 分钟超时） |
| `auto_check` | 编排收尾、`gitService.commitWorkspace` **之前** | `check_key=code_validation` → `codeValidationService.validateWorkspace(caseId)`（checkKey→检查器用 Map 注册表分发，本期仅 code_validation 一项，新增检查器=新增注册项）。allPassed=false 且 block → 编排终判失败、**不 commit/push/不触发 CI**（AC-F6.6）；warn → validation 记录 FAIL 告警放行。**无 auto_check 规则时验证仍执行**（现状行为）——语义：validateWorkspace=验证（总跑、记录），auto_check 规则=是否阻断的治理决策（数据驱动）。升级等价性由此保持 |

### 6.5 升级等价性验证表（Q1 裁决依据）

| 现状行为 | 升级后（seed 三条规则） | 等价? |
|---|---|---|
| reviewer/qa 产出含 GATE:PASS/FAIL，FAIL 打回 ≤2 轮 | 规则 a/b 附着到同两步，block/max_retries=2 | 是 |
| team-ops 前检查点等待 30min，拒绝跳过部署 | 规则 c) pre_deploy 审批闸，同 awaitApproval | 是 |
| security/performance 若被智能规划选中则带门禁 | 不 seed——租户自建规则才有 | 行为变化点（升级后默认无此二角色门禁），已在 seed 注释与发布说明标注；FAST_PIPELINE 不含二者，主流程无感知 |
| 收尾验证只记录不阻断 | 无 auto_check seed → 维持 | 是 |

### 7.1 决策 D-4：t_tenant 加两列；L2 一体；关层=入口拒绝+数据链路保留

### 7.3 读取点与降级行为

`TenantLayerService`：`ConcurrentHashMap<tenantId, LayerFlags>` 本地缓存，**写后主动失效**（PUT layers 成功即 evict，管理员改完立即可见；读 miss 回源 selectById，无 TTL——开关读写比极低，CacheAside 足够）。

## 本次经验沉淀

1. **配置化改造"删除硬编码"的验收锚点是升级等价性表，不是功能清单**。本次 GATE_ROLES→t_quality_gate_rule 改造，真正难的不是"读表驱动"（一小时的活），而是证明"删掉常量后默认行为不变"——seed 三条规则必须与硬编码行为逐项对齐（含 team-ops 检查点这种藏在另一个 if 里的隐式门禁）。做法：先列"现状行为清单"（§6.5），每行找 seed 规则或变更点承接，变更点显式标注进发布说明。没有这张表，"配置化"改造极易在升级夜翻车。

2. **跨层机制的解耦模式：L1 编排只认 String/快照，不认 L2/L3 类型**。下行注入若让 ContextAssembler 直接查 hierarchy 表，就造出了 L1→L2 的反向依赖（违反 P3），且单角色派生被牵连。本次定型模式：**边界层（runAsync 入口）解析一次 → 不可变快照（String 章节 + record 规则）存入编排状态 → 下游只消费快照**——同时免费拿到"运行中不受配置漂移影响"（快照语义）、"断点续跑复用同一份约束"、留痕载体三个特性。凡是"上层策略要进下层执行引擎"的场景，都应优先做快照注入而不是让引擎实时查上层。

3. **MyBatis-Plus 租户拦截器的隐性约束要在方案期就固化成编码规约**：新表默认进拦截器（不进 IGNORE_TABLES）意味着所有自定义 SQL 都会被 rewrite——子查询/SET 子句是重灾区。本次刻意把进度汇总写成"两条标准 count + 一条 LambdaUpdateWrapper set 三列"这种拦截器友好形态，而不是一条优雅的原子 UPDATE 子查询。规约：租户级表上的非标准 SQL（子查询/updateText）必须在方案评审时单独标注验证，否则 Dev 阶段会在集成测试才撞上 SQL 解析异常。
