逐端点核对 `@RequirePermission` 注解：

| Controller | 端点数 | 注解情况 |
|---|---|---|
| StrategyController | 7（page/create/get/update/transit/delete/board） | 全部有（strategy:view/create/edit） |
| ProgramController | 5 | 全部有（program:view/create/edit） |
| ProjectController | 7（含 linkCase/unlinkCase） | 全部有（project:view/create/edit；挂接/解除走 project:edit） |
| PrincipleController | 8（含 toggleEnabled/bindProjects） | 全部有（principle:view/create/edit） |
| QualityGateRuleController | 6（含 toggleEnabled） | 全部有（gate:view/create/edit） |

| CaseController.delete（新增） | 1 | 有（case:delete，V4 seed 1045） |
| **合计** | **36** | **35 显式注解 + 1 个设计内登录即可** |

**TenantLayerController GET 无注解的定性：可接受。**
- JWT 拦截器（order=1）覆盖全部 `/api/**`，未登录 401，"登录即可"成立；
- 响应仅含本租户两个开关布尔值（`TenantContext.get()` 来自 JWT claims，非请求参数），无跨租户、无配置明细、无敏感数据；
- 菜单渲染（T29）确实需要全角色可读。信息价值极低（见风险 L3）。

**结论：鉴权层无缺失。**

## 二、越权（重点）

### 2.1 跨租户访问 —— 未发现可利用路径

隔离机制核实：
- 6 张新表（t_strategy / t_program / t_project / t_project_principle / t_architecture_principle / t_quality_gate_rule）均带 `tenant_id` 且**均不在** `EaiselpTenantHandler.IGNORE_TABLES` 中 → MyBatis-Plus TenantLineInnerInterceptor 对所有标准 MP 查询（selectById/getOne/selectList/selectCount/selectBatchIds/update/delete）自动追加 `tenant_id = 当前租户`；
- 新代码全部走 LambdaWrapper（类型安全列名），无自定义 SQL/子查询（SE §11 R4 规约被遵守，仅 DashboardController 存量代码有一处 QueryWrapper，列名硬编码无用户输入）；
- 直改 URL /{id} 攻击：`getById(id)` 跨租户 → null → 统一 404，文案不区分"不存在/不属于本租户"，无存在性泄露（AC-ISO.2 落实）；
- 关联引用校验同样走租户过滤查询：ProgramController 校验 strategyId、ProjectController 校验 programId、PrincipleServiceImpl.bindProjects 校验 projectIds（selectCount 不齐 → 404 拒绝）——他租户 ID 作为外键注入不可行。

### 2.2 水平越权（Case 挂接）—— 未发现

`POST /api/v1/projects/{id}/cases/{caseId}`：
- project 与 case 双实体均经租户拦截器加载（`loadCase` 按 case_id + 隐式 tenant_id），**他租户 Case → null → 404**，无法挂接到本项目；
- 更新语句 `eq(Case::getId, c.getId())` 同样被拦截器追加租户条件，二次防护。

`DELETE`（解除）的"非 done 不可解"校验：
- 服务端校验 `CaseStatus.DONE.dbValue().equals(c.getStatus())` → 400；
- CaseStatus 状态机中 done 为**终态**（`DONE → ∅`），无法通过 transit 流出 done 后再解除；
- 绕过路径核查：① `case:delete` 删 Case 会静默解除挂接（但 Case 本体已删，非"解除保留"语义）；② 项目删除 `deleteWithUnlinkCase` 清空全部挂接（含 done）——均为合法破坏性操作且已审计，属语义边界而非越权（见 L1/L2）。

### 2.3 垂直越权 —— 未发现

- `strategy:view`（V1 seed 1029）仅授 platform_admin（2027）与 executive（2057）；`strategy:create/edit`（V4 seed 1032/1033）仅 platform_admin（2058/2059）与 executive（2090/2091）。**tenant_admin 无任何 strategy 权限原子**，直接调 API 会被 PermissionInterceptor（order=2）以 40301/HTTP 403 拒绝；
- 拦截器顺序核实（RuntimeWebMvcConfig）：0 限流 → 1 JWT → 2 权限 → 3 分层守卫。guard 在权限之后仅影响"关层时先见 403 而非 43001"，不产生绕过；权限拦截器注册于 `/api/**` 全前缀，36 个端点全覆盖；
- 权限矩阵核对（V4 r3 seed 2058~2091 对齐 SE §10）：engineer 零新增、executive 无 program:edit、project_manager 无 program/principle/gate:edit 与 tenant:layer:edit——最小权限落实，无过度授权。

### 2.4 租户上下文来源链（纵深核实）

X-Tenant-Id 头（TenantContextFilter）在 JWT 解析前设置，但 `LoginUser.set()` 会用 JWT claims 的 tenantId **覆盖**之；t_user.tenant_id NOT NULL → 签发 token 必含 tenantId → 正常路径客户端无法选租户。遗留隐患见 L5。

## 三、注入

- **SQL 注入：未发现。** 新增代码 100% LambdaQueryWrapper/LambdaUpdateWrapper（参数化）；分页/过滤参数（status/strategyId/programId/enabled）或经枚举白名单校验或为 Long 类型；无字符串拼接 SQL、无 apply()/last()。
- **审计 JSON 注入：已防。** 各 Controller 的 safeJson() 对 title/name/comment 做 \\、"、\n、\r 转义后拼入审计 detail。
- **KPI JSON 存储链：服务端安全。** KPI 数组由 Jackson `writeValueAsString` 序列化（保证合法 JSON），前端 `JSON.parse` try-catch 降级空数组，渲染走 escapeHtml/escapeAttr——**唯一例外见风险 M1（strategy-list.html 的 k.unit）**。
- **前端 XSS 总体：9 页面均内置 escapeHtml/escapeAttr（转义 &<>"' 五字符，实现正确），标题/名称/描述/章程/原则内容/门禁配置等用户可控文本渲染均已覆盖**；URL 参数均 encodeURIComponent；下钻链接 id 取自服务端数值主键，无注入面。

## 四、敏感数据

- **V4 seed：无敏感值。** 原则/门禁内容均为治理文本；无密钥、口令、内部 IP；ID 用 7000000+/8000000+ 保留区间避让雪花；INSERT IGNORE 幂等。
- **审计日志：未记录敏感字段。** 仅记 title/name/code/enabled/projectId 等元数据，不落 KPI 值、章程全文、原则内容。
- **LLM 链路租户泄露：未发现。** 治理注入（GovernanceInjectionService）在编排租户上下文内解析，原则查询经租户拦截器；注入文本仅进入**本租户**编排的角色 prompt，无跨租户编排路径。
- **prompt 注入面：存在，见风险 M2。**

## 五、新攻击面

- **LayerGuardInterceptor 43001/43002**：HTTP 200 + 业务码（禁 500）设计合理；未认证请求在 order=1/2 已被挡，不泄露权限布局；已认证用户可感知本租户层开关状态——信息价值低（L3）。
- **策略/门禁启停滥用**：PUT /{id}/enabled 需 principle:edit / gate:edit（仅 platform_admin/tenant_admin），且全量审计（principle_enabled / gate_enabled），快照语义保证在跑编排不受影响（不可用于干扰他人进行中的流程）。单管理员关停 block 门禁属授权内行为，建议增加治理提示（L4）。
- **门禁规则数据驱动化（替换 GATE_ROLES 硬编码）**：gateRole/gateRole→步骤附着逻辑有白名单语义（仅匹配既有步骤或插入标准门禁步骤），无角色名注入执行面；rule.name 拼入门禁步骤 instruction —— 归入 M2 prompt 注入面统一治理。

## 本次经验沉淀

1. **多租户新表的"安全默认"应被结构化验证而非口头确认**：本次 6 张新表全部带 tenant_id 且未进 IGNORE_TABLES、查询全部 LambdaWrapper（R4 规约），隔离无需逐条人工确认——规约本身即门禁。经验：把"新表必带 tenant_id + 禁自定义 SQL"固化为 CI 检查项（扫 @TableName 实体与 IGNORE_TABLES 差集、扫 QueryWrapper/apply/last），安全评审即可聚焦业务语义（挂接/解除/启停）而非重复查隔离机制。
2. **前端模板渲染的"兜底分支"是转义遗漏的高发点**：9 个页面主体渲染均规范转义，漏洞恰好出在 `map[值] || 原始值` 的兜底拼接与 title 属性的多段拼接处。经验：约定"任何进入 .html() 的表达式，每个动态段必须显式包 escapeHtml/escapeAttr，无例外"，并以 ESLint 自定义规则或 DOMPurify 统一收口，消灭逐处自觉。
3. **数据驱动化（规则/原则可配置）会把配置写入者变成 prompt 注入者**：平台把硬编码门禁改为租户数据驱动后，信任边界从"平台代码"移到"租户配置文本"，project.description 这类低权限可写字段进入全角色 prompt 即成注入面。经验：凡用户可控文本进入 LLM prompt，一律按"数据"处理（定界 + 声明非指令 + 长度/字符约束），门禁/评审类角色 prompt 原则上不注入业务侧自由文本。
