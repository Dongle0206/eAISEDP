# 任务执行计划

## 1. 流程档位：fast

**判定理由**：6 个收尾项均为三层贯通评审已定位到"文件+行为"级的小型修补/补显（后端数据已在、接口已在、缺前端展示或局部逻辑补强），无新表、无新接口契约、无跨模块架构决策；Swagger 为标准依赖接入。单文件改动为主，可一次任务清单直排，无需 standard 档的独立技术方案与 QA 全回归。

## 2. PRD 要点

本 case 关闭三层贯通评审遗留的 5 个收尾项与 1 个文档项，目标是把"演示能跑"补齐为"评审意见全部落地"：编排过程对用户透明可审计（D5 注入清单前端可见）、治理门禁不可被重试旁路（D10 断点续跑补终判检查）、Case 与 L2 项目双向闭环入口补全（D4 挂接按钮）、高管角色一屏直达战略看板（D7 菜单入口）、平台注入文本可定界防角色篡改且门禁角色豁免注入以保证裁判中立（M2）、OpenAPI 文档自助可查且生产可关（Swagger）。全部改动限定在 runtime 模块与 eaiselp-web-separate 前端，不新增数据库迁移。

## 5. 变更影响评估

- **波及面**：runtime（编排重试路径、治理注入、上下文组装、Web 配置、pom）+ web（case-detail、menu.js）。无 DB 迁移、无新接口、无契约变更。
- **D10 为唯一逻辑高危点**：runFromStep 是断点续跑主干，改动需保证"无门禁终判"场景零行为变化（AC-D10.3 回归）；建议拒绝策略用 BizException 走既有错误码通道，前端重试按钮区显示后端 message。
- **M2 有既有消费方**：定界标记会改变 governanceContext 字符串内容，所有断言注入文本原文的单测需同步更新；对 LLM 提示词是纯增量包裹，不影响既有注入语义。
- **Swagger 安全面**：仅白名单放行文档路径，业务接口权限拦截不变；生产 profile 必须置 springdoc.api-docs.enabled=false（随本任务在 prod 配置中落默认值），防止接口清单外泄。
- **前端两处均为增量渲染**：case-detail 新卡片/新按钮在既有 DOM 容器内追加，不动既有编排轮询逻辑；menu.js 一行增量走已验证的 layers 过滤管线。

## 本次经验沉淀

1. **评审收尾项要"数据链路对齐"而非单点补显**：D5 的根因是后端已留痕（injectedPrinciplesJson）但前端契约未消费——后续凡评审提出"可见性"类问题，先查数据是否已在响应里，多数时候是展示层缺口，改动半径远小于预期。
2. **重试/续跑类旁路要在"终判"语义上设闸**：任何允许从中间步骤恢复的执行引擎，恢复入口都必须重新校验不可绕过的终态（门禁终判、人工锁、不可逆标记），且把"拒绝旁路"与"重置后合法重跑"拆成两条显式路径，避免用同一个标志位糊住两种语义。
