## 3. 关键决策与理由

### D1 t_milestone 处置结论：V1 结构**不够用**，ALTER 补列激活（不重建）✅

- 缺口清单：两级归属（V1 只有 VARCHAR program_id 弱关联，与 V4 t_program.id BIGINT 错位）、达成日期、负责人、描述、用户可见编号；status 默认 not_started 与词汇表不符。死表零数据，无存量迁移负担。
- **Q3 裁决（owner_type+owner_id 单列对）DBA 确认**：双列二选一非空（program_id2/project_id）产生 OR 查询无法走单索引，且"二选一"约束只能靠应用层；单列对 + idx(tenant_id, owner_type, owner_id) 三等值完全命中，沙箱 EXPLAIN 验证 ref 访问。
- 不重建表的理由：V1 已发布不可改，DROP+重建虽对死表等效但破坏"已发布迁移的历史完整性"惯例；ALTER 补列语义清晰且 legacy 列处置（放松 NOT NULL 支持只读不写）必须通过 ALTER 表达。

### D2 gate_result 宽度纠偏 VARCHAR(8)→VARCHAR(16)，且**不加新索引** ✅

- 任务书 VARCHAR(8) 存不下 9 字符的 `FAIL_WARN`（PRD §4.1.2④ 枚举含它）——上线后首批 warn 判定即写入失败/截断，属必须纠偏的规格错误。
- 索引评估结论：不加。RT 计算访问路径恒为"先定位 Case 集合→再取派生记录"，入口是 case_id(±role)，既有 idx_tenant_case / idx_case_role 已覆盖（沙箱 EXPLAIN 确认）；gate_result 基数 3+NULL 单列索引无选择性，并入复合也不覆盖 finished_at 仍需回表。按需加列不按需加索引。

### D3 依赖表唯一键取租户粒度 uk(tenant_id, from, to, type)（任务书 uk(from,to,type) 为复合键尾部）✅

- 沙箱实测：uk 不含 tenant_id 时"租户 B 登记与租户 A 相同 ID 对"被跨租户误拦——生产雪花 ID 下虽不可能发生，但导入/修复脚本用小 ID 即复现；且拦截器改写后的真实 SQL 是 `WHERE tenant_id=? AND from_project_id=?`，(tenant_id, from_project_id) 前缀完全命中正向主查询（EXPLAIN 验证）。
- 与 V4 t_project_principle"tenant 不入 uk"先例的分歧已写进迁移注释：该先例依赖"两端全局雪花 ID 跨租户同对不可能"，本表同样成立，但唯一性本身是租户内治理规则（P11 边界），入 tenant_id 代价仅索引项 +8 字节，权衡取租户粒度。
- 看板全图加载（WHERE tenant_id=?）由 uk 的 tenant_id 前缀承担；idx(tenant_id, to_project_id) 只服务反向查询"谁依赖 P"与删除联动清理。

### D4 ADR 关联原则用 JSON 列而非关联表/单值列 ✅

- PRD §4.4 契约是"可空**多选**"（任务书 related_principle_code 单值是简写）：单值列装不下 AC-F4.4 的多原则关联；JSON_CONTAINS 租户内扫描（5000 ADR 量级）毫秒级，无需索引。
- 不建 t_adr_principle 关联表：原则引用不需要行级启停/独立生命周期（对照 V4 D2 建表的判据——t_project_principle 是因要 enabled 覆盖位+删除联动才建表），纯展示引用一张表过度设计。

### D5 权限 seed：13 原子（view/create/edit 三段制），非任务书摘要的 9 原子 ✅

- PRD §4.6 表格是 view/create/edit 三段；只 seed view/edit 的话 create 接口的 @RequirePermission 全员 403，AC-RBAC.1（project_manager create 200）直接挂。dora:view 为纯只读无 create/edit，共 13。
- id 区间严格顺延（1046~1058 / 2092~2133），与 V4 r3 的 1032~1045 / 2058~2091 无一碰撞（沙箱 max(id) 核对）；INSERT IGNORE 幂等重放实测通过。

### D6 命名对齐 PRD 契约（任务书简写 → 落地名，已在 V5 头部注释声明）✅

t_tech_radar→**t_tech_radar_item**（PRD §4.5 表名）；dep_type→**dependency_type**、from_project→**from_project_id**/to_project_id（PRD §4.3 列名）。原则：PRD 是 PO/UX/BA/Dev/QA 共同契约，QA 用例与 AC 均引用 PRD 用词，DB 列名与之同词减少一层映射。

## 本次经验沉淀

1. **规格里的字面宽度要按枚举值实长复核**：任务书写 gate_result VARCHAR(8)，但枚举 FAIL_WARN 是 9 字符——这类"差一个字符"的规格错误编译期不报错、上线后首批 warn 判定才爆，是埋点列最典型的隐性事故。DBA 对任何 VARCHAR(n) 都应列出全部枚举值逐个数字符（含未来可能新增的 `_WARN` 类后缀，适当留余量）。
2. **沙箱实测能推翻纸面推演的索引/唯一键设计**：uk(from,to,type) 纸面论证（V4 雪花先例）成立，但沙箱里"租户 B 登记同 ID 对被误拦"暴露了防御性缺口；多租户表的唯一约束取租户粒度（业务规则的粒度）比依赖"ID 全局唯一所以跨租户不可能撞"更稳——先例要理解其成立前提再沿用，且落库前用一个假数据脚本把约束打一遍。
3. **"保留只读不写"的 legacy 列必须放松 NOT NULL 才真正可执行**：t_milestone 的 program_id/milestone_id 若保持 NOT NULL，每次插入仍被迫填假值，"不写"就是空话——死表激活类变更要先把 legacy 列的写路径物理关死（NULL 化），再谈新列设计。
