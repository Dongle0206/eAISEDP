### 2.2 t_milestone 激活（Q3 回应=决策 D-3）

```sql
-- 决策 D-3：owner_type + owner_id 单列对（而非 program_id/project_id 双列二选一非空）
--   理由：①唯一约束/索引形态统一（一个 idx 覆盖两级查询）；②两级归属语义在代码里是同一张
--   状态机与同套 CRUD，双列形态会产生"两列都填/都不填"的脏数据防线；③PRD Q3 默认处理同此。
ALTER TABLE `t_milestone`
  ADD COLUMN `owner_type` VARCHAR(16) NOT NULL DEFAULT 'project' COMMENT '归属层级: program/project',
  ADD COLUMN `owner_id` BIGINT NOT NULL DEFAULT 0 COMMENT '归属 t_program.id 或 t_project.id',
  ADD COLUMN `ms_code` VARCHAR(32) DEFAULT NULL COMMENT '用户可见编号（如 MS-0001，租户内唯一）',
  ADD COLUMN `achieved_date` DATE DEFAULT NULL COMMENT '达成日期（仅 achieved 态有值）',
  ADD COLUMN `owner_name` VARCHAR(64) DEFAULT NULL COMMENT '负责人';

-- 旧列治理（死表零数据，安全；PRJ-002 Q6 t_case.program_id "保留只读不写"先例）：
--   放宽 NULL 后新写入一律 NULL；uk_tenant_program_ms 中 NULL 不参与去重（MySQL 语义），无冲突面。
ALTER TABLE `t_milestone`
  MODIFY COLUMN `program_id` VARCHAR(64) NULL DEFAULT NULL COMMENT '[legacy 只读不写] 旧项目群弱关联',
  MODIFY COLUMN `milestone_id` VARCHAR(32) NULL DEFAULT NULL COMMENT '[legacy 只读不写] 旧编号',
  MODIFY COLUMN `status` VARCHAR(32) NOT NULL DEFAULT 'planned' COMMENT 'planned/achieved/delayed';

ALTER TABLE `t_milestone`
  ADD UNIQUE KEY `uk_tenant_ms_code` (`tenant_id`, `ms_code`),
  ADD KEY `idx_ms_owner` (`tenant_id`, `owner_type`, `owner_id`, `target_date`);
```

状态机落库校验在 Service 层（§5.2）；`achieved_date 仅 achieved 态有值` 由应用层维护（撤销达成时清空），不加 DB 约束（条件约束 MySQL 不支持，实体校验足够）。

### 2.3 三张新表（建议 DDL 语义）

```sql
CREATE TABLE IF NOT EXISTS `t_project_dependency` (
  `id` BIGINT NOT NULL,
  `tenant_id` BIGINT NOT NULL DEFAULT 0,
  `from_project_id` BIGINT NOT NULL COMMENT '依赖方（规范向：A depends_on B 则 from=A）',
  `to_project_id` BIGINT NOT NULL COMMENT '被依赖方',
  `dependency_type` VARCHAR(16) NOT NULL COMMENT '归一化存储: depends_on(强)/relates_to(弱)——blocks 登记换向后归一为 depends_on（D-5）',
  `orig_type` VARCHAR(16) NOT NULL COMMENT '用户原始登记类型 blocks/depends_on/relates_to（仅文案区分用，判定不看它）',
  `remark` VARCHAR(500) DEFAULT NULL,
  `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `create_by` VARCHAR(64) DEFAULT NULL,
  `update_by` VARCHAR(64) DEFAULT NULL,
  `is_deleted` BIGINT NOT NULL DEFAULT 0 COMMENT '逻辑删位：0=活跃，删除时置=id（见下方说明）',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_dep_edge` (`tenant_id`, `from_project_id`, `to_project_id`, `dependency_type`, `is_deleted`),
  KEY `idx_dep_to` (`tenant_id`, `to_project_id`)
) COMMENT='跨项目依赖表（F3，P3 环检测载体）';

CREATE TABLE IF NOT EXISTS `t_adr` (
  `id` BIGINT NOT NULL,
  `tenant_id` BIGINT NOT NULL DEFAULT 0,
  `adr_code` VARCHAR(32) NOT NULL COMMENT '编号（默认 ADR-NNN，租户内唯一）',
  `title` VARCHAR(200) NOT NULL,
  `status` VARCHAR(16) NOT NULL DEFAULT 'proposed' COMMENT 'proposed/accepted/deprecated/superseded',
  `context` MEDIUMTEXT NOT NULL COMMENT '上下文（五段式，必填）',
  `decision` MEDIUMTEXT NOT NULL COMMENT '决策（必填）',
  `consequences` MEDIUMTEXT NOT NULL COMMENT '后果（必填）',
  `related_principles` JSON DEFAULT NULL COMMENT '关联原则 code 数组，如 ["P11","P3"]（存在性校验见 §7.2）',
  `superseded_by` VARCHAR(32) DEFAULT NULL COMMENT '被取代关系：指向新 ADR 编号（superseded 态必填）',
  `deprecate_reason` VARCHAR(500) DEFAULT NULL COMMENT '废弃说明（deprecated 态必填）',
  `decision_date` DATE DEFAULT NULL,
  `author` VARCHAR(64) DEFAULT NULL,
  -- 审计五件套 + is_deleted TINYINT 同各表
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_adr_code` (`tenant_id`, `adr_code`),
  KEY `idx_adr_status` (`tenant_id`, `status`)
) COMMENT='架构决策记录表（F4，不限层）';

CREATE TABLE IF NOT EXISTS `t_tech_radar_item` (
  `id` BIGINT NOT NULL,
  `tenant_id` BIGINT NOT NULL DEFAULT 0,
  `name` VARCHAR(200) NOT NULL COMMENT '技术项名称（租户内唯一：一技术一当前态）',
  `quadrant` VARCHAR(16) NOT NULL COMMENT 'techniques/tools/platforms/languages',
  `ring` VARCHAR(16) NOT NULL COMMENT 'adopt/trial/assess/hold',
  `reason` VARCHAR(2000) NOT NULL COMMENT '理由（必填）',
  `review_date` DATE NOT NULL COMMENT '评审日期（必填）',
  `remark` VARCHAR(500) DEFAULT NULL,
  -- 审计五件套 + is_deleted TINYINT
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_radar_name` (`tenant_id`, `name`),
  KEY `idx_radar_quad` (`tenant_id`, `quadrant`, `ring`)
) COMMENT='技术雷达表（F5，不限层）';
```

**t_project_dependency 两个关键设计说明（D-5）**：

1. **类型归一化存储**：登记入参仍是三值枚举（blocks/depends_on/relates_to，PRD P6 领域字典），但落库前归一——`blocks` 快捷录入（"A 阻塞 B"）换向存为 `from=B, to=A` 且 `dependency_type='depends_on'`，原始语义存 `orig_type='blocks'` 仅供文案（"硬阻塞"/"受阻"）。**收益**：AC-F1.1 第二次"B depends_on A"直接撞 `uk_dep_edge` 被拒（PRD 字面唯一键 (from,to,type) 无法拒绝"blocks 与 depends_on 同向"的语义重复）；blocked 判定与环检测只看 `dependency_type` 一个谓词，复杂度减半。
2. **逻辑删与唯一键共存**：`is_deleted` 用 BIGINT 且删除时置 `=id`（活跃行恒 0，uk 第五列保证同对依赖删后可重登；二次删除的行 id 不同也不冲突）。沿用逻辑删语义满足 PRD"删除为逻辑删"，避免 t_project_principle 式 uk 不含删除位的重绑冲突问题（该先例的隐患在此表规避）。

## 4. DORA 聚合服务（核心难点一，决策 D-1/D-2）

### 4.1 决策 D-1：实时聚合 + 5 分钟 TTL 缓存，不上预聚合表（Q7 回应）

**数据量评估**（PRD §6.2 规格量级：单项目 1000 Case / 5000 派生 / 10000 审计行）：

| 步骤 | 查询形态 | 命中索引 | 预估 |
|---|---|---|---|
| scope 解析 | t_project 按 program_id IN / 全量 id | idx_project_program | <5ms |
| Case 池 | t_case WHERE tenant_id=? AND project_id IN(...) | idx_case_project | <20ms，≤1000 行 |
| done 审计 | t_governance_log WHERE tenant_id=? AND action='case_transit' AND create_time>=? AND resource_id IN(...)（IN 分批 500） | idx_tenant_action_time（V5 新增，§2.4） | <100ms，≤1000 行 |
| 编排终态 | t_orchestration WHERE tenant_id=? AND case_id IN(...) AND status IN('done','failed') | idx_orch_case | <100ms，≤1000 行 steps_json |
| 派生明细 | t_derivation WHERE tenant_id=? AND case_id IN(...) | idx_tenant_case | <100ms，≤5000 行 |

内存聚合（去重/分位数/steps_json Jackson 解析）<100ms。**单次全链路 <500ms，P95 ≤1s 达标余量充足；"全部项目"维度按租户项目数×N 同比放大，dogfooding 量级（个位数项目）仍 <1s。**

结论与依据：
- **实时聚合**：数据量证明不足以上预聚合表（预聚合需定时任务+增量回填+失效管理三件套，成本大于收益）；PRD 时效约束"延迟 ≤5 分钟"由缓存 TTL=300s 天然满足（done 流转后最迟 5 分钟可见，正好是上界）。
- **缓存**：`ConcurrentHashMap<String, CacheEntry>`（key=`tenantId|scope|scopeId|periodDays`，value=DoraBoardVo+expireAt），同步计算、TTL 300s、无主动失效（治理数据非强一致）。零新增依赖（不引 Caffeine）。每次**未命中计算**打结构化日志（tenantId/scope/四指标样本数/耗时，§6.6 PRD 要求）。
- **升级触发条件**（写死，防"到时候再说"）：单租户 done Case 累计 >2 万或看板 P95 实测 >800ms 时，启用预案 R1-2（§11）——按 (tenant_id, project_id, stat_date) 日粒度快照表 t_dora_snapshot，本方案的计算逻辑全部下沉为快照回填复用。

### 4.2 三级维度聚合与排除总纲

- 维度解析：`scope=project`（scopeId 必填）/ `scope=program`（成员项目合并）/ `scope=all`（租户全部项目，走拦截器自动过滤）。**project_id 为空的 Case 在 Case 池阶段即被排除**（IN 条件天然不含），三级维度均不计入（AC-F1.6 的 C9）。
- **SQL 形态规约（沿 PRJ-002 SE §11 R4）**：不写跨 IGNORE_TABLES 边界的 JOIN（t_governance_log 不走拦截器、业务表走，JOIN 改写行为不可控）；全部采用"两段式 IN 查询 + 内存聚合"。DORA 是只读消费端，不涉 UPDATE，规约仅约束查询形态。
- t_governance_log 查询**手写 tenant_id 等值条件**（表在 IGNORE_TABLES，F-21）；t_case/t_orchestration/t_derivation 查询不写 tenant_id（拦截器注入）。

### 4.3 四指标计算（口径唯一权威=PRD §4.1.2，本节为可执行落地）

公共：`periodStart = now - periodDays`；done 审计明细取回后**内存解析 detail JSON 取 targetStatus='done'**（不依赖 JSON 列函数，防索引失效与方言差异），按 caseId **去重取最早一条**（幂等重放防线，F-20）。

**① 部署频率 DF**
```
分子 = 周期内首次流转 done 的去重 Case 数 N
DF = N / periodDays（自然日天数，无数据天计 0）
分档徽标：DF≥1 → 精英/高档区间渲染（前端分档表常量，集中一处定义）
```

**② 变更前置时间 LT**
```
样本 = 有 done 审计的 Case：lt = doneTs − t_case.create_time
排除：t_case.status='done' 但无对应 case_transit 审计的 Case → excludedCount M
     （严禁用 update_time 冒充——F-20/update_time 会被任意更新改写）
看板文案："样本 N（另有 M 条历史数据不可回溯，已排除）"（AC-F1.5）
分位数规则（满足 AC-F1.2 断言的落地实现，QA 照此）：
  P50 = 线性插值分位（Excel PERCENTILE.INC 语义）：N=2 样本 [24h,48h] → 36h ✓
  P90 = 向上取整序位（ceil(0.9×N)）：保守取大，N=2 → 第 2 个 = 48h ✓
  （两规则并列是显式口径决策：中位连续、长尾保守，治理语义"风险高估优于低估"）
单位自适应：<24h 显示小时，否则显示天（前端）
```

**③ 变更失败率 CFR（代理指标，tooltip 明示）**
```
分母 = 终态编排 Case 去重数（t_orchestration.status ∈ {done,failed}，按 case 取最新终态记录）
分子 = 终态 Case 中"门禁终判失败"者，两源合一（F-22）：
  a) llm_review 终判超限：steps_json 存在 status='failed' 且 gateResult='FAIL' 的步骤
  b) auto_check block 阻断：编排 status='failed' 且 validation_json.allPassed=false 且无 a) 信号（防双计）
FAIL_WARN 放行不计入（gateResult='FAIL_WARN' ≠ 'FAIL'）
打回率（参考值，非四指标）：终态 Case 中存在过 gateResult='FAIL' 步骤但未终判失败者 / 分母
steps_json 解析失败：该 Case 跳过并计入 parseErrorCount，指标卡降级"该项暂不可用"（§6.3 PRD）
```

**④ 恢复时间 RT（含埋点，决策 D-2）**
```
样本框 = 周期内 done 且非 CFR 分子的 Case（终判失败无恢复）
按 (caseId, role) 分组取派生记录：
  有埋点样本（组内存在 gate_result 非空行）：
    firstFailTs = min(finished_at where gate_result='FAIL')
    lastPassTs  = max(finished_at where gate_result='PASS')
    firstFail && lastPass && lastPass > firstFail → RT = 差值，approximate=false
  无埋点（历史数据，全 NULL）且组内行数>1：
    RT = 末条 finished_at − 首条 started_at（把打回间隙等待计入，系统性偏大），approximate=true → 前端"≈"角标
项目/群维度：P50（同②线性插值规则）+ 均值 + 样本数 N
```

### 4.4 gate_result 埋点写入点（决策 D-2，Q1 回应=加列）

**载体裁决**：t_derivation 加一列（PRD Q1 默认处理采纳）——独立门禁事件表需新表+新写入链路+与派生记录对齐的关联键，过度设计；加列只需"一列 + 一处写入 + 一个回填 ID"。

**写入点**（唯一）：`OrchestrationService.runAsync` 主循环 `engine.derive` 返回后的门禁判定块（F-17），三支汇合调一个私有方法：

```java
// 判定块内（FAIL_WARN 放行 / 打回重做 / 终判超限 / PASS 四分支各自调用）：
markGateResult(result.getDerivationId(), gateResultValue);   // gateResultValue ∈ PASS/FAIL/FAIL_WARN
// parseGateResult 返回 null（LLM 未输出判定）→ 不写，保持 NULL（与 PRD 列值域一致）

private void markGateResult(Long derivationId, String gateResult) {
    if (derivationId == null || gateResult == null) return;
    try {
        derivationService.update(new LambdaUpdateWrapper<Derivation>()
                .eq(Derivation::getId, derivationId)
                .set(Derivation::getGateResult, gateResult));
    } catch (Exception e) {
        // PRD §6.3：埋点失败仅 ERROR 告警，绝不影响编排主流程（打回/重做/终判行为不变）
        log.error("[Orchestration][Gate] gate_result 埋点写入失败 derivationId={}, result={}",
                derivationId, gateResult, e);
    }
}
```

精准 UPDATE 依赖 derivationId：`DerivationResult` 增字段、`DerivationPersistenceService.persist` 末尾回填（§3.6）。**不采用** `UPDATE ... WHERE case_id=? AND role=? ORDER BY id DESC LIMIT 1`——依赖行序且与并发派生有竞态面，回填 ID 一行改动根除。
`executeStep`（断点续跑）不解析判定（F-17 现状语义），其派生记录 gate_result 保持 NULL，RT 计算按无埋点近似分支处理——口径自洽，不做额外改造（断点续跑属人工重试场景，样本占比极小）。

**回填边界（风险 R2，§11）**：升级时刻起的新派生才有埋点；历史行全 NULL → RT 近似口径 + "≈"角标 + 看板"近似样本 X 条"提示。**不做批量回填脚本**（无法从 steps_json 复原中间轮次 FAIL 时间戳，F-22；回填只能造出近似值，与"不冒充精确值"的 PRD 口径冲突）。

## 7. ADR 库与技术雷达

### 7.1 ADR CRUD 与编号

- 创建：五段式必填（context/decision/consequences 空串 400）；adrCode 缺省 `ADR-` + 租户内自增序（uk 兜底 + 重试）；related_principles 可空数组。
- 列表筛选：status（默认 proposed+accepted）/ principleCode（JSON_CONTAINS 或内存过滤）/ keyword（title LIKE）；详情五段式全文 + 关联原则可点击穿透原则管理页（AC-F4.4）。
- 审计：`adr_create/update/delete/transit`（detail 含状态前后值与 superseded_by 链）。

### 7.2 ADR 状态机与原则联动

状态机（AdrStatus）：
```
proposed → accepted                       （评审通过）
accepted → deprecated                     （必填 deprecateReason）
accepted → superseded                     （必填 supersededBy：目标 ADR 须存在、状态=accepted、≠自身）
deprecated / superseded = 终态，无出边    （回 proposed 400，AC-F4.2）
proposed → superseded/deprecated = 非法   （400，AC-F4.2 跳过 accepted 用例）
```

**原则联动（提示而非自动，两处）**：
1. `related_principles` 存在性校验（保存时）：每个 code 须存在于 t_architecture_principle（tenant 内、未删）——不存在的 code 整单 400 并指名（"原则 P99 不存在"）。这是**校验**（阻断），提示是**非阻断**：
2. 状态流转离开 accepted（→deprecated/superseded）且关联原则非空 → transit **成功响应体**携带 `principleSyncHints: [{code, title}]`，前端弹提示条"该 ADR 关联原则 P11，请检查原则内容是否需要同步更新"+ 原则管理直达链接（AC-F4.3）。**系统不自动修改原则内容**（治理变更人责）。
3. 原则侧反查：`GET /api/v1/principles/{id}/adrs` → 该 code 被哪些 ADR 关联（含状态），原则管理/编辑页展示"关联的 ADR 列表"（PrincipleController 改造，§3.6）。

### 7.3 技术雷达

- CRUD：quadrant/ring 四值枚举校验（非法 400，AC-F5.1）；同名唯一冲突→400 提示"编辑既有项"；review_date 必填。

- 待复审：review_date < today−180d → Vo.pendingReview=true（展示层角标，不阻塞任何操作，AC-F5.4）。
- 四象限渲染：**纯 SVG 自包含**（Q6 回应；jQuery 动态拼 `<svg>` 扇区+点+标签，禁外部 CDN/在线图表服务，离线部署约束）+ 列表保底视图（同数据两视图，AC-F5.2）。

## 本次经验沉淀

1. **指标类需求的技术方案要先做"查询形态审计"再谈性能架构**：本次盘点发现 t_governance_log 在租户拦截器 IGNORE_TABLES（SQL 必须手写 tenant_id、不能与业务表随意 JOIN）、steps_json 重跑覆盖时间戳、auto_check 阻断不写步骤 gateResult 三个硬事实——DORA 四指标的每条口径都被迫写成"两段式 IN 查询 + 内存聚合"的确定形态，CFR 分子必须两源合一。若直接上"实时 vs 快照"的架构争论而不做这层审计，会在 Dev 阶段才发现 JOIN 跨拦截器边界的坑。教训：**聚合方案选型前，先把每条指标拆到"表.列.索引.拦截器语义"四要素，性能结论才有事实地基**。
2. **"语义唯一性"要用存储归一化消灭，而不是用应用层预检围堵**：blocks 与 depends_on 同向是语义重复，若原样存两值再靠 Service 预检拦截，会把不变式分散到每个写入路径；归一化为单一 depends_on + orig_type 仅留展示语义后，DB 唯一键直接成为 AC-F3.1 的判定基础，环检测/blocked 判定的谓词也从"两值或"降为"一等值"。教训：**当两个枚举值在全部判定规则上等价、仅文案不同时，归一化存储 + 原值留痕是唯一正确解**。
3. **状态机类需求复用"枚举内嵌流转图"先例的成本极低、收益极高**：CaseStatus 的 canTransitionTo + IllegalStateTransitionException(400) 模式直接复刻到 MilestoneStatus/AdrStatus，三个状态机（含必填项规则如 superseded_by）零新增基础设施，QA 断言口径天然一致（非法流转一律 400）。教训：**新功能设计前先扫一遍代码里已有哪些"模式级资产"（状态机/审计/拦截器/缓存写法），复刻先例的一致性本身就是评审通过的加速器**。
