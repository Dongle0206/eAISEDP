## 1. 项目群总览

### 1.1 M2 阶段目标（一句话）

从 M1 的"手调派生跑通"演进到"**Web 工作台驱动 Case 全生命周期闭环，多租户隔离可用，过程资产结构化透明**"，同时清除 4 条架构技术债（P6 硬编码 / P8 模型内联 / ADR-003 档位激活 / P12 落库容错已落地但检查点未实现）。

**关键路径识别依据**：
- SP-2 必须先行——Web 工作台（SP-1）所有请求需带 JWT，runtime 状态机 API 需经 gateway 路由，auth + gateway 是南北向入口地基（EA 蓝图 §2.6）
- SP-3 必须在 SP-1 之前——Web 工作台要展示/操作 Case 状态，状态机 API 是 UI 的数据源
- SP-1 是闭环终点——它消费 SP-2 + SP-3 的契约，端到端验证 L1 case 跑通

### SP-2 认证授权（auth + gateway）

| 字段 | 内容 |
|---|---|
| **编号** | SP-2 |
| **优先级** | P0 |
| **一句话目标** | 把 auth（仅 Application 骨架）和 gateway（仅 Application 骨架）两个 service 从骨架落地为可用：auth 实现 JWT 签发/校验 + t_user 驱动登录；gateway 实现路由转发 + JWT 校验 + tenant header 透传。|
| **范围边界（做什么）** | **auth**：① `/api/auth/login`（用户名密码校验 t_user，签发 JWT，JWT 含 tenant_id/user_id/roles）② `/api/auth/validate`（校验 JWT 有效性，返回用户信息）③ JWT 工具类（签发/解析/过期校验，HS256，密钥可配）④ 密码 BCrypt 校验（t_user.password 已是 BCrypt，dogfooding admin 用户已插）。**gateway**：① Spring Cloud Gateway 路由配置（按 /api/{module}/** 转发到 runtime/auth，EA 蓝图 §2.6）② 全局 JWT 校验 Filter（白名单 /api/auth/login，其余校验 Authorization header）③ tenant header 透传（从 JWT 解析 tenant_id，塞 X-Tenant-Id header 转发给下游）④ 限流（按 tenant_id，t_quota 驱动，M2 可先简单计数）。|
| **范围边界（不做什么）** | 不做 LDAP/SSO（M3+，EA 蓝图 §2.5）；不做 RBAC 权限管理 UI（M3 admin）；不做 OAuth2 第三方登录；不做密码找回/修改（M2 只登录）。|
| **前置依赖** | 无（M2 地基，最先启动）。|
| **后置被依赖** | **SP-1**（Web 工作台登录需 auth）、**SP-3**（状态机 API 需经 gateway 路由 + 鉴权）、**SP-5**（capability 加载需 tenant edition 上下文）、**SP-7**（配额校验需 gateway 入口统一）。|
| **涉及模块** | `eaiselp-auth`（从骨架到落地）/ `eaiselp-gateway`（从骨架到落地）/ `eaiselp-common`（新增 JWT 工具类，可能放 common/security 包）。|
| **涉及数据表** | 不新增表。读 t_user（登录校验）/ t_tenant（取 edition）。|
| **验收标准（L1 QA）** | 1. POST /api/auth/login 传 admin/正确密码，返回 200 + JWT token；错误密码返回 401。2. 解析返回的 JWT，payload 含 tenant_id=1 / user_id=1 / roles 字段（可用 jwt.io 在线解析验证）。3. 带 JWT 调 /api/auth/validate，返回用户信息；不带 JWT 或伪造 JWT 返回 401。4. gateway 路由：/api/runtime/derive 带 JWT 转发到 runtime；/api/auth/login 不需 JWT。5. gateway 从 JWT 解析 tenant_id，下游 runtime 收到 X-Tenant-Id=1 header（打日志验证）。6. gateway 限流：单 tenant 短时高频请求触发限流响应（429）。|
| **预估工作量** | 24-32 小时（auth 8-12h + gateway 12-16h + JWT 工具 4h）。建议拆 3-4 个 case。|
| **风险** | ① JWT 密钥管理（M2 先硬编码 yml，M3 接 Vault/KMS）—— 缓解：yml 可配 + dogfooding 用占位密钥。② gateway 全局 Filter 与 runtime 现有 TenantContextFilter 的职责重叠（runtime 内 TenantContextFilter 解析 header，gateway 也解析）—— 缓解：gateway 负责鉴权 + 注入 header，runtime 的 Filter 只负责读 header 填 ThreadLocal，二者不重复鉴权。|
| **架构约束** | 受 P11（多租户隔离贯穿，JWT 必须带 tenant_id）、P3（依赖单向，gateway/auth 不反向依赖 runtime）、P13（API 版本化）约束。|

### SP-3 Case 状态机 + 检查点人工锁

| 字段 | 内容 |
|---|---|
| **编号** | SP-3 |
| **优先级** | P0 |
| **一句话目标** | 用 Spring Statemachine 驱动 Case 从 drafting→deriving→reviewing→checkpoint→done 的状态流转，并对不可逆操作（如 case 完成、删除）强制检查点人工确认（reliability-governance 落地）。|
| **范围边界（做什么）** | ① 定义 Case 状态机（States: drafting/deriving/reviewing/checkpoint/done/cancelled；Transitions: 各状态间的合法跳转）② 状态机配置类（Spring Statemachine Config，状态转移守卫 Guard）③ RuntimeController 增状态流转 API（/api/runtime/case/{id}/transition，触发状态机 sendEvent）④ CheckpointService（t_checkpoint CRUD：创建 pending / 确认 confirm / 驳回 reject）⑤ 不可逆操作前插入 pending 检查点（如 case→done 前，必须先 confirm 检查点）⑥ 检查点确认 API（/api/runtime/checkpoint/{id}/confirm）。|
| **范围边界（不做什么）** | 不做状态机可视化（M3 admin）；不做复杂审批流（多级审批 M3+）；不做检查点超时自动处理（M2 人工确认即可）；不做状态回滚（M2 只前进，cancelled 是终态）。|
| **前置依赖** | **SP-2**（状态流转 API 需经 gateway 鉴权，确认人需从 JWT 取 user_id）。|
| **后置被依赖** | **SP-1**（Web 工作台展示状态 + 检查点 UI）、**SP-4**（artifact 关联 case 状态，但配置化解耦后弱依赖）。|
| **涉及模块** | `eaiselp-runtime`（状态机 Config + Controller + CheckpointService）/ `eaiselp-data`（新增 CaseService + CheckpointService 补全 Service 层）/ `eaiselp-common`（可能新增 CaseStatus 枚举）。|
| **涉及数据表** | 不新增表。改 t_case.status（状态机驱动更新）/ t_checkpoint（status pending→confirmed/rejected）。|
| **验收标准（L1 QA）** | 1. 新建 Case，初始 status=drafting（t_case schema 默认值验证）。2. 调 /api/runtime/case/{id}/transition 传合法事件（如 START_DERIVE），status 变 deriving；传非法事件（如 drafting 直接跳 done）被 Guard 拒绝。3. Case 流转到 done 前自动创建 t_checkpoint 一条 pending 记录（operation=case_complete）。4. 检查点未确认时，Case 无法进入 done（状态机 Guard 拦截）；调 /api/runtime/checkpoint/{id}/confirm 后，Case 可流转到 done。5. 检查点确认记录 confirmed_by = JWT 解析的 user_id（验证 SP-2 联动）。6. 状态流转全程在 t_derivation 或审计日志可追溯（哪个角色哪个时刻触发的流转）。|
| **预估工作量** | 28-40 小时（Spring Statemachine 学习曲线 + 状态机 Config + Controller + CheckpointService）。建议拆 4-5 个 case。|
| **风险** | ① Spring Statemachine 首次用，学习曲线（EA 蓝图 §5.3 已标注，tech-radar: Trial）—— 缓解：先跑官方 demo 验证 4.0.0 与 Spring Boot 3.2.5 兼容性，再集成。② 状态机持久化与 t_case.status 同步（Statemachine 内存状态 vs DB 状态）—— 缓解：M2 用 DB 为准，每次流转从 t_case 读当前状态重建 Statemachine 实例（DB-driven，非内存常驻）。③ 检查点与状态机的交互边界（检查点确认是状态机外部动作还是 Guard 内部）—— 缓解：检查点作为 Guard 的前置条件（Guard 查 t_checkpoint 是否 confirmed），不耦合进状态机内部。|
| **架构约束** | 受 P7（状态流转必经 runtime，唯一调度入口）、P12（检查点失败不阻塞已消耗 token 的派生——但检查点本身是前置确认，不是失败容错）、reliability-governance（不可逆操作人工锁）约束。|

### SP-7 配额强校验

| 字段 | 内容 |
|---|---|
| **编号** | SP-7 |
| **优先级** | P2 |
| **一句话目标** | 在 runtime 派生入口（DerivationEngine.derive 前）强校验 t_quota（token/case/派生 配额），超限拒绝并告警，实现 cost-governance 闭环。|

| **后置被依赖** | 无（M2 收尾）。|
| **涉及模块** | `eaiselp-runtime`（DerivationEngine 加拦截 + QuotaService）/ `eaiselp-data`（新增 QuotaService 或扩展现有）。|
| **涉及数据表** | 不新增表。改 t_quota.token_used / case_used / derivation_used（派生时累加）。|
| **验收标准（L1 QA）** | 1. t_quota 初始 token_used=0，派生一次后 token_used += 本次 input+output tokens（验证累加）。2. 手动把 t_quota.token_used 改到接近 token_limit（如 token_limit=1000, token_used=950），再派生（消耗 100 token），抛 QuotaExceededException，返回 429。3. 派生到达 alert_threshold（如 80%）时，日志出现告警（[Quota] tenant=X token 使用达 82%，接近上限）。4. case_used / derivation_used 同理累加（新建 case 时 case_used++，派生时 derivation_used++）。5. 跨租户隔离：tenant A 的配额耗尽不影响 tenant B 派生（P11 验证）。6. | **架构约束** | 受 P11（多租户隔离，配额按 tenant_id）+ cost-governance（配额管控）约束。|

## 本次经验沉淀

1. **依赖关系必须三方交叉验证，不能只看文档**。本次推导依赖图时，同时用了 ADR-001 P3（模块单向依赖）、EA 蓝图 §2.4（依赖图）和 §3.2（数据流）、以及实际代码（DerivationEngine 构造函数注入 adapter/capability/data 三个 Bean）。三方一致才确认依赖关系真实，避免"文档写的依赖"与"代码实际的依赖"脱节。例如 SP-6 放 ModelRoutingService 时，发现文档没说 adapter 能否依赖 data，查 P3 才知 adapter 与 data 同层，需评估，最终决策放 adapter 内部避免依赖。

2. **验收标准要绑定到具体的代码行或表字段，L1 QA 才能用**。本次每个 SP 的验收标准都指向可验证的具体物：SP-4 验收"grep runtime/adapter/data 无 team-* 角色名硬编码"指向 DerivationEngine.java:85-100；SP-6 验收"grep GlmLlmAdapter 无 MODEL_MAPPING 内联"指向第 44-48 行；SP-5 验收"enterprise/pro/starter 三档 listAgents 返回不同 agent 集"指向 CapabilityLoader.listAgents()。教训：抽象的"配置化生效"不可验收，"改 yml 一行重启后 type 变化"才可验收。

3. **接口契约是跨子项目协同的生命线，必须显式编号归属**。本次识别 7 个接口契约（C-1 到 C-7），每个明确归属方和消费方。SP-2 的 JWT 契约（C-1）被 5 个子项目消费，是单点——这就是为什么 SP-2 必须独占 Wave 1。教训：项目群计划不能只列子项目，必须列子项目间的契约，否则并行开发时各写各的、集成时对不上。

4. **fast vs standard 的判据是"需求是否清晰 + 是否涉及安全/新功能"**。本次 SP-4/SP-6 走 fast（解技术债，EA 蓝图已给完整方案），SP-2/SP-3/SP-5 走 standard（安全/核心逻辑/批量改造）。判据不是工作量大小，而是需求的确定性和风险高低。dogfooding 模式下资源有限，把 fast 流程留给确定性高的重构，把 standard 留给需要全流程把关的新功能和安全相关。
