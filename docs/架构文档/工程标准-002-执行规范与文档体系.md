## 1. 角色产出物落盘规范（修复 IMP-004 / 瑕疵 1）

### 1.1 硬约束（强制，不可协商）

**所有 L1 角色的关键产出物必须以物理文件形式 Write 到指定路径，不能只输出在 Agent 回复里。**

> M1.1 真实教训（`M1.1-dogfooding-验证报告.md:106-111`）：Reviewer Agent 把评审报告内容输出在回复里，没有 Write 到 `docs/测试报告/review-M1.0-编译修复.md`，导致 Reviewer 评审结论（0 阻断 / 1 建议项）的物理载体丢失。虽然结论已沉淀到 changelog，但下游角色（QA/Ops）无法以 file:line 方式引用 Reviewer 报告，跨层信息保真度降级（同报告 §5.2 "Reviewer → QA"环节标注 ⚠ 物理文件缺失）。

### 1.2 角色 → 产出物 → 必落盘路径映射表

| 角色 | 产出物 | 必落盘路径（相对项目根） | case 级/工程级 |
|---|---|---|---|
| L1-PO | PRD / 需求文档 | `docs/需求文档/<case-id>-PRD.md` 或 `docs/过程跟踪文档/case-<id>/<case-id>-PRD.md` | case 级 |
| L1-BA | API 契约 / 数据契约 | `docs/需求文档/<case-id>-API契约.md` | case 级 |
| L1-SE | 技术方案 | `docs/设计规划文档/<里程碑>-<主题>-技术方案.md` | case 级（命名按里程碑） |
| L1-Dev | 改动报告（含 `git diff` 摘要） | `docs/过程跟踪文档/case-<id>/dev-report-<里程碑>-<主题>.md` | case 级 |
| **L1-Reviewer** | **评审报告** | **`docs/测试报告/review-<里程碑>-<主题>.md`** | **case 级（G7 强制检查）** |
| **L1-QA** | **测试报告** | **`docs/测试报告/qa-<里程碑>-<主题>.md`** | **case 级（G7 强制检查）** |
| L1-Security | 安全评审报告 | `docs/测试报告/security-<里程碑>-<主题>.md` | case 级 |
| L1-Performance | 性能评测报告 | `docs/测试报告/perf-<里程碑>-<主题>.md` | case 级 |
| L1-Ops | 部署/归档清单 | `docs/过程跟踪文档/case-<id>/ops-checklist-<里程碑>.md` | case 级 |
| L1-PM | changelog / kanban / risks 三件套 | `docs/过程跟踪文档/changelog.md` 等（共享区） | 工程级共享 |
| L3-EA | ADR 架构决策记录 | `docs/架构文档/ADR-<编号>-<标题>.md` | 工程级共享（不可变） |
| L2-Standards | 工程标准 / 质量门禁 | `docs/架构文档/工程标准-<编号>-*.md` + `.ps1` | 工程级共享 |
| L2-PgM / 编排者 | case 验证报告 | `docs/过程跟踪文档/case-<id>/<里程碑>-验证报告.md` 或 `docs/过程跟踪文档/<里程碑>-验证报告.md` | case 级（或共享） |

### 1.3 落盘自检清单（每个角色产出后必须自跑）

每个 L1 角色完成产出后，**在向编排者回复前**必须执行：

1. **Write 落盘**：调用 Write 工具把完整产出物写到 §1.2 指定路径。
2. **自检文件存在**：跑 `Test-Path <绝对路径>` 返回 `True`。
3. **报告路径**：向编排者回复时明确写明"已 Write 到 `<绝对路径>`"，附 `Test-Path` 验证结果。
4. **检查非空**：产出物不能是空文件或仅含标题的占位文件（`Get-Item <path> | Select-Object Length` 应 > 100 字节，否则视为落盘失败）。

> **编排者派生 prompt 时强制加一句**："你的产出物必须 Write 落盘到 `<具体路径>`，不能只输出在回复里。完成后用 `Test-Path` 自检文件存在并向我报告绝对路径。"

### 1.4 反例（来自 M1.1）

```
❌ 错误（M1.1 Reviewer 实际行为）：
   Reviewer 在回复里输出完整评审报告内容（0 阻断 / 1 建议项 / D1 缺陷...），
   但没有调用 Write 工具，导致 docs/测试报告/review-M1.0-编译修复.md 不存在。

✅ 正确（按 ES-002）：
   1. Reviewer 调用 Write 把完整报告写到 docs/测试报告/review-M1.0-编译修复.md
   2. 自检 Test-Path 返回 True，文件大小 > 100 字节
   3. 向编排者回复："评审报告已 Write 到 D:\AI\mywork\platform\docs\测试报告\review-M1.0-编译修复.md（Test-Path=True, 4321 字节）。摘要：0 阻断 / 1 建议项。"
```

## 2. 文档体系与目录归属规范（修复 IMP-005 / 瑕疵 2）

### 2.1 二分总则：工程级共享 vs case 级

```
docs/
├── 架构文档/                     ← 【工程级共享】跨 case 持续维护
│   ├── ADR-001-*.md              （L3 EA 决策，不可变历史）
│   ├── 工程标准-001-*.md         （L2 Standards 标准）
│   ├── 工程标准-002-*.md         （本标准）
│   ├── 质量门禁-*.md / .ps1      （L2 Standards 门禁）
│   └── DESIGN.md（项目根，非本目录，但同性质）
│
├── 设计规划文档/                 ← 【case 级】技术方案（按里程碑命名，归档后保留）
│   └── <里程碑>-<主题>-技术方案.md
│       例：M1.0-编译修复-技术方案.md
│
├── 测试报告/                     ← 【case 级】评审 / 测试 / 安全 / 性能报告
│   ├── review-<里程碑>-<主题>.md  （Reviewer，G7 强制）
│   ├── qa-<里程碑>-<主题>.md       （QA，G7 强制）
│   ├── security-<里程碑>-<主题>.md （Security）
│   └── perf-<里程碑>-<主题>.md     （Performance）
│
├── 过程跟踪文档/                 ← 【工程级共享 + case 级混合】
│   ├── changelog.md              （PM，工程级共享，跨 case 持续追加）
│   ├── kanban.md                 （PM，工程级共享）
│   ├── risks.md                  （PM，工程级共享）
│   ├── <里程碑>-验证报告.md       （编排者/PgM，工程级共享）
│   │   例：M1.1-dogfooding-验证报告.md
│   └── case-<YYYYMMDD>-<简短标题>/  ← 【case 级归档目录】
│       ├── <里程碑>-验证报告.md   （可选：case 内的副本）
│       ├── dev-report-*.md       （Dev 改动报告）
│       ├── ops-checklist-*.md    （Ops 归档清单）
│       └── <case-id>-PRD.md      （PO 需求文档，可选放此）
│
├── 过程执行文档/                 ← 【可选 case 级】执行日志（git log / mvn 输出快照）
│   └── <空时不要预创建占位目录>
│
└── 需求文档/                     ← 【可选 case 级】需求文档（与 PO 产出物路径可二选一）
    └── <空时不要预创建占位目录>
```

### 2.2 判定规则（一个产物放哪？）

| 问 | 答 |
|---|---|
| 这个产物是**跨 case 持续维护**的吗？（changelog / kanban / risks / ADR / 工程标准 / 门禁 / CLAUDE.md / 验证报告） | 放工程级共享区（`docs/过程跟踪文档/` 顶层 或 `docs/架构文档/`） |
| 这个产物是**单 case 归档**的吗？（技术方案 / 评审报告 / 测试报告 / Dev 报告 / Ops 清单） | 放 case 级目录或对应标准目录（`docs/设计规划文档/` / `docs/测试报告/` / `docs/过程跟踪文档/case-<id>/`） |
| 不确定 | **优先放 case 级目录**（归档时再外迁共享区，比反向容易） |

### 2.3 case 目录命名规范

```
case-<YYYYMMDD>-<简短标题（ASCII 或中文均可，建议 ASCII）>
```

| 字段 | 规则 | 示例 |
|---|---|---|
| `YYYYMMDD` | case 启动日期（PM 登记 case 时确定） | `20260721` |
| `<简短标题>` | 用横线分隔的 ASCII 或简短中文 | `M1.0-编译修复` / `ES002-执行瑕疵补全` |

**完整示例**：
- `case-20260721-M1.0-编译修复`（M1.1 Dogfooding case）
- `case-20260722-ES002-执行瑕疵补全`（本次本标准产出 case）

### 2.4 反例（来自 M1.1，`M1.1-dogfooding-验证报告.md:113-118`）

```
❌ 错误（M1.1 实际行为）：
   - 预创建了 docs/过程执行文档/、docs/需求文档/、docs/过程跟踪文档/case-20260721-M1.0-编译修复/ 三个空目录
   - 但实际产物没按"case 目录隔离"放置，而是堆在 docs/过程跟踪文档/ 共享区
   - 结果：3 个空目录占位 + 共享区混入 case 级产物 + case 目录空着

✅ 正确（按 ES-002）：
   1. 不预创建空目录（git 不跟踪空目录，预创建纯属噪音）
   2. PM 登记 case 时只创建 case 目录（docs/过程跟踪文档/case-<id>/）
   3. 各角色按 §1.2 + §2.1 路径落盘，需要时由首个产出角色创建对应子目录
   4. 工程级共享资产（changelog/kanban/risks）直接写在共享区顶层
```

### 2.5 与空目录的关系（明确禁令）

**禁止预创建空占位目录**。git 不跟踪空目录，预创建只产生噪音（IDE 显示空文件夹、`git status` 噪音）。需要时由**第一个产出该类文件的角色**创建目录。

> 这条规则同时解决了 M1.1 `docs/过程执行文档/`、`docs/需求文档/`、`docs/过程跟踪文档/case-20260721-*/` 三个空目录的占位问题。

## 3. Windows 工程标准（修复 IMP-006 / 瑕疵 3）

> M1.1 Dogfooding 在 Windows 10 + PowerShell 5.1 + Git for Windows 环境下暴露 3 类陷阱：`$null` 字面文件残留、commit message 中文 cmd 转码、CRLF 警告污染。本节固化 5 条 Windows 工程规范。

### 3.1 git commit message：用 `-F <文件>` 而非 `-m`

**问题**（`M1.1-dogfooding-验证报告.md:128-130`）：在 cmd 直接传 `git commit -m "中文多行 message"` 会因 cmd 的 ANSI 代码页与 git 期望的 UTF-8 不一致，导致 commit message 中文乱码（`git log` 看到的是乱码）。

**规范**：
- 多行 / 含中文的 commit message **必须**用 `git commit -F <message-file>`，文件 **UTF-8 无 BOM** 编码。
- 文件路径优先 ASCII（如 `D:\AI\mywork\platform\.git\COMMIT_MSG.tmp`）。
- 写文件时用 PowerShell 的 `Set-Content -Encoding utf8NoBOM`（PS 6+）或 `Out-File -Encoding utf8`（PS 5.1 默认带 BOM，需用 .NET `[System.IO.File]::WriteAllText($path, $content, [System.Text.UTF8Encoding]::new($false))` 显式无 BOM）。

**示例**（推荐写法）：
```powershell
$msg = @"
docs(M1.0): 修复编译失败

根因：父 POM pluginManagement 含 repackage executions
修复：删 executions，下沉到各 service 模块 POM
"@
[System.IO.File]::WriteAllText('D:\AI\mywork\platform\.git\COMMIT_MSG.tmp', $msg, [System.Text.UTF8Encoding]::new($false))
git -C 'D:\AI\mywork\platform' commit -F 'D:\AI\mywork\platform\.git\COMMIT_MSG.tmp'
```

**简短纯 ASCII message**（如 `fix(M1.0): compile error`）可以直接用 `-m`，不受此约束。

### 3.2 PowerShell 重定向：`> $null` 必须紧跟无空格

**问题**（`M1.1-dogfooding-验证报告.md:128-130`）：在 cmd 或混合 shell 下执行 `command > $null`（`>` 与 `$null` 之间有空格，或 cmd 上下文），PowerShell 会把 `$null` 当字面字符串，生成一个名为 `$null` 的文件污染工作区。

**规范**：
- **丢弃输出**：用 `2>$null`（错误流丢弃，**紧贴无空格**）或 `| Out-Null`（管道丢弃，更安全）。
- **`> $null`（有空格）禁止使用**。
- **cmd 上下文下**：cmd 不识别 `$null`，必然生成字面文件，禁止在 cmd 用 `> $null`。

**示例**：
```powershell
# ❌ 禁止：会生成字面 $null 文件
Get-Process > $null
cmd /c "dir > $null"

# ✅ 推荐
Get-Process | Out-Null                    # PowerShell 原生方式
Get-Process 2>$null                        # 错误流丢弃（紧贴无空格）
cmd /c "dir > NUL"                         # cmd 上下文用 NUL（不是 $null）
```

### 3.3 CRLF 处理：根目录加 `.gitattributes`

**问题**：Windows 上 git 默认 `core.autocrlf=true`，导致 checkout 时 LF→CRLF、commit 时 CRLF→LF，产生大量 `LF will be replaced by CRLF` 警告噪音，且不同协作者换行符不一致。

**规范**：项目根目录**必须**有 `.gitattributes` 文件，统一换行符策略。

**推荐内容**（最小集）：
```
# 统一所有文本文件用 LF（推荐，跨平台一致）
* text=auto eol=lf

# Windows 专属脚本保留 CRLF（PS 5.1 兼容性更好）
*.ps1   text eol=crlf
*.cmd   text eol=crlf
*.bat   text eol=crlf

# 二进制文件不做换行符处理
*.png   binary
*.jpg   binary
*.jar   binary
*.pdf   binary
```

> **保守版本**（不强制 eol=lf，仅消除警告）：`* text=auto`（让 git 自动判断，不强制转换）。

**部署责任**：`.gitattributes` 文件由 **L1-Dev** 落地创建（不是 team-standards，避免越界）。team-standards 只在本文档定义内容（本节即定义）。

> **G8 检查不覆盖 `.gitattributes`**——`.gitattributes` 是建议项非阻断项，因为没有它项目也能跑，只是有噪音。但 M2 起 Reviewer 验收时应警告"缺 .gitattributes"。

### 3.4 中文路径：优先 ASCII，PowerShell 用 UTF-8 编码读写

**问题**：中文路径在 cmd + `findstr` 下易乱码；PowerShell 5.1 默认 ANSI 读无 BOM 的 .ps1 也会乱码。

**规范**：
- **目录/文件名优先 ASCII**（如 `docs/architecture/` 而非 `docs/架构文档/`）—— 但本平台已有中文目录（`docs/架构文档/` 等），**保持现状不重命名**（重命名代价大于收益），仅新增目录时优先 ASCII。
- **PowerShell 读中文路径**：用 `Get-ChildItem -Path <中文路径>`（PS 原生支持 UTF-16 字符串），**不要用** cmd 的 `findstr` / `dir`（cmd 代码页受限）。
- **PowerShell 输出中文**：`$OutputEncoding = [System.Text.Encoding]::UTF8; [Console]::OutputEncoding = [System.Text.Encoding]::UTF8`（PS 5.1 默认 console 用 ANSI，需显式切 UTF-8 才能正确显示中文）。
- **核对未跟踪文件清单**：用 `git -C <path> ls-files --others --exclude-standard` 而非 `git status`（前者纯路径列表，后者中文路径会转义成 `\xxx` 八进制）。

### 3.5 脚本编码：所有 .ps1 / .sh 一律 ASCII 或 UTF-8 with BOM

**问题**（`质量门禁-模块边界.ps1:9-13` 已记录此教训）：PowerShell 5.1 默认用 ANSI 读无 BOM 的 .ps1，含中文注释的脚本会乱码、解析失败。

**规范**：
- **可执行脚本（.ps1 / .sh / .cmd）一律纯 ASCII**（注释也用英文或拼音，不用中文）—— 这是默认推荐。
- **若必须含中文**：脚本文件**必须 UTF-8 with BOM**（PS 5.1 检测到 BOM 会用 UTF-8 解码，无 BOM 才用 ANSI）。
- **质量门禁脚本**：`质量门禁-模块边界.ps1` 已遵循"纯 ASCII"原则（其 `.NOTES` 段明确记录），所有新门禁脚本（含本标准配套的 `质量门禁-产出物落盘.ps1`）必须延续此原则。

**校验方法**：
```powershell
# 检查 .ps1 是否纯 ASCII
$content = Get-Content -Path 'gate.ps1' -Raw -Encoding Byte
$nonAscii = $content | Where-Object { $_ -gt 127 }
if ($nonAscii) { Write-Host 'NOT pure ASCII' } else { Write-Host 'pure ASCII OK' }
```

## 4. Dev 报告规范（修复 IMP-007 / 瑕疵 4）

### 4.1 硬约束：改动描述必须对照 HEAD / diff

**问题**（`M1.1-dogfooding-验证报告.md:83-88, 164, 187`）：M1.1 中 Dev 报告说"删除 pluginManagement executions"，但实际 HEAD 本无 executions，diff 是"新增 configuration"。这是 Dev 把"目标态描述"误当作"对照基线的改动描述"，导致 Reviewer/QA 验证时按"删 executions"找 diff 找不到，需重新核对磁盘事实。

**规范**：
- Dev 报告每个文件改动**必须**以"对照 HEAD"为基准描述改动方向（新增 / 删除 / 修改），**禁止**以"目标态"为基准描述。
- 描述格式：`<文件路径>:<行号范围> — 对照 HEAD，<新增/删除/修改> <内容摘要>`。
- 多文件改动**逐文件列出**，不要混在一段散文里。

### 4.2 正确写法 vs 错误写法（对照表）

| 场景 | ❌ 错误写法（M1.1 真实偏差） | ✅ 正确写法（按 ES-002） |
|---|---|---|
| 父 POM pluginManagement 段 | "删除 executions 段"（实际 HEAD 本无 executions，diff 是新增 configuration） | "对照 HEAD，pom.xml:122-134 新增 `<configuration><mainClass>...</mainClass></configuration>` 段（pluginManagement 内 spring-boot-maven-plugin 块）" |
| library 模块删 Application 类 | "删掉 Application 类"（笼统） | "对照 HEAD，删除 `eaiselp-capability/src/main/java/.../EaiselpCapabilityApplication.java`（10 行，含 @SpringBootApplication + @EnableScheduling）。注解迁移：@EnableScheduling 迁至 runtime/EaiselpRuntimeApplication.java:12" |
| 新增依赖 | "加上 nacos 依赖"（笼统，看不出加在哪） | "对照 HEAD，eaiselp-runtime/pom.xml:45 新增 `<dependency>spring-cloud-starter-alibaba-nacos-discovery</dependency>`" |
| 修改配置值 | "改成新值"（看不出旧值） | "对照 HEAD，application.yml:23 `server.port: 8080` 改为 `server.port: 8081`" |

### 4.3 反幻觉硬约束（Dev 报告产出前必跑）

Dev Agent 在向编排者回复报告**之前**，**必须**：

1. **跑 `git diff` 核对自己描述的改动方向**：
   ```powershell
   git -C 'D:\AI\mywork\platform' diff --stat         # 改了哪些文件
   git -C 'D:\AI\mywork\platform' diff <file>          # 具体改动
   ```
2. **对照 diff 检查报告**：报告里每条"新增 / 删除 / 修改"声明，必须在 diff 里能找到对应证据（`+` 开头 = 新增，`-` 开头 = 删除）。
3. **行号以 HEAD 为基准**：报告里的行号是改动后的行号（工作区行号），但描述方向时必须明确"对照 HEAD"。
4. **未在 diff 里出现的改动禁止写入报告**（避免幻觉"我改了 X"实际没改）。

### 4.4 Dev 报告模板（强制使用）

```markdown
# Dev 改动报告 — <case-id> / <里程碑>

## 1. 改动总览（对照 HEAD）
- 改动文件数：<N>
- 新增 / 删除 / 修改：<X> 新 / <Y> 删 / <Z> 改
- 自检命令：`git -C 'D:\AI\mywork\platform' diff --stat`

## 2. 逐文件改动（对照 HEAD）

### 2.1 <文件路径>
- 改动类型：新增 / 删除 / 修改
- 行号范围：<起>-<止>（工作区行号）
- diff 摘要（对照 HEAD）：
  - <line>: 新增 `<tag>...</tag>`（diff 里 `+` 开头）
  - <line>: 删除 `<old-tag>...</old-tag>`（diff 里 `-` 开头）

### 2.2 <文件路径>
（同上）

## 3. 反幻觉自检
- [x] 已跑 `git diff --stat`，文件数与报告一致
- [x] 每条改动声明在 diff 里有对应 `+` / `-` 证据
- [x] 未将"目标态描述"误作"改动描述"

## 4. 未做 git commit（按 Dev 边界约束，提交由 Ops 执行）
```

## 附录 A：违反示例与修正（M1.1 真实案例 + 修正方向）

### A.1 IMP-004 — Reviewer 报告未落盘

**M1.1 真实案例**（`M1.1-dogfooding-验证报告.md:106-111, 245`）：
- 现象：`docs/测试报告/review-M1.0-编译修复.md` 不存在（已用 `Test-Path` 验证 False）。
- 根因：Reviewer 角色定义只说"产出评审报告"，没硬性要求 Write 落盘 + 自检文件存在。
- 影响：QA 无法以 file:line 引用 Reviewer 报告，跨层信息保真度降级（Reviewer → QA 环节标注 ⚠）。

**修正方向**（已落地）：
- 本标准 §1 定义"角色产出物落盘规范"。
- 配套门禁 G7（`质量门禁-产出物落盘.ps1`）检查 `docs/测试报告/review-*.md`、`docs/测试报告/qa-*.md`、`docs/设计规划文档/*-技术方案.md` 至少各存在 1 个。
- 编排者派生 Reviewer/QA/SE prompt 时强制加"必须 Write 落盘到 <具体路径>，完成后 Test-Path 自检"。

### A.2 IMP-005 — case 级 vs 工程级目录归属混乱

**M1.1 真实案例**（`M1.1-dogfooding-验证报告.md:113-118`）：
- 现象：`docs/过程执行文档/`、`docs/需求文档/`、`docs/过程跟踪文档/case-20260721-M1.0-编译修复/` 均为空目录（已用 `Get-ChildItem | Measure-Object` 验证 Count=0）。
- 根因：编排者按"标准目录结构"预创建占位目录，但产物实际放在了共享区顶层。
- 影响：3 个空目录占位 + 共享区混入 case 级产物 + case 目录空着。

**修正方向**（已落地）：
- 本标准 §2 定义"文档体系与目录归属规范"，给目录映射表 + 命名规范。
- §2.5 明确"禁止预创建空占位目录"。
- 后续 case 启动时 PM 只创建 case 目录，不预创建空目录。

### A.3 IMP-006 — Windows 环境陷阱

**M1.1 真实案例**（`M1.1-dogfooding-验证报告.md:128-130`）：
- 现象 1：`$null` 字面文件残留工作区（M1.1 已被编排者清理，本次预跑 G8 在 M1.1 现状 PASS）。
- 现象 2：commit message 中文在 cmd 直接传时乱码（M1.1 用 PowerShell 写文件 + `-F` 已规避，`git log` 中文正常显示）。
- 现象 3：CRLF 警告污染（M1.1 根目录无 `.gitattributes`，本次 `Test-Path` 验证 False）。
- 根因：Windows 工程标准缺失。

**修正方向**（已落地）：
- 本标准 §3 定义 Windows 工程 5 条规范（commit message / 重定向 / CRLF / 中文路径 / 脚本编码）。
- 配套门禁 G8（检查 `$null` 字面文件）+ G9（检查 commit message 中文是否正常）。
- §3.3 定义 `.gitattributes` 推荐内容（落地由 L1-Dev 执行，本标准不越界 Write）。

### A.4 IMP-007 — Dev 报告措辞偏差

**M1.1 真实案例**（`M1.1-dogfooding-验证报告.md:83-88, 164, 187`）：
- 现象：Dev 报"删 pluginManagement executions"，实际 HEAD 本无 executions，diff 是新增 configuration。
- 根因：Dev 报告规范允许"语义描述"而非"对照磁盘事实描述"。
- 影响：Reviewer/QA 按"删 executions"找 diff 找不到，需重新核对磁盘事实（M1.1 中 QA 独立验证发现此偏差，未阻断但增加沟通成本）。

**修正方向**（已落地）：
- 本标准 §4 定义 Dev 报告规范，硬约束"改动描述必须对照 HEAD/diff"。
- §4.3 反幻觉硬约束：Dev 报告产出前必跑 `git diff` 核对。
- §4.4 提供 Dev 报告模板。
- 配套门禁 G10（弱语义检查：Dev 报告若含改动方向描述，须以"对照 HEAD"开头）。
