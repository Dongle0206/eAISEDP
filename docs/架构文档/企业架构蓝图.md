## 1. 业务架构（Platform for What）

> 业务架构层回答：平台承载什么业务价值？切成哪些能力域？每个能力域归谁？谁会用？

### 1.1 平台承载的核心业务价值

**一句话定位**：eAISEDP 是**承载一套 AI 多 Agent 软件工程体系（L3 战略→L2 项目群→L1 实施）端到端运作的运行时平台**，平台是"载体"不是"主角"。

给企业带来的转型价值（按企业当前痛点映射）：

| 企业痛点 | 平台解法 | 转型价值 |
|---|---|---|
| AI 应用散落在各团队，能力无法复用 | 体系 markdown 驱动，22 角色/26 skills/4 commands 全平台共享 | **能力资产化**——一次定义，全企业复用 |
| 软件工程过程不透明，PRD/方案/测试报告散落 git/邮件 | 过程资产入平台数据，全链路追溯（case→derivation→artifact）| **过程透明化**——管理者看得到每一步 |
| AI 协作无治理，模型成本/质量/合规失控 | 内置 model-registry 档位 + cost-governance + reliability-governance + GRC | **治理闭环**——商用敢用，不是演示能跑 |
| 企业已有 GitLab/Jira/Confluence/CI，换不掉 | 适配器 SPI，企业工具零改动接入 | **资产保留**——适配代价最低，不要求企业换工具 |
| 体系演进要改代码 | 体系配置独立仓库，30 秒热加载 | **体系独立演进**——平台代码不随体系变 |

### 1.2 核心业务能力域划分（7 域）

按"高内聚低耦合 + 可独立交付"划分 7 个业务能力域。每个能力域对应一个或多个平台模块，是 L2 拆项目群的天然边界。

```
┌─────────────────────────────────────────────────────────────────┐
│                    eAISEDP 平台业务能力域                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ① 能力注册域      ② 派生调度域      ③ Case 生命周期域          │
│  (capability)      (runtime)         (data + runtime)            │
│                                                                  │
│  ④ 多租户与配额域  ⑤ 过程资产域      ⑥ 协同治理域               │
│  (common+auth+     (data +           (admin + observability      │
│   data.quota)       adapter.docstore)  + 治理类 skills)          │
│                                                                  │
│  ⑦ 适配集成域                                                     │
│  (adapter SPI)                                                   │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

| 能力域 | 职责定义 | 当前模块归属 | M1 状态 | 核心交付 |
|---|---|---|---|---|
| ① **能力注册域** | 从体系 markdown 加载 agent/skill/command 定义，热更新，版本化 | eaiselp-capability | 已落地（22 agent + 26 skill + 4 cmd 可加载） | CapabilityLoader 30s 热更新 + MarkdownParser + 6 个 REST 端点 |
| ② **派生调度域** | 平台唯一调度入口，7 步标准动作（校验→选模型→装配→调LLM→提取→入库→埋点）| eaiselp-runtime | 已落地（DerivationEngine 端到端验证） | DerivationEngine + ContextAssembler + DerivationPersistenceService |
| ③ **Case 生命周期域** | Case 从起草→派生→评审→检查点→完成的全状态机管理 | eaiselp-data + eaiselp-runtime | 部分（t_case/t_derivation/t_checkpoint 已建，状态机未实现）| Case 状态机（Spring Statemachine）+ Checkpoint 人工锁 |
| ④ **多租户与配额域** | 租户隔离（tenant_id 自动注入）+ 配额管控（token/case/派生/存储）| eaiselp-common + eaiselp-auth + eaiselp-data | 已落地（TenantContext + t_quota），认证未落地 | TenantContextFilter + EaiselpTenantHandler + t_quota 埋点 |
| ⑤ **过程资产域** | PRD/方案/评审/测试报告等过程产物结构化存储与检索 | eaiselp-data + eaiselp-adapter.docstore | 部分（t_artifact 已建，结构化与检索未实现）| Artifact 结构化 + DocStoreAdapter 对接 |
| ⑥ **协同治理域** | 项目群协同 + GRC 合规 + 监控指标 + 治理类 skills 落地 | eaiselp-admin + eaiselp-observability + 治理 skills | 骨架（admin/observability 仅 Application 类）| 项目群协同 + 可观测 + GRC 审计链 |
| ⑦ **适配集成域** | 外部对接走 SPI，企业已有 Git/LLM/DocStore/Ticket/CICD/IM/MCP 零侵入接入 | eaiselp-adapter | 已落地（Git/LLM/DocStore 三大 SPI + 默认实现，GLM 接通）| 7 大适配器 SPI + 默认实现 + 企业实现注册 |

### 1.3 业务能力与体系角色的映射

这是"平台模块 ↔ 体系角色"的对接表。平台承载体系角色运作，每个能力域归口特定的 team-* 角色主理（L1 实施角色）或对应治理角色协同。

| 能力域 | 主理角色（L1）| 协同/治理角色 | 角色在能力域中做什么 |
|---|---|---|---|
| ① 能力注册域 | — | team-standards（写工程标准）| 平台侧无 L1 角色主理；体系角色定义在 markdown，由 capability 模块加载。Standards 治理 markdown 规范 |
| ② 派生调度域 | team-orchestrator | team-ea（架构原则 P2 唯一调度入口）| 编排者是唯一调用 DerivationEngine 的角色；EA 定义"唯一调度入口"铁律 |
| ③ Case 生命周期域 | team-orchestrator + team-pm | team-pgm（项目群）| 编排者驱动 case 状态流转，PM 跟踪，PgM 跨项目协调 |
| ④ 多租户与配额域 | — | team-grc（合规）+ EA（隔离原则）| 平台基础设施能力，GRC 审计租户隔离有效性 |
| ⑤ 过程资产域 | team-po/ba/se/dev/reviewer/qa/ops（产出方）| team-steward（数据治理）| 14 个 L1 角色产出过程资产入平台；Steward 治理资产标准化/质量 |
| ⑥ 协同治理域 | team-pgm/vsm | team-grc + team-ea + team-strategy | L2 治理角色主理协同治理；EA/GRC/Strategy 提供约束 |
| ⑦ 适配集成域 | team-dev（实现适配器）| team-ea（SPI 架构）| Dev 实现企业适配器，EA 定义 SPI 接口规范 |

**关键洞察**：平台模块不"拥有"角色，平台只**承载**角色运作。22 角色/26 skills/4 commands 全部从 markdown 加载，平台代码零角色硬编码（铁律 1）。**但当前 `DerivationEngine.guessType()` 第 86-99 行硬编码了 team-po/team-ux 等角色名做 artifact 类型推断，违反铁律 1，列为 M2 重构项（见 §7 P6）。**

### 1.4 目标用户画像（三档分场景）

平台按企业规模分三档激活体系层级（ADR-003 详述）：

```
大型企业 (L3→L2→L1)          中小型企业 (L2→L1)          小团队 (L1)
┌──────────────────┐         ┌──────────────────┐         ┌──────────────────┐
│ 战略规划层激活     │         │                  │         │                  │
│ - EA 出架构蓝图   │         │   跳过 L3        │         │   跳过 L3/L2     │
│ - GRC 治理合规    │         │                  │         │                  │
│ - Strategy 投资   │         │                  │         │                  │
├──────────────────┤         ├──────────────────┤         ├──────────────────┤
│ 项目群协同层激活   │         │ 项目群协同层激活   │         │                  │
│ - PgM 拆项目群    │         │ - PgM 拆项目群    │         │   直接单项目      │
│ - Standards 标准  │         │ - Standards 标准  │         │ - 编排者直接跑    │
│ - VSM 效能度量    │         │ - VSM 效能度量    │         │ - 14 角色流水线   │
│ - Steward 数据    │         │ - Steward 数据    │         │                  │
├──────────────────┤         ├──────────────────┤         ├──────────────────┤
│ 单项目实施层（恒激活）        │ 单项目实施层（恒激活）        │ 单项目实施层（恒激活）        │
│ 14 角色 case 流水线          │ 14 角色 case 流水线          │ 14 角色 case 流水线          │
└──────────────────┘         └──────────────────┘         └──────────────────┘
   私有部署 + 全适配器            私有/SaaS + 按需适配器         SaaS + 默认适配器
```

| 用户档 | 规模 | 激活层级 | 部署方式 | 适配器策略 | 典型场景 |
|---|---|---|---|---|---|
| **大型企业** | 1000+ 人，多事业部 | L3 + L2 + L1 | 私有部署 | 全适配器接企业资产（GitLab/Jira/Confluence/Jenkins/钉钉）| 集团级 AI 软件工程平台，跨事业部协同 |
| **中小型企业** | 100-1000 人 | L2 + L1 | 私有或 SaaS | 按需适配器（Git+Jira 常接，DocStore/CICD 可选）| 单一公司多项目并行，需项目群协同但无战略层 |
| **小团队** | <100 人 | L1 | SaaS（共享租户）| 默认适配器（本地 Git + GLM + MinIO）| 单项目快速跑通 AI 协作，无治理开销 |

**架构含义**：平台必须支持"层级按需激活"——`t_case.layer` 字段（已有，L1/L2/L3）+ `t_tenant.edition` 字段（已有，pro/enterprise）是激活机制的载体。激活哪层就加载哪层的 agent/skill（capability 模块按 tenant edition 过滤加载）。

## 2. 应用架构（How Services Split）

> 应用架构层回答：目标态服务怎么拆？现有 9 模块怎么演进？服务间怎么依赖？网关怎么路由？

### 2.1 现状盘点（9 模块 M1 实际形态）

基于 ADR-001 §5.1 裁决，M1 为**模块化单体**：1 个 host 进程（runtime）+ 若干 library + 若干 service 骨架。

| 模块 | 当前定性 | 启动？ | 实际承载 | 代码实证 |
|---|---|---|---|---|
| eaiselp-common | library | 否 | BaseEntity/R/TenantContext/BizException/MetaObjectHandler/TenantHandler | 9 个类 |
| eaiselp-data | library | 否 | 8 实体 + 8 Mapper + 2 Service（Artifact/Derivation）+ MybatisPlusConfig | 18 个类 |
| eaiselp-capability | library | 否 | AgentDefinition/SkillDefinition/CommandDefinition + MarkdownParser + CapabilityLoader + CapabilityController | 6 个类 |
| eaiselp-adapter | library | 否 | Adapter/AdapterFactory/GitAdapter/LlmAdapter/DocStoreAdapter SPI + 3 默认实现 + AdapterController | 10 个类 |
| eaiselp-runtime | **service（host）**| **是** | DerivationEngine + ContextAssembler + DerivationPersistenceService + RuntimeController | 4 个类 + 2 测试 |
| eaiselp-gateway | service | 是（骨架）| 仅 Application 类 | 1 个类 |
| eaiselp-auth | service | 是（骨架）| 仅 Application 类 | 1 个类 |
| eaiselp-observability | service | 是（骨架）| 仅 Application 类 | 1 个类 |
| eaiselp-admin | service | 是（骨架）| 仅 Application 类 | 1 个类 |

**M1 唯一启动进程是 runtime**，capability/adapter/data 的端点（`/api/capability/**`、`/api/adapter/**`）由 runtime 通过 `scanBasePackages` 接管合并暴露。

### 2.2 目标态微服务拆分（M3+ 触发）

**关键约束（ADR-001 §5.3）**：不在 M1/M2 强拆微服务，避免 premature distribution。当且仅当以下条件触发，才启动 library→service 外移评估：
- capability 的 markdown 热更新需独立扩容
- adapter 需支持多供应商并行/灰度
- data 的数据量/并发触发独立分库
- 团队按模块分拆（Conway's Law）

目标态（M3+）服务拓扑：

```

                                     │

┌──────────────┐ ┌───────────┐ ┌──────────┐ ┌───────────┐ ┌──────────────┐
```

### 2.3 每个服务的职责边界（一句话定义）

| 服务 | 一句话职责边界 | 不做什么（反向约束）|
|---|---|---|
| **eaiselp-runtime**（核心）| 平台唯一调度入口，执行派生 7 步标准动作，驱动 case 状态机 | 不直接调 LLM/Git/DocStore（走 adapter）；不直接读写 markdown（走 capability）|
| **eaiselp-capability** | 从体系仓库加载 agent/skill/command，30s 热更新，版本化 | 不执行派生（只提供定义）；不持久化业务数据 |
| **eaiselp-data** | case/derivation/artifact/milestone/checkpoint 的 CRUD + 检索 | 不含业务逻辑（纯数据服务）；不调外部系统 |
| **eaiselp-adapter** | 7 大适配器 SPI 的实现注册与路由，外部系统对接的唯一出口 | 不含业务规则（只做协议转换）；不持久化（除适配器配置）|
| **eaiselp-auth** | 多租户用户/角色/权限，可接 LDAP/SSO | 不做业务鉴权（只做身份认证 + RBAC）|
| **eaiselp-gateway** | 南北向流量入口，路由/鉴权/限流/熔断 | 不含业务逻辑；不做东西向路由（服务间直连或经注册中心）|
| **eaiselp-observability** | 指标采集/聚合/导出（Prometheus），体系自身健康度 | 不做告警决策（只采集和暴露）；不做日志（Loki 独立）|
| **eaiselp-admin** | 管理后台，体系管理/适配器配置/治理配置/租户管理 | 不执行业务流程（只做配置管理）|
| **eaiselp-common** | 公共 DTO/工具/异常/多租户上下文/常量 | **永远不拆服务**（ADR-001 P1 隐含：common 是纯库，被所有服务依赖）|

### 2.4 服务间依赖关系（单向无环）

ADR-001 P3 约束：依赖单向无环。当前（M1 模块化单体）与目标态（M3 微服务）的依赖图一致，只是调用方式从 bean 注入改为 Feign。

```
                    gateway
                       │
                       ▼
        ┌────────── auth ──────────┐
        │              │            │
        ▼              ▼            ▼
     runtime ─────► capability    admin
        │
        ├──► adapter ──► (外部系统: Git/LLM/DocStore/...)
        │
        └──► data ──► (MySQL)
        
        所有模块 ──► common (公共库，被所有人依赖，不依赖任何人)
        
        observability (旁路，被所有服务埋点，不依赖业务服务)
```

**依赖铁律**：
- `common` 是依赖链最底层，不依赖任何业务模块
- `runtime` 是业务中枢，依赖 capability/adapter/data
- `adapter` 不依赖 runtime（反向禁止）—— ADR-001 P3
- `data` 不依赖 runtime（反向禁止）—— ADR-001 P3
- `observability` 是旁路，被埋点不主动依赖业务

### 2.5 M1→M2→M3 演进路径（library 何时外移为 service）

| 模块 | M1（当前）| M2 | M3+ |
|---|---|---|---|
| common | library | library | library（永不拆）|
| data | library | library（加 Service 层补全）| service（数据量触发分库时）|
| capability | library | library（加版本管理）| service（热更新需独立扩容时）|
| adapter | library | library（加 4 个新 SPI：Ticket/CICD/IM/MCP）| service（多供应商灰度时）|
| runtime | service（host，承载所有）| service（host，但 data 持久化下沉）| service（独立，Feign 调 capability/adapter/data）|
| gateway | service 骨架 | service（路由 + 鉴权落地）| service |
| auth | service 骨架 | service（JWT + RBAC 落地）| service（LDAP/SSO）|
| observability | service 骨架 | service（埋点 + Prometheus 导出）| service |
| admin | service 骨架 | service（管理后台落地）| service |

**演进触发条件**（每条都需新写 ADR 替代 ADR-001 相关条款，ADR-001 §5.3 已预留）：
- **data 外移**：单表 > 1000 万行，或并发 > 1000 QPS
- **capability 外移**：体系仓库 > 100 角色，热更新 GC 压力明显
- **adapter 外移**：需同时接 > 3 个 LLM 供应商做灰度

### 2.6 API 网关路由规划

gateway（M2 落地）按 `/api/{module}/**` 前缀路由，与 library 模块的 Controller 前缀对齐（ADR-001 §5.2.4 已保留）：

| 路由前缀 | 目标服务 | 当前承载 | 鉴权要求 |
|---|---|---|---|
| `/api/runtime/**` | runtime | derive / 状态机 / 检查点 | 需登录 + 租户隔离 |
| `/api/capability/**` | runtime（M1）→ capability（M3）| agent/skill/command 列表与详情 | 需登录 |
| `/api/adapter/**` | runtime（M1）→ adapter（M3）| adapter status / 切换 | 需管理员 |
| `/api/data/**` | runtime（M1）→ data（M3）| case/artifact/derivation CRUD | 需登录 + 租户隔离 |
| `/api/auth/**` | auth | login / token / RBAC | 公开（login）/ 需 token（其余）|
| `/api/admin/**` | admin | 体系管理 / 适配器配置 / 租户管理 | 需租户管理员 |
| `/api/observability/**` | observability | 指标查询 | 需管理员 |
| `/actuator/**` | 各服务 | Prometheus 抓取 | 内网（不经 gateway）|

**网关横切关注点**：鉴权（JWT 校验，转发 X-Tenant-Id / X-User-Id header）→ 限流（按 tenant_id 配额，t_quota 驱动）→ 熔断（Sentinel，按服务）→ 路由。

### 3.5 多租户数据隔离方案（演进）

**演进路径**：

### 4.2 适配器 SPI 架构（保留企业已有资产的关键）

**SPI 设计（已落地 3 个，M3 扩展到 7 个）**：

```java
// 已落地（eaiselp-adapter/spi/）
public interface Adapter {           // 顶层 SPI
    String getType();                // git/llm/docstore/ticket/cicd/im/mcp
    String getProvider();            // default/gitlab/gitea/glm/openai/...
    boolean isAvailable();
}
public interface GitAdapter extends Adapter { ... }       // 默认:LocalGit  企业:GitLab/Gitea
public interface LlmAdapter extends Adapter { ... }       // 默认:GLM       企业:多供应商路由
public interface DocStoreAdapter extends Adapter { ... }  // 默认:MinIO     企业:Confluence/SharePoint

// M3 新增（待实现）
public interface TicketAdapter extends Adapter { ... }    // 默认:内置工单  企业:Jira/Plane
public interface CiCdAdapter extends Adapter { ... }      // 默认:无        企业:Jenkins/GitLabCI
public interface ImAdapter extends Adapter { ... }        // 默认:无        企业:钉钉/企微
public interface McpAdapter extends Adapter { ... }       // 默认:无        企业:MCP 工具集
```

**配置驱动切换**（application.yml，零代码侵入）：

```yaml
adapter:
  git:
    provider: default       # default / gitlab / gitea
  llm:
    provider: glm           # glm / openai / azure
  docstore:
    provider: default       # default(MinIO) / confluence
  ticket:
    provider: none          # M3 启用
```

**企业已有资产适配映射**：

| 企业已有资产 | 对应适配器 SPI | 默认实现替代关系 |
|---|---|---|
| GitLab / Gitea / GitHub Enterprise | GitAdapter | LocalGit → GitLab/Gitea |
| OpenAI / Azure OpenAI / 文心 / 通义 | LlmAdapter | GLM → 多供应商 |
| Confluence / SharePoint / 语雀 | DocStoreAdapter | MinIO → Confluence |
| Jira / Plane / 禅道 / 飞书项目 | TicketAdapter | 内置工单 → Jira（M3）|
| Jenkins / GitLab CI / ArgoCD | CiCdAdapter | 无 → Jenkins（M3-M4）|

### 4.3 LLM 集成架构（model-registry 档位→模型映射）

**M1 现状（已落地 GLM）**：
- `GlmLlmAdapter` 手写 RestClient 调智谱 v4 API（放弃 LangChain4j SDK，因版本冲突）
- `MODEL_MAPPING` 内联档位→模型映射（opus→glm-4-plus, sonnet→glm-4, haiku→glm-4-flash）
- yml 预留 `eaiselp.adapter.llm.model-mapping` 段，M1.x 启用 @ConfigurationProperties 覆盖

**M2 目标（model-registry skill 落地）**：
- 档位→模型映射**从代码内联迁移到配置表** `t_model_routing`（解决 P8：模型换代不改代码）
- 角色定义写能力档位（reasoning/structured/mechanical），路由表映射到具体模型
- 模型换代只改路由表，不动 22 个角色定义

```
角色 markdown 定义          t_model_routing（M2）         具体模型
agent.model: sonnet    ──►  tier=sonnet → glm-4       ──►  GLM API
                           tier=opus   → glm-4-plus   ──►  GLM API
                           tier=haiku  → glm-4-flash  ──►  GLM API
                           
角色 markdown 不写具体模型，写档位；路由表是档位与模型的解耦层
```

**多供应商路由（M3+）**：
- adapter 支持多 LlmAdapter 并存（按 tenant 配置不同供应商）
- 灰度：按 tenant_id/role 路由到不同供应商（成本/质量权衡）

### 4.4 热加载机制（CapabilityLoader 30 秒热更新）

**M1 现状（已落地）**：
- `CapabilityLoader` `@Scheduled(fixedDelay=30000)` 每 30s 检查体系仓库文件指纹（mtime 求和）
- 指纹变化触发 `load()`，重新解析所有 markdown，原子替换 ConcurrentHashMap
- 体系仓库路径 `eaiselp.system.path` 可配（默认 `./eAISEDP-system`，submodule）

**热加载价值**：体系（agent/skill/command）独立演进，平台不重启。新增一个角色只需在体系仓库加一个 markdown，30 秒后平台可用（铁律 1 落地的工程保证）。

**M2 演进**：
- 加载性能优化（>100 角色时增量加载，非全量）
- 版本管理（system_version 字段记录加载的体系版本，便于追溯）

### 4.5 可观测性架构（M2-M3 落地）

### 6.5 SaaS vs 私有部署的数据隔离差异

| 维度 | SaaS（共享租户）| 私有部署（独立租户/独立库）|
|---|---|---|
| 部署模式 | deploy_mode=shared | deploy_mode=private |
| 数据库 | 共享 MySQL，tenant_id 列隔离 | 独立 MySQL（每客户一套）|
| 适配器 | 默认适配器（Git/GLM/MinIO）| 企业适配器（客户自选）|

**混合模式**：大型企业可能"核心数据私有部署 + 非敏感能力用 SaaS"——通过 adapter 配置混合，平台支持。

## 7. 架构原则（Constraints for L2/L1）

> 本节是 L2 team-standards 翻译为工程标准的输入。P1-P5 来自 ADR-001（前置约束），P6-P14 为本蓝图新增。每条原则含：编号/一句话/理由/违反后果/示例。

### 前置原则（来自 ADR-001，已接受，本蓝图引用）

#### P1 库与服务的二选一
- **一句话**：一个 Maven 模块在同一次构建产物里，要么是 library，要么是 service，不可兼得。
- **理由**：repackage 不可逆改变 jar 内部布局（BOOT-INF/classes），库与服务对构建产物的诉求互斥。
- **违反后果**：编译失败（M1.0 已验证）/ fat jar 无法被依赖。
- **示例**：capability 不能既有 @SpringBootApplication 又被 runtime 当 Maven 库依赖。

#### P2 库不能 repackage
- **一句话**：library 模块禁止配 spring-boot-maven-plugin 的 repackage execution。
- **理由**：repackage 重定位 class 到 BOOT-INF/classes/，破坏 jar 作为 classpath 库的可用性。
- **违反后果**：依赖该库的模块编译期找不到符号（M1.0 BUG-001 根因）。
- **示例**：eaiselp-data 的 POM 不得出现 spring-boot-maven-plugin。

#### P3 依赖方向单向无环
- **一句话**：runtime → capability/adapter/data → common，单向依赖，禁止反向。
- **理由**：防止依赖环导致构建/启动失败，保持架构层次清晰。
- **违反后果**：循环依赖编译失败 / 架构层次混乱。
- **示例**：capability 不能 import runtime 的类。

#### P4 repackage 配置下沉到 service 模块
- **一句话**：repackage execution 只允许出现在 service 模块 POM 的 `<plugins>` 段，不允许放在父 POM pluginManagement。
- **理由**：pluginManagement 是默认配方，含 executions 会全局波及所有子模块。
- **违反后果**：所有子模块被 repackage（M1.0 BUG-001）。
- **示例**：父 POM pluginManagement 只放 configuration，executions 下沉到 runtime/gateway/auth。

#### P5 模块化单体的演进预留
- **一句话**：当前 library 形态的模块，保留包结构/Bean 命名/Controller 边界，未来外移为服务只需"加 Application + Feign"。
- **理由**：今天模块化单体，明天可无痛拆服务，但不今天承担拆服务的成本。
- **违反后果**：未来拆服务需大改业务代码 / 演进受阻。
- **示例**：capability 的 Controller 保留 @RestController + /api/capability/** 前缀。

### 本蓝图新增原则（P6-P14）

#### P6 平台零角色硬编码（铁律 1 的工程落地）
- **一句话**：平台代码不得出现任何 team-* 角色名、skill 名、流程阶段名的硬编码；所有这类映射必须配置化（yml/表）或从 markdown 加载。
- **理由**：平台是"载体"不是"主角"。角色/skill/阶段是体系资产，独立演进，平台代码硬编码它们会导致体系变更必须改平台代码，违背"承载不重写"。
- **违反后果**：新增角色要改平台代码（违背铁律 1）/ 平台与体系强耦合 / 商用客户自定义角色无法支持。
- **示例**：**当前 `DerivationEngine.guessType()` 第 86-99 行硬编码 team-po/team-ux 等做 artifact 类型推断，违反本原则。M2 必须重构为 yml 配置 `eaiselp.artifact.type-mapping`（见 §3.3）。**

#### P7 唯一调度入口（铁律 2 的工程落地）
- **一句话**：所有角色派生必经 DerivationEngine，不得绕过直接调 LLM/Git/DocStore。
- **理由**：统一入口才能统一埋点（token/cost/duration）、统一持久化（derivation/artifact）、统一治理（配额/检查点）。
- **违反后果**：派生不可追溯 / 成本不可控 / 治理失效。
- **示例**：任何角色要调 LLM，必须通过 DerivationEngine → AdapterFactory.getLlmAdapter()，不得直接 new GlmLlmAdapter()。

#### P8 模型档位与具体模型解耦（model-registry 落地）
- **一句话**：角色 markdown 写能力档位（opus/sonnet/haiku 或 reasoning/structured/mechanical），不得写具体模型名；档位→模型映射走配置表 t_model_routing。
- **理由**：模型换代频繁（GLM-4→GLM-5），硬编码模型名导致换模型要改 22 个角色定义。档位是抽象层，路由表是解耦层。
- **违反后果**：模型换代要改所有角色定义 / 多供应商无法路由 / 成本优化受阻。
- **示例**：**当前 `GlmLlmAdapter.MODEL_MAPPING` 内联档位→模型映射（第 44-48 行），违反本原则。M2 必须迁移到 t_model_routing 配置表。**

#### P9 适配器 SPI 零侵入（铁律 4 的工程落地）
- **一句话**：所有外部系统对接（Git/LLM/DocStore/Ticket/CICD/IM/MCP）必须走适配器 SPI，企业实现按需启用，配置驱动切换。
- **理由**：企业已有资产保留，适配代价最低。切换适配器只改配置，平台核心代码零改动。
- **违反后果**：企业接入要改平台核心代码 / 适配代价高 / 销售阻力大。
- **示例**：企业接 GitLab，配 `adapter.git.provider=gitlab` + 实现 GitlabGitAdapter，runtime 代码零改动。

#### P10 过程资产入平台（铁律 5 的数据落地）
- **一句话**：所有 L1 角色的产出（PRD/方案/评审/测试报告/代码等）必须结构化入平台数据（t_artifact），不只入 git。
- **理由**：过程透明化是平台核心价值（§1.1）。只入 git 无法检索/追溯/治理；入平台数据才能全链路透明。
- **违反后果**：过程不透明 / 无法检索 / 治理失效 / 商用卖点丧失。
- **示例**：DerivationEngine 派生后，LLM 输出必须 extractArtifacts + persist 到 t_artifact，不得只返回给调用方不入库。

#### P11 多租户隔离贯穿（铁律 3 的工程落地）
- **一句话**：所有业务表带 tenant_id，所有查询自动注入 tenant_id 过滤（MyBatis-Plus 拦截器），禁止手写不带 tenant_id 的 SQL。
- **理由**：商业化多租户的数据隔离是合规底线。泄露租户数据是商用致命风险。
- **违反后果**：跨租户数据泄露 / 合规违规 / 商用信誉崩塌。
- **示例**：禁止 `SELECT * FROM t_case`（必须带 tenant_id）；用 MyBatis-Plus 的 LambdaQueryWrapper 自动注入。

#### P12 落库失败不阻塞主流程
- **一句话**：高价值派生结果已构建后，落库失败只 log 不重抛，不得让 DB 抖动拖垮主流程。
- **理由**：LLM 调用成本高（token 已消耗），派生结果必须返回给调用方；DB 抖动是临时故障，可异步补偿。
- **违反后果**：DB 抖动导致已消耗 token 的派生结果丢失 / 用户体验差。
- **示例**：**DerivationEngine 第 61-66 行已实现（M1.2 决策，try-catch Throwable 只 log）。本原则固化此决策。**

#### P13 接口版本化与文档化
- **一句话**：对外 REST API 必须版本化（/api/v1/）+ 文档化（OpenAPI/Swagger）；适配器 SPI 变更必须有兼容策略。
- **理由**：商用产品 API 是契约，破坏性变更会让客户集成失效。版本化让演进可控。
- **违反后果**：API 破坏性变更导致客户集成断裂 / 适配器 SPI 变更导致企业实现失效。
- **示例**：当前 /api/runtime/derive 是 M1 简化版，M2 应规划 /api/v1/runtime/derive 并保留旧路径兼容期。

#### P14 分场景层级按需激活
- **一句话**：平台按 tenant edition（pro/enterprise）和 case layer（L1/L2/L3）按需激活体系层级，不得强制全层级加载。
- **理由**：小团队用全层级是过度复杂，大型企业不用 L3 是能力缺失。按需激活是商用分档的基础。
- **违反后果**：小团队门槛过高 / 大型企业能力不足 / 资源浪费。
- **示例**：capability 模块按 tenant edition 过滤加载 agent（enterprise 加载 L3 EA/GRC/Strategy，pro 只加载 L2/L1）。

## 8. 架构决策记录（ADR-002 / ADR-003）

> ADR-001 已存在（模块边界与 repackage）。本蓝图产出 ADR-002、ADR-003 两条新决策。完整 ADR 正文将另文件落盘到 `docs/架构文档/`，本节为摘要。

### ADR-002：过程资产入平台的分阶段策略（markdown→MySQL→企业对接）

| 字段 | 值 |
|---|---|
| 编号 | ADR-002 |
| 标题 | 过程资产（PRD/方案/评审/测试报告）入平台数据的分阶段演进策略 |
| 日期 | 2026-07-23 |
| 状态 | 提议（Proposed）—— 待 team-pgm/team-standards 评审后接受 |
| 决策者 | team-ea（L3）|
| 影响范围 | eaiselp-data / eaiselp-runtime / eaiselp-adapter.docstore |
| 下游传导 | L2-Standards（定义 artifact 结构化标准）→ L1-Dev（实现 Service 层）|

**背景**：平台核心价值之一是"过程透明化"（§1.1）。但过程资产（PRD/方案/评审/测试报告）当前散落 git/邮件，无法检索/追溯/治理。需定义入平台数据的演进策略，同时兼顾"M1 跑通"与"M3 对接企业系统"。

**决策**：三阶段演进，不一步到位。
- **M1（当前，已落地）**：LLM 输出整段存为 1 个 t_artifact，type 由 guessType 推断，正文存 content 字段。
- **M2**：结构化 frontmatter（version/review_status/approver/tags）+ 正文分离；type-mapping 配置化（解决 P6）；新增 t_program/t_subproject 承载项目群资产。
- **M3**：对接企业 DocStore（Confluence/SharePoint），平台存索引 + 元数据（t_artifact），正文存企业系统（doc_key 指向企业文档 ID）。

**备选方案（未选）**：
- 一步到位 M3 方案（直接对接企业 DocStore）：M1 阶段无企业客户，过度工程化，否决。
- 只入 git 不入平台数据：违背"过程透明化"核心价值，否决。

**后果**：
- 正向：分阶段降低风险，M1 已验证可行性，M2/M3 增量演进。
- 负向：M1→M2→M3 需数据迁移（frontmatter 结构化时，旧 artifact 需补全）。
- 约束：Steward M2 必须定义 artifact frontmatter 标准（data-contract 承载）。

### ADR-003：分场景层级激活机制（L3→L2→L1 按需裁剪）

| 字段 | 值 |
|---|---|
| 编号 | ADR-003 |
| 标题 | 平台按企业规模/租户档位按需激活体系层级（L3/L2/L1）的机制 |
| 日期 | 2026-07-23 |
| 状态 | 提议（Proposed）—— 待 team-pgm/team-standards 评审后接受 |
| 决策者 | team-ea（L3）|
| 影响范围 | eaiselp-capability / eaiselp-common.tenant / eaiselp-admin |
| 下游传导 | L2-Standards（定义 edition 字段语义）→ L1-Dev（实现按 edition 过滤加载）|

**背景**：平台服务三档用户（大型企业 L3→L2→L1 / 中小型 L2→L1 / 小团队 L1）。强制全层级加载对小团队是过度复杂，对大型企业不全层级是能力缺失。需定义按需激活机制。

**决策**：基于 `t_tenant.edition`（已有字段，pro/enterprise）+ `t_case.layer`（已有字段，L1/L2/L3）双层激活。
- capability 模块加载 agent/skill 时，按 tenant edition 过滤：
  - `enterprise`：加载全部 22 agent（含 L3 EA/GRC/Strategy + L2 PgM/Standards/VSM/Steward）
  - `pro`：加载 L2 + L1 agent（不加载 L3）
  - `starter`（M2 新增档位）：只加载 L1 agent（14 角色）
- case 创建时指定 layer，runtime 只激活对应层级的角色派生。

**备选方案（未选）**：
- 全层级恒加载：小团队门槛过高，资源浪费，否决。
- 按租户硬编码层级：不灵活，租户升级档位需改代码，否决。

**后果**：
- 正向：商用分档清晰，小团队低门槛，大型企业全能力。
- 负向：capability 加载逻辑变复杂（需 edition 过滤）；租户升级档位需重新加载体系。
- 约束：edition 字段语义 M2 由 Standards 定义；capability M2 实现按 edition 过滤加载逻辑。

## 本次经验沉淀

1. **EA 蓝图产出必须先读实际代码，不能凭文档记忆**。本次读 schema.sql 发现 8 表已有 tenant_id/deploy_mode/edition/layer 等字段，使 ADR-003（层级激活）能复用已有字段而非新增；读 DerivationEngine 发现 guessType 硬编码角色名，识别出 P6（零角色硬编码）这条原则的现实违反点，使原则不是空谈而是有具体重构目标。教训：架构原则要从代码债中长出来，不是拍脑袋。

2. **业务能力域应从模块反推，不是凭空划分**。本次 7 能力域是从 9 模块职责归纳而来，确保每个能力域有模块归属、有当前状态、有演进路径。这避免了"能力域空中楼阁"——能力域划分若与模块脱节，PgM 拆项目群时会无所适从。

3. **铁律要落地为可检查的工程原则**。5 铁律（承载不重写/唯一调度入口/多租户隔离/适配器 SPI/dogfooding）是高层理念，L1 无法直接执行。本蓝图把它们工程化为 P6-P11（如 P6"零角色硬编码"对应铁律 1，并指出 guessType 的具体违反点）。教训：EA 产出的原则必须可被 L2 翻译为门禁、可被 L1 执行，否则只是文档。
