## 0. 背景：EA 蓝图新增 9 条架构原则需要落地为工程标准

`docs/架构文档/企业架构蓝图.md` §7 在 ADR-001 P1-P5（Maven 模块边界）之上新增了 P6-P14 共 9 条架构原则，覆盖"平台承载体系"的核心约束。这 9 条原则目前分两类状态：

| 状态 | 原则 | 含义 |
|---|---|---|
| **已落地（记录性）** | P7 / P9 / P12 | 代码已实现，本标准固化为约束防回退 |
| **有技术债（待 M2 重构）** | P6 / P8 | M1 阶段有硬编码违反点，M2 子项目 SP-4/SP-6 负责清除 |
| **M2 落地（进行中）** | P10 / P11 / P13 / P14 | M2 子项目 SP-1~SP-7 的核心交付目标 |

> **本标准的定位**：ES-001 解决"Maven 模块构建层规范性"，ES-002 解决"执行层规范性"，**ES-003 解决"平台承载层规范性"——平台代码如何承载体系角色运作而不耦合体系**。三套标准都是强制级。

## §1 平台零角色硬编码规范（P6，对应 SP-4）

### 1.1 硬约束（强制，不可协商）

**平台 Java 代码（eaiselp-common / eaiselp-capability / eaiselp-adapter / eaiselp-data / eaiselp-runtime / eaiselp-gateway / eaiselp-auth / eaiselp-admin / eaiselp-observability 的 `src/main/java` 下）不得出现任何 team-\* 角色名字面量、skill 名字面量、command 名字面量、流程阶段名字面量的硬编码。** 所有这类映射必须：

- 配置化（application.yml / 配置表），或
- 从体系 markdown 加载（CapabilityLoader 已落地）。

### 1.2 当前违反点（P6 技术债，SP-4 负责清除）

| 违反位置 | 违反内容 | 清除方式 |
|---|---|---|
| `eaiselp-runtime/src/main/java/com/eaiselp/runtime/engine/DerivationEngine.java:88-97` | `guessType()` 方法用 switch 硬编码 13 个角色名（team-po→prd / team-ux→design / team-se→tech-design / team-ba→tasks / team-dev→code / team-reviewer→review / team-security→review / team-qa→test / team-performance→perf / team-ops→deploy / team-pm→tracking）做 artifact 类型推断 | SP-4 重构为 application.yml 配置 `eaiselp.artifact.type-mapping`（@ConfigurationProperties 注入 Map），删除 switch |
| `eaiselp-runtime/src/main/java/com/eaiselp/runtime/service/DerivationPersistenceService.java:87` | 仅注释（示例 JSON），**不算违反**——注释里举例 artifact 结构，但若注释删掉不影响功能，建议 SP-4 顺手清理 | SP-4 顺手清理注释中的角色名 |

### 1.3 L1-Reviewer 验收检查项（G11 门禁）

```powershell
# 在项目根执行（G11 完整脚本见 质量门禁-平台承载规范.ps1）
# 检查 eaiselp-*/src/main/java 下是否还有 team-po/team-ux/team-se/team-dev/team-ba/team-qa/team-reviewer/team-security/team-performance/team-ops/team-pm 字面量
# 排除规则：单行注释（// 开头，去除前导空白）不算违反
# 通过判据：命中数 = 0（SP-4 完成后阻断；SP-4 完成前 WARN）
```

### 1.4 例外（允许含角色名的地方）

| 位置 | 为什么允许 |
|---|---|
| `agents-config/` 下的 markdown（体系层角色定义）| 体系资产，不是平台代码。平台只加载不硬编码 |
| `eaiselp-*/src/test/`（测试 fixture）| 测试需要指定角色名做断言，但测试本身不进生产 |
| `*.yml` / `*.yaml` 配置文件（如 `eaiselp.artifact.type-mapping.team-po=prd`）| 配置化正是 P6 要求的落点，角色名在配置里是合规的 |
| 代码注释（`//` 或 `/* */`）| 注释不影响行为，G11 排除注释行 |

### 1.5 反例与正例

```
❌ 错误（当前 DerivationEngine.java:88-97，违反 P6）：
   private String guessType(String role) {
       return switch (role) {
           case "team-po" -> "prd";        // 硬编码角色名
           case "team-ux" -> "design";     // 新增角色必须改这里
           ...
       };
   }

✅ 正确（SP-4 重构后）：
   // application.yml
   // eaiselp:
   //   artifact:
   //     type-mapping:
   //       team-po: prd
   //       team-ux: design
   //       (新增角色只加一行配置，不改代码)

   @ConfigurationProperties(prefix = "eaiselp.artifact")
   public class ArtifactTypeMapping {
       private Map<String, String> typeMapping = new HashMap<>();
       // getter/setter
   }

   // DerivationEngine 注入 ArtifactTypeMapping，guessType 改为：
   private String guessType(String role) {
       return typeMapping.getTypeMapping().getOrDefault(role, "other");
   }
```

## §2 模型路由配置化规范（P8，对应 SP-6）

**模型档位（tier：opus/sonnet/haiku 或 reasoning/structured/mechanical）→ 具体模型名的映射不得内联在 Java 代码常量里。** 所有这类映射必须：

- 迁移到配置表 `t_model_routing`（SP-6 新增，全局配置表无 tenant_id），或
- 退一步放 application.yml `eaiselp.adapter.llm.model-mapping`（M1 临时方案）。

## §3 多租户隔离规范（P11，对应 SP-2 / SP-7）

### 3.1 硬约束（强制，不可协商）

1. **所有业务表必须带 `tenant_id` 列**（M1 已落地：8 表均有；M2 新增表 t_program/t_subproject/t_adapter_config 带 tenant_id；t_model_routing 是全局配置表，豁免）。
2. **所有业务 SQL 自动注入 `tenant_id` 过滤**——通过 MyBatis-Plus 多租户拦截器（`EaiselpTenantHandler` 已落地）。
3. **禁止手写不带 tenant_id 的 SQL**——即禁止使用 `@InterceptorIgnore(tenantLine = "true")` 注解绕过拦截器。若确需绕过（如系统级全局查询），必须：
   - 提 EA 审批 ADR，记录绕过的正当理由
   - ADR 编号在代码注释里标注
4. **新增 Controller 从 TenantContext 取 tenant_id，不从请求参数取**——防客户端伪造 tenant_id 越权。

### 3.2 当前状态

| 检查项 | M1 现状 | G13 预跑结果 |
|---|---|---|
| MyBatis-Plus 多租户拦截器（EaiselpTenantHandler）| 已落地 | — |
| `@InterceptorIgnore` 注解使用 | **0 命中**（grep 验证）| PASS |
| TenantContext + TenantContextFilter | 已落地 | — |
| 业务表 tenant_id 列 | 8 表均有 | — |

### 3.3 L1-Reviewer 验收检查项（G13 门禁）

```powershell
# 检查 eaiselp-*/src/main/java 下是否有 @InterceptorIgnore(tenantLine = ...) 注解
# 通过判据：命中数 = 0（除非代码注释里标注了 EA 审批的 ADR 编号）
# 类别：阻断（无 ADR 审批时）
```

### 3.4 SP-2 落地新增约束（auth + gateway）

SP-2 实现后，多租户隔离强化为：

| 层 | 约束 |
|---|---|
| gateway | 从 JWT 解析 tenant_id，注入 `X-Tenant-Id` header 转发给下游 |
| runtime TenantContextFilter | 从 `X-Tenant-Id` header 读 tenant_id 填 ThreadLocal（不重复鉴权，与 gateway 分工）|
| auth | JWT payload 必须含 `tenant_id` 字段（C-1 契约）|

### 3.5 反例与正例

```
❌ 错误（违反 P11）：
   // 1. Controller 从请求参数取 tenant_id（客户端可伪造）
   @GetMapping("/case")
   public List<Case> list(@RequestParam Long tenantId) { ... }

   // 2. Mapper 手写不带 tenant_id 的 SQL
   @InterceptorIgnore(tenantLine = "true")   // 绕过拦截器，无 ADR 审批
   @Select("SELECT * FROM t_case")
   List<Case> selectAllIgnoreTenant();

✅ 正确：
   // 1. Controller 从 TenantContext 取（从 JWT 来，不可伪造）
   @GetMapping("/case")
   public List<Case> list() {
       Long tenantId = TenantContext.getTenantId();
       return caseService.listByTenant(tenantId);
   }

   // 2. 用 MyBatis-Plus LambdaQueryWrapper，拦截器自动注入 tenant_id
   caseService.lambdaQuery().eq(Case::getStatus, "drafting").list();
   // 生成的 SQL 自动带 WHERE tenant_id = ?
```

## §4 接口版本化规范（P13，对应 SP-2 / SP-3）

| `eaiselp-capability/.../controller/CapabilityController.java` | `@RequestMapping("/api/capability")` 无版本前缀 | 同上迁移到 `/api/v1/capability` |

## §5 过程资产入平台规范（P10，对应 SP-4）

### 5.1 硬约束（强制，不可协商）

**每个 case 的关键产出（PRD / 方案 / 评审 / 测试报告 / 代码等）必须结构化入 `t_artifact` 表，不只入 git。**

t_artifact 是"过程透明化"的数据载体（EA 蓝图 §1.1 核心价值）。只入 git 无法检索/追溯/治理；入 t_artifact 才能全链路透明。

### 5.2 当前状态（M1 临时方案 → M2 结构化）

| 阶段 | 存储方式 | t_artifact 字段填充情况 |
|---|---|---|
| M1（当前）| LLM 输出整段存 t_artifact.content，type 由 guessType 推断 | `frontmatter` / `doc_key` / `contract_key` **全 NULL** |
| M2（SP-4 目标）| 结构化 frontmatter + 正文分离 | 三字段必须填充（见 §5.3）|
| M3 | 对接企业 DocStore | `doc_key` 指向企业系统文档 ID |

### 5.3 t_artifact 结构化字段填充规范（SP-4 落地后强制）

| 字段 | 类型 | M2 填充要求 | 示例 |
|---|---|---|---|
| `type` | VARCHAR(32) | **必填**，从 `eaiselp.artifact.type-mapping` 配置映射（不再 guess）| `prd` / `design` / `tech-design` / `tasks` / `code` / `review` / `test` / `perf` / `deploy` / `tracking` / `other` |
| `frontmatter` | JSON | **必填**（SP-4 后），结构化元数据 | `{"version":"1.0","review_status":"draft","approver":null,"tags":["m2","auth"]}` |
| `doc_key` | VARCHAR(200) | M2 填平台内 doc_id；M3 填企业系统文档 ID | `case-20260723-sp2/auth-prd-v1` |
| `contract_key` | VARCHAR(200) | **可选**，data-contract 标识（Steward 协同定义后强制）| `artifact:prd:v1` |
| `derivation_id` | BIGINT | **必填**，关联派生记录（追溯产出来源）| `123` |

### 5.4 L1-Reviewer 验收检查项（G15 门禁）

```powershell
# 检查 t_artifact 表中 frontmatter/doc_key/contract_key 三字段是否全 NULL
# 通过判据：三字段不应全 NULL（SP-4 完成后阻断；SP-4 完成前 WARN——因为 M1 阶段本就全 NULL）
# 实现方式：连 MySQL 查 SELECT COUNT(*) FROM t_artifact WHERE frontmatter IS NULL AND doc_key IS NULL AND contract_key IS NULL
# M1 阶段无 DB 连接时，G15 降级为查 schema.sql 是否存在这三列（存在即 WARN 提示字段待填充）
```

### 5.5 反例与正例

```
❌ 错误（违反 P10，M1 当前状态）：
   DerivationEngine 派生后，LLM 输出整段存 1 个 artifact：
   - type = guessType(role) 推断（P6 违反）
   - frontmatter = NULL
   - doc_key = NULL
   - contract_key = NULL
   结果：过程资产不可检索、不可追溯、不可治理

✅ 正确（SP-4 后）：
   DerivationEngine 派生后，extractArtifacts + persist：
   - type = typeMapping.get(role)（配置化）
   - frontmatter = parseFrontmatter(llmOutput)（结构化 JSON）
   - doc_key = generateDocKey(caseId, role, version)
   - contract_key = "artifact:" + type + ":v1"
   - derivation_id = 本次派生 ID
   结果：过程资产可按 type/role/stage/frontmatter 标签检索，全链路追溯
```

## §6 分场景层级激活规范（P14 / ADR-003，对应 SP-5）

### 6.1 硬约束（强制，不可协商）

**CapabilityLoader 加载 agent/skill 时，必须按 `t_tenant.edition`（enterprise/pro/starter）过滤加载体系层级（L3/L2/L1），不得强制全层级加载。**

| edition | 加载层级 | agent 数 |
|---|---|---|
| `enterprise` | L3 + L2 + L1 | 22（全部）|
| `pro` | L2 + L1 | 约 18（不含 L3 的 ea/grc/strategy）|
| `starter`（M2 SP-5 新增档位）| L1 | 14（基础角色流水线）|

### 6.2 当前违反点（M1 全量加载）

| 违反位置 | 现状 | SP-5 改造 |
|---|---|---|
