## 0. 阅读指引（怎么用这份框架）

本框架不是单项目的风险清单，而是**整个平台"生产敢用"的治理顶层设计纲**。四类读者按需取用：

| 读者 | 必读章节 | 怎么用 |
|---|---|---|
| **L2 team-standards** | §7 给 L2/L1 的治理约束 | 把 G1-G14 治理要求翻译为质量门禁写入 CLAUDE.md / .ps1 脚本 |
| **L1 编排者/SE** | §3 可靠性治理 + §7 给 L1 的约束 | 出技术方案时落地 4 道防线，遵守不可逆操作锁 |
| **L1 Reviewer/QA** | §3 防线 2 + §7 给 L1 的约束 | 执行独立校验，不抄 Dev 报告 |
| **L2 team-pgm / L3 team-ea** | §2 风险 + §6 持续改进 | 据风险登记册排期整改，据治理指标评估体系健康度 |

**前置约束（不可违背）**：本框架不替代 EA 架构原则、不替代 Standards 工程标准、不替代 Steward 数据标准、不替代 Reviewer 代码门禁。GRC 是**监督层**——审视这些是否被遵循、是否仍适用、是否有效、是否可控。

## 1. 治理体系总览

### 1.1 治理目标：让平台"生产敢用"，不只"演示能跑"

平台 M1 已验证"手调派生跑通"——这是**演示能跑**。但商用要求**生产敢用**：企业敢把真实业务交由平台运作，敢让 22 角色 case 流水线无人值守跑生产代码，敢让多租户共享一个平台。

两个状态的差距，本质是**治理成熟度**：

| 维度 | 演示能跑（M1 已达）| 生产敢用（治理目标）|
|---|---|---|
| 可靠性 | 单角色手调验证 | AI 出错可拦住、可校验、可回滚（4 道防线）|
| 数据安全 | 单租户单进程 | 多租户隔离不泄露（P11 + G13 门禁）|
| 成本 | 不计 token | LLM 成本可计量、可控制、可优化（cost-governance）|
| 合规 | 无合规基线 | 等保/GDPR/AI 生成内容合规达标 |
| 可审计 | log.info 手写 | 全链路审计追溯链可还原任一操作 |
| 可改进 | 无治理指标 | 治理指标驱动持续改进闭环 |

**一句话治理目标**：用最小治理开销，让平台从"信任每个角色"升级为"不信任、必校验、可回滚、可审计"，达到商用可接受的风险水位。

### 1.2 治理框架对标（COBIT/COSO/ITIL/ISO 31000 裁剪到 AI 可执行）

业界四大框架各有侧重，本框架裁剪其交集到 AI 可执行的最小集——**不堆砌标准，每条都能落到平台实现或门禁检查**：

| 框架 | 原始定位 | 本框架裁剪点 | 平台落地 |
|---|---|---|---|
| **COBIT 2019** | IT 治理目标/管理目标/控制目标 | 裁剪：治理策略审视 + 控制有效性评估 + 持续改进 | §6 治理审计周期 + 控制有效性复验 |
| **COSO ERM** | 企业风险管理八要素 | 裁剪：内部环境/识别/评估/应对/监控 | §2 风险登记册 + 风险预警机制 |
| **ITIL 4** | 服务价值系统/四维度 | 裁剪：变更管理（CAB）/事件管理 | §3 防线 1 不可逆操作变更管理 |
| **ISO 31000** | 风险管理原则与指南 | 裁剪：风险识别/分析/评价/处置闭环 | §2 风险矩阵（可能性×影响）|
| **三道防线模型** | 业务执行/风控监督/内审 | 裁剪：GRC 在第二道（监督），不替代第三道内审 | §1.3 治理组织分工 |

**裁剪原则**：原版标准动辄数百条控制目标，对 AI 平台过度。本框架只保留**与 AI 多 Agent 软件工程直接相关**的治理要求，其余（如财务内控 SOX 细则）等平台进入强合规行业客户时再扩展。

### 1.3 治理组织（三层分工，GRC 监督不下场执行）

```
┌─────────────────────────────────────────────────────────────────┐
│                     第一道防线：业务执行（L1/L2）                 │
│                                                                  │
│  L1 各角色执行（Dev 写码/Reviewer 核对/QA 测试/Ops 部署）         │
│  L2 Standards 定门禁 / Steward 治数据 / PgM 管项目群             │
│  → 第一手风险在这里产生和自控                                    │
├─────────────────────────────────────────────────────────────────┤
│              第二道防线：风险合规监督（GRC 主理）                 │
│                                                                  │
│  team-grc 独立审视——不替代第一道执行：                            │
│  - 审视 EA 原则是否被遵循、是否仍适用                            │
│  - 审视 Standards 门禁是否真拦住风险                             │
│  - 审视 Steward 数据标准是否落地                                 │
│  - 评估企业级系统性风险（不替代 PM/PgM 项目级风险）               │
│  - 合规基线对照                                                  │
│  - 控制有效性复验                                                │
├─────────────────────────────────────────────────────────────────┤
│              第三道防线：内部审计（企业内审，GRC 不替代）          │
│                                                                  │
│  企业的内审/外审（如 ISAE 3402 / SOX 审计）——法定人责            │
│  GRC 只为内审提供证据链（t_governance_log），不替代内审裁定      │
└─────────────────────────────────────────────────────────────────┘
```

| 层级 | 角色 | 在治理中的职责 | GRC 与其关系 |
|---|---|---|---|
| L3 | **team-grc**（本框架主理）| 治理审视/审计/风险评估/合规/控制评估/改进驱动 | 自身 |
| L3 | team-ea | 定架构原则（P1-P14）| GRC 审视原则是否被遵循、是否仍适用，反哺 EA 修订 |
| L2 | team-standards | 把治理要求翻译为门禁（G1-G14）| GRC 审视门禁是否真拦住风险，反哺 Standards 强化 |
| L2 | team-steward | 定数据标准/质量规则 | GRC 审视数据标准是否落地，反哺 Steward 强化 |
| L2 | team-pgm | 管项目级风险 | GRC 管企业级系统性风险，与 PgM 项目级风险互补 |
| L1 | team-orchestrator | 执行 case 流水线，遵守人工锁 | GRC 审计 case 执行是否符合 4 道防线 |
| L1 | team-reviewer/team-qa | 执行独立校验（防线 2）| GRC 评估校验有效性（是否真拦住缺陷）|
| L1 | team-ops | 执行不可逆操作（带人工锁）| GRC 审计操作是否经确认、是否留回滚方案 |
| L1 | team-security | 查代码安全 | GRC 审计安全控制是否有效（与 compliance-audit 协同）|

**关键边界**：GRC 不下场执行。GRC 不写门禁脚本（Standards 写）、不做代码 Review（Reviewer 做）、不裁定审计结论（人工签字）、不决定风险处置（人工决策）。GRC 只**审视、审计、评估、报告、驱动改进**。

### 1.4 AI vs 人的职责边界（法定人责不越权）

这是本框架的**硬约束**，不可协商：

| 治理活动 | AI 可自主（GRC 工具化）| 人工保留（法定人责）|
|---|---|---|
| 数据采集 | 自动从 t_derivation/t_artifact/t_governance_log 采集指标 | — |
| 规则检查 | 自动检查门禁是否通过、租户是否隔离、配额是否超限 | — |
| 风险预警 | 自动识别风险信号并触发告警 | — |
| 审计报告生成 | 自动生成审计报告草稿（缺陷清单/整改建议）| — |
| 改进建议 | 自动产出"补强哪个门禁/修订哪条原则"建议 | — |
| 控制有效性评估 | 自动统计门禁拦截率、误判率 | — |
| **审计结论签字** | — | **人工签字**（审计报告结论的法定人责）|
| **内控认证** | — | **人工认证**（如 ISAE/SOX 内控认证）|
| **合规处罚决定** | — | **人工裁定**（违规如何处罚）|
| **重大风险处置决策** | — | **人工决策**（如发现数据泄露如何处置）|
| **不可逆操作执行** | — | **人工确认后 Ops 执行**（防线 1）|

**底线**：AI 可质疑、可预警、可拦停（不可逆操作人工锁是 AI 可执行的拦截），但**不裁定**（审计结论/处罚/认证/重大处置是法定人责）。本框架所有"审计报告"末尾都标注"结论待人工签字"，所有"风险预警"都路由到责任人决策而非 AI 自动处置。

## 2. 风险管理（COSO ERM / ISO 31000 裁剪）

### 2.1 平台运行的四大风险分类

基于 EA 蓝图 §5.6 风险矩阵 + 三大治理 skill，平台运行有四类核心风险。每类风险对应一个治理 skill 落地：

| 风险类别 | 一句话定义 | 治理 skill 落地 | 平台实现载体 |
|---|---|---|---|
| **AI 可靠性风险** | AI 幻觉/虚报/不可逆操作造成生产事故 | reliability-governance 4 道防线 | t_checkpoint + 独立校验 + git 回滚 |
| **数据安全风险** | 多租户越权/敏感数据泄露/数据丢失 | EA P11 多租户隔离 + G13 门禁 | tenant_id 拦截器 + 审计链 |
| **成本失控风险** | LLM token 消耗爆炸，规模化下不可持续 | cost-governance 配额与降级 | t_quota + 模型路由 + 上下文裁剪 |
| **合规风险** | AI 生成内容违规/数据隐私违法/等保不达标 | compliance-audit + 本框架 §5 | 合规基线对照 + 审计证据链 |

### 2.2 风险登记册（Risk Register）

按 ISO 31000 风险矩阵（可能性×影响）登记。风险等级：红（高×高）/黄（中）/绿（低）。

#### RISK-001：AI 幻觉导致代码/方案虚构（AI 可靠性）

| 字段 | 值 |
|---|---|
| 类别 | AI 可靠性 |
| 描述 | Dev/SE 角色产出虚构的 API 调用、不存在的库依赖、臆造的实现路径，未被拦截流入生产 |
| 可能性 | 中（LLM 固有特性）|
| 影响 | 高（虚构代码上线导致运行时崩溃/安全漏洞）|
| 风险等级 | 黄 |
| 应对策略 | 减轻（防线 2 独立校验 + 防线 3 可回滚）|
| 责任人 | team-reviewer（代码层）+ team-grc（审计校验有效性）|
| 状态 | 开放（M2 防线 2 落地后复验）|

#### RISK-002：AI 虚报测试通过（AI 可靠性）

| 字段 | 值 |
|---|---|
| 类别 | AI 可靠性 |
| 描述 | QA 角色报告"13 PASS"但实际未真跑，或 Dev 自证 git diff 但实际未改（M1 已有 Dev 自证机制，仍是单方）|
| 可能性 | 中 |
| 影响 | 高（缺陷流入生产）|
| 风险等级 | 黄 |
| 应对策略 | 减轻（防线 2：QA 不抄 Dev 报告，编排者抽查 AC 覆盖）|
| 责任人 | team-qa + team-orchestrator |
| 状态 | 开放 |

#### RISK-003：AI 自治执行不可逆操作（AI 可靠性，最高危）

| 字段 | 值 |
|---|---|
| 类别 | AI 可靠性 |
| 描述 | Ops 角色未经人工确认执行生产部署/数据删除/schema 变更/主分支 push，造成不可恢复损失 |
| 可能性 | 低（已有 Ops 角色定义约束）|
| 影响 | 极高（数据丢失/生产宕机/历史污染）|
| 风险等级 | 黄（可能性低但影响极高，须用人工锁把可能性压到接近零）|
| 应对策略 | 规避（防线 1：不可逆操作一律人工锁，禁止 AI 自治）|
| 责任人 | team-ops（执行）+ team-orchestrator（确认）+ 用户（最终确认）|
| 状态 | 开放（M2 t_checkpoint 人工锁落地后闭环）|

#### RISK-004：多租户数据越权泄露（数据安全，最高危）

| 字段 | 值 |
|---|---|
| 类别 | 数据安全 |
| 描述 | 共享库共享 schema 模式下，因 SQL 漏带 tenant_id 或拦截器失效，租户 A 看到/改了租户 B 的 case/artifact 数据 |
| 可能性 | 低（MyBatis-Plus 拦截器已落地）|
| 影响 | 极高（商用信誉崩塌 + 合规违规 + 法律责任）|
| 风险等级 | 黄（EA 蓝图 §5.6 标"极高影响"，须持续审计把可能性压到接近零）|
| 应对策略 | 减轻（P11 拦截器 + G13 门禁禁手写无 tenant_id SQL + 渗透测试 + GRC 审计）|
| 责任人 | team-security + team-grc |
| 状态 | 开放（M2 渗透测试 + GRC 季度审计后持续复验）|

#### RISK-005：LLM 成本失控（成本）

| 字段 | 值 |
|---|---|
| 类别 | 成本 |
| 描述 | 规模化后（每天几十上百 case），全量上下文注入 + reasoning 档滥用 + 无配额，token 账单爆炸，吞噬利润 |
| 可能性 | 高（线性增长，无治理必然发生）|
| 影响 | 中（不致命但吞噬商用利润）|
| 风险等级 | 黄 |
| 应对策略 | 减轻（cost-governance 三手段：配额 + 降级 + 裁剪）|
| 责任人 | team-orchestrator（case 级）+ team-pgm（项目群级）+ team-grc（成本审计）|
| 状态 | 开放（M2 t_quota 强校验 + 模型路由配置化后闭环）|

#### RISK-006：AI 生成内容违法违规（合规）

| 字段 | 值 |
|---|---|
| 类别 | 合规 |
| 描述 | AI 角色产出含违规内容（如《生成式 AI 服务管理暂行办法》禁止的内容），或生成代码侵犯第三方知识产权 |
| 可能性 | 中 |
| 影响 | 高（监管处罚 + 下架 + 商用中止）|
| 风险等级 | 黄 |
| 应对策略 | 减轻（输入/输出内容过滤 + 审计链可追溯 + 人工抽检）|
| 责任人 | team-security + team-grc + 用户（重大内容人工把关）|
| 状态 | 开放（M2-M3 内容过滤机制落地后复验）|

#### RISK-007：审计追溯链断裂（合规/可靠性）

| 字段 | 值 |
|---|---|
| 类别 | 合规 + 可靠性 |
| 描述 | 派生调用/Case 状态变更/不可逆操作未留审计日志，出事后无法还原"谁在何时基于什么确认改了什么" |
| 可能性 | 中（M1 仅 t_derivation 记派生，状态变更/操作未全审计）|
| 影响 | 高（合规不达标 + 事故无法复盘）|
| 风险等级 | 黄 |
| 应对策略 | 减轻（M3 t_governance_log 全审计链落地）|
| 责任人 | team-dev（实现）+ team-grc（审计链完整性审视）|
| 状态 | 开放（M3 落地后闭环）|

#### RISK-008：模型供应商 API 变更导致中断（系统性）

| 字段 | 值 |
|---|---|
| 类别 | 系统性 |
| 描述 | GLM（当前唯一供应商）API 升级/限流/停服，平台派生全部中断 |
| 可能性 | 中（供应商单点）|
| 影响 | 高（全平台瘫痪）|
| 风险等级 | 黄 |
| 应对策略 | 减轻（model-registry 路由解耦 P8 + M3 多供应商路由）|
| 责任人 | team-dev + team-ea |
| 状态 | 开放（M2 路由配置化 + M3 多供应商后缓解）|

### 2.3 风险预警机制（什么情况触发告警）

GRC 不只是登记风险，要**主动预警**。预警信号由 system-observability skill 的埋点 + GRC 规则引擎识别：

| 预警信号 | 触发条件 | 告警对象 | 处置 |
|---|---|---|---|
| 可靠性预警 | case 成功率 < 80%（连续 N 个 case）| team-orchestrator + team-grc | 暂停新 case，复盘失败模式 |
| 可靠性预警 | 某角色派生反复失败 ≥ 2 轮 | team-orchestrator | 防线 4：上报用户，不硬试 |
| 数据安全预警 | 查询日志出现不带 tenant_id 的 SQL | team-security + team-grc | 立即排查拦截器是否失效 |
| 数据安全预警 | 跨租户访问尝试（tenant_id 不匹配的请求）| team-security | 立即阻断 + 审计 |
| 成本预警 | 单 case token 消耗达预算 80% | team-orchestrator | 预警，评估升预算或裁范围 |
| 成本预警 | 单 case token 消耗达预算 100% | team-orchestrator | 停止派生新角色 |
| 成本预警 | 项目群级 token 消耗周环比 > 50% | team-pgm + team-grc | 异常飙升排查（可能是上下文未裁剪）|
| 合规预警 | AI 产出命中违规关键词 | team-security | 拦截产出 + 人工复核 |
| 合规预警 | 审计日志写入失败 | team-dev + team-grc | 立即修复（审计链断裂是高危）|
| 系统性预警 | LLM 适配器调用失败率 > 10% | team-dev | 排查供应商 API，启动备用路由 |

**预警层级**：黄色预警（GRC 记录+通知责任人）→ 红色预警（GRC 拦停+上报用户决策）。GRC 可拦停（不可逆操作锁、超配额停止派生），但**不处置**（处置由人工决策）。

## 3. 可靠性治理（4 道防线在平台落地）

> 基于 reliability-governance skill 的 4 道防线，明确每道在 eAISEDP 平台的具体落地方式。这是平台从"演示能跑"到"生产敢用"的核心。

### 3.1 防线 1：不可逆操作人工锁（Red Line Lock）

**原则**：AI 不得未经人工确认执行任何不可逆操作。

#### 平台落地方式：t_checkpoint 检查点机制

EA 蓝图已建 `t_checkpoint` 表（M1 已建表，M2 落地人工锁逻辑）。本框架定义其状态机：

```
不可逆操作触发
     │
     ▼
INSERT t_checkpoint (status='pending', operation=..., confirmed_by=NULL)
     │
     ▼
编排者复核（计划合理性 + 回滚方案可行性）
     │  ├─ 不合理 → 驳回，状态置 'rejected'
     │  └─ 合理 → 上报用户
     ▼
用户显式确认
     │  ├─ 拒绝 → 状态置 'rejected'，操作不执行
     │  └─ 确认 → 状态置 'confirmed'，记录 confirmed_by + comment
     ▼
Ops 执行（仅 confirmed 状态可执行）
     │
     ▼
执行后验证 + 记录执行结果
     │
     ▼
状态置 'done'，留完整审计记录（谁/何时/基于什么确认/改了什么）
```

#### 不可逆操作清单（平台级，必须人工锁）

| 操作 | 为什么不可逆 | 平台检查点 | 谁确认 |
|---|---|---|---|
| 生产环境部署 | 影响真实用户 | t_checkpoint operation='deploy_prod' | 编排者 + 用户 |
| 数据库 schema 变更（DDL）| 删列/改类型丢数据 | t_checkpoint operation='ddl_change' | 用户 |
| 数据删除/清空 | 数据不可恢复 | t_checkpoint operation='data_delete' | 用户 |
| 生产配置变更（Nacos）| 影响线上行为 | t_checkpoint operation='config_change' | 用户 |
| 主分支 git push | 改写/污染历史 | t_checkpoint operation='main_push' | 用户 |
| 删除服务/下线模块 | 影响系统可用性 | t_checkpoint operation='service_offline' | 用户 |
| 模型部署到生产（MLOps）| 影响 AI 产品行为 | t_checkpoint operation='model_deploy' | 用户 |
| Case 状态置 done（闭环）| 闭环后难重开 | t_checkpoint operation='case_close' | 编排者 + 用户 |

**门禁要求**（GRC 审计）：上述任一操作若**无对应 t_checkpoint confirmed 记录直接执行**，判定为防线 1 失效，列为审计重大缺陷。

#### 当前落地情况

- M1：t_checkpoint 表已建，无人工锁逻辑（EA 蓝图 §3.1）
- M2：落地状态机 + 人工锁（EA 蓝图 §5.3 SP-3 交付物 ⑤）
- GRC 责任：M2 落地后审计第一个 case 的不可逆操作是否都经确认

### 3.2 防线 2：输出兜底校验（Defense-in-Depth）

**原则**：任何角色的关键产出，必须有独立校验，不采信单方报告。

#### 平台落地方式：模型隔离 + 编排者抽查

| 产出类型 | 产出者 | 独立校验者 | 平台校验方式 |
|---|---|---|---|
| 代码 | team-dev | team-reviewer + team-security | 磁盘 diff 核对（已有）+ G1-G6 模块边界门禁 |
| 测试结论 | team-qa | team-orchestrator | 抽查关键 AC 是否真覆盖（不抄 QA 报告）|
| 数据模型/迁移 | team-db | team-reviewer + team-orchestrator | 迁移脚本幂等性抽查（可重跑）|
| 性能结论 | team-performance | team-orchestrator | 压测数据真实性核对 |
| 部署/迁移方案 | team-ops | team-orchestrator | 回滚方案可行性核对 |
| 战略/架构决策 | team-ea/team-strategy | 用户（人工）| 重大决策须人确认（防线 1 兜底）|
| 度量数据 | team-analyst/team-vsm | team-orchestrator | 数据来源真实性核对 |

#### 核心原则（从不信任到校验）

1. **产出者不自证**：Dev 不能只靠自己报告通过，Reviewer 必须独立核对
2. **校验者不抄作业**：Reviewer/QA 不抄 Dev 报告，必须自己跑 diff/grep/read
3. **编排者兜底抽查**：编排者在部署前做最终抽查（fast 档核 1 处、standard 档核 2-3 处）
4. **重大决策上升到人**：架构/战略/预算类，编排者也不自治，上报用户

#### 门禁要求（GRC 审计）

- G7-G10 产出物门禁（已有）是防线 2 的工程化
- Reviewer/QA 校验记录入 t_artifact（review_status 字段）或审计链
- **若某 case 的 Reviewer 校验记录缺失或与 Dev 报告完全雷同（抄作业嫌疑）**，判定为防线 2 失效

### 3.3 防线 3：全链路可回滚（Rollback Everywhere）

**原则**：每个 AI 动作都要可回滚。出了问题能退回安全状态。

#### 平台落地方式

| 维度 | 回滚手段 | 平台实现 | 谁负责 |
|---|---|---|---|
| 代码改动 | git checkout / git reset | GitAdapter（已落地）+ 每个派生的 t_derivation 记录产出 | team-dev/team-ops |
| 配置变更 | 配置版本化 + 回滚到上一版 | Nacos 配置中心（M3）+ t_governance_log 记录变更 | team-ops |
| 部署 | 蓝绿/灰度 + 上一版本回滚 | CiCdAdapter（M4）+ t_checkpoint 记录部署 | team-ops |
| 数据库迁移 | 迁移脚本配套回滚脚本 | EA 要求每个 DDL 必配回滚说明 | team-db |
| 模型部署 | 模型注册表 + 版本回滚 | t_model_routing 版本化（M2）+ MLOps（插件）| team-mle/team-ops |
| 派生产出 | 派生记录可追溯 + 重新派生 | t_derivation 记录每次派生（input/output/model/token）| team-orchestrator |

#### 强制规则

- 阶段 5 部署前，Ops 必须先产出**回滚方案**（怎么退、退到哪、退了影响什么）。无回滚方案不得部署——这是 t_checkpoint operation='deploy_prod' 的必填前置项
- 数据库迁移脚本必须配套回滚说明（哪怕是"手动恢复"也要写清步骤）
- 部署用蓝绿/灰度，不走直接替换（M4 CiCdAdapter 落地后强制）

#### 门禁要求（GRC 审计）

- 部署类 t_checkpoint 的 comment 字段必须含回滚方案摘要
- **若部署检查点无回滚方案**，判定为防线 3 失效，拦截执行

### 3.4 防线 4：置信度评估与失败兜底

**原则**：AI 产出要标注置信度，低置信度的必须人工复核或重做。

#### 平台落地方式（分里程碑）

**M2（暂不做自动置信度评分）**：靠编排者人工评估 + 信号识别

| 置信度信号 | 判定 | 处置 |
|---|---|---|
| 角色自己标注不确定项（"此处假设 X，需确认"）| 中置信 | 编排者关注，必要时上报 |
| 角色产出与上下文矛盾/自相矛盾 | 低置信 | 打回重做 |
| 角色跳过步骤（如 Reviewer 没提任何缺陷）| 低置信 | 编排者复核 |
| 角色多轮修改仍不稳定 | 低置信 | 上报用户 |
| 角色产出与磁盘事实一致、覆盖完整、逻辑自洽 | 高置信 | 通过 |

**M3（引入置信度评分）**：基于 system-observability 埋点，对每个角色产出计算置信度分数（综合：产出完整性/与历史一致性/校验通过率/修改轮次）。低置信度自动触发人工复核标记。

#### 失败兜底

- 角色产出不合格：打回重做，最多 2 轮（已有机制）
- 2 轮仍不达标：上报用户，不自作主张放行
- 阶段卡死（某角色反复失败）：编排者上报，不强行推进
- **诚实原则优先**：宁可慢、宁可上报，绝不掩盖失败、绝不假通过

#### 门禁要求（GRC 审计）

- 若某 case 出现"2 轮失败后仍标记通过"，判定为防线 4 失效（假通过）

## 4. 审计追溯链

> 合规底线：任何操作都可还原"谁在何时基于什么确认改了什么"。审计链断裂 = 合规不达标。

### 4.1 审计事件分类

平台运行的所有关键事件必须留审计。分 5 类：

| 事件类别 | 审计事件 | 当前载体 | M3 落地载体 |
|---|---|---|---|
| **派生调用** | 谁调用了哪个角色/用哪个模型/消耗多少 token/产出什么 | t_derivation（已落地）| t_derivation + t_governance_log 补充 |
| **Case 状态变更** | Case 从 drafting→deriving→reviewing→checkpoint→done 的每次流转 | t_case.status（M1 有字段无变更日志）| t_governance_log 记录每次变更 |
| **角色产出** | 14 角色的 PRD/方案/评审/测试报告/代码产出 | t_artifact（已落地）| t_artifact + frontmatter 记录 review_status |
| **不可逆操作** | 部署/DDL/删除/配置变更/主分支 push | t_checkpoint（M2 落地）| t_checkpoint + t_governance_log |
| **配置变更** | 模型路由/适配器配置/租户配额变更 | 无（M1）| t_governance_log + 配置版本化 |

### 4.2 审计日志结构（who/when/what/before/after）

M3 新增 `t_governance_log` 表（EA 蓝图 §3.4 已规划），结构遵循审计标准：

```sql
CREATE TABLE t_governance_log (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id       BIGINT       NOT NULL,          -- 多租户隔离（P11）
    event_category  VARCHAR(32)  NOT NULL,          -- derivation/case_change/artifact/irreversible/config
    event_type      VARCHAR(64)  NOT NULL,          -- 具体事件类型（如 deploy_prod, ddl_change）
    actor_type      VARCHAR(16)  NOT NULL,          -- agent（AI 角色）/ user（人工）/ system
    actor_id        VARCHAR(64)  NOT NULL,          -- agent_id 或 user_id
    actor_role      VARCHAR(32),                    -- 角色（如 team-ops）
    target_type     VARCHAR(32)  NOT NULL,          -- 操作对象类型（case/derivation/checkpoint/config）
    target_id       VARCHAR(64)  NOT NULL,          -- 操作对象 ID
    action          VARCHAR(32)  NOT NULL,          -- create/update/delete/execute/confirm
    before_state    JSON,                           -- 变更前状态（update 类必填）
    after_state     JSON,                           -- 变更后状态（update/create 类必填）
    confirmation    JSON,                           -- 人工确认信息（irreversible 类必填：confirmed_by/reason/comment）
    rollback_plan   TEXT,                           -- 回滚方案（irreversible 类必填）
    create_time     DATETIME     NOT NULL,          -- when
    INDEX idx_tenant_target (tenant_id, target_type, target_id),
    INDEX idx_event_time (event_category, create_time)
);
```

**关键字段说明**：
- `confirmation`：对不可逆操作，记录**谁确认的、基于什么理由**——这是法定人责的留痕
- `rollback_plan`：对部署/DDL 类，记录回滚方案——防线 3 的审计留痕
- `before_state`/`after_state`：任何变更都记录前后态——可还原任一时刻状态

### 4.3 当前落地情况与演进

| 阶段 | 审计能力 | 缺口 |
|---|---|---|
| **M1（当前）** | t_derivation 记录派生审计（who/when/what/model/token/cost）| Case 状态变更/不可逆操作/配置变更未审计 |
| **M2** | t_checkpoint 落地，不可逆操作审计部分覆盖 | 配置变更审计仍缺 |
| **M3** | t_governance_log 全审计链落地（EA 蓝图 §5.4 SP-10）| — |
| **M4** | 审计链对接企业 SIEM（安全信息事件管理）| — |

### 4.4 保留期限（合规要求）

| 数据类别 | 保留期限 | 依据 |
|---|---|---|
| 派生审计（t_derivation）| ≥ 3 年 | 软件工程过程资产保留惯例 |
| 不可逆操作审计（t_governance_log irreversible 类）| ≥ 6 年 | 等保 2.0 三级要求（日志留存 ≥ 6 个月，重要操作审计建议更长）|
| 合规审计报告 | ≥ 10 年 | SOX/内控审计惯例 |
| 安全事件日志 | ≥ 6 个月（等保）/ ≥ 1 年（GDPR 事故调查）| 等保 2.0 + GDPR |

**M3 落地**：t_governance_log 配置 TTL 策略，到期归档到冷存储（MinIO），不物理删除（合规要求可追溯）。

## 5. 合规基线

> 平台商用必须满足的法规合规基线。按企业部署地域/行业裁剪。

### 5.1 等保 2.0（中国信息安全等级保护）

**适用**：所有中国境内部署的客户，建议定级二级（一般业务系统）或三级（涉及重要数据）。

| 等保要求域 | 平台落地措施 | 里程碑 |
|---|---|---|
| 安全物理环境 | 私有部署依赖客户机房；SaaS 依赖云厂商等保 | — |
| 安全通信网络 | gateway 网关（M2）+ 通信加密（HTTPS）| M2 |
| 安全区域边界 | 网络隔离 + 防火墙规则（依赖部署环境）| M2 |
| 安全计算环境 | 多租户隔离（P11）+ 身份认证（auth，M2 JWT+RBAC）+ 访问控制 | M2 |
| 安全管理中心 | admin 管理后台（M2 落地）+ 集中审计（t_governance_log，M3）| M2-M3 |
| **安全审计（重点）** | t_governance_log 全审计链 + 审计日志防篡改（只追加不修改）+ 留存 ≥ 6 个月 | M3 |

**GRC 责任**：客户定级后，GRC 出"等保符合性对照表"，逐项核对平台措施，缺口列入整改。

### 5.2 GDPR / 个人信息保护法（多租户数据隔离）

**适用**：欧盟客户（GDPR）/ 所有中国客户（个人信息保护法）。

| 合规要求 | 平台落地措施 | 里程碑 |
|---|---|---|
| 数据最小化 | 仅采集必要用户信息（t_user 最小字段）| M1 已落地 |
| 目的限制 | 用户数据仅用于认证/授权，不挪用 | M2 auth 落地 |
| 数据隔离（多租户）| tenant_id 隔离（P11）+ MyBatis-Plus 拦截器 | M1 已落地，M2 渗透测试 |
| 数据可删除（被遗忘权）| 用户注销时物理/逻辑删除其数据（M2 auth 提供接口）| M2 |
| 数据可移植 | 用户可导出其 case/artifact 数据（M3 数据导出接口）| M3 |
| 数据泄露通知 | 安全事件 72 小时内通知（GDPR 要求）+ 审计链可追溯 | M3 安全事件响应流程 |
| 跨境传输 | 私有部署数据不出客户环境；SaaS 明确数据存储地域 | 按客户 |

**GRC 责任**：多租户隔离是 GDPR/个保法的底线。RISK-004（数据越权泄露）直接关联本项。GRC 季度审计租户隔离有效性。

### 5.3 AI 生成内容合规（中国《生成式 AI 服务管理暂行办法》）

**适用**：所有中国境内提供生成式 AI 服务的场景。

| 合规要求 | 平台落地措施 | 里程碑 |
|---|---|---|
| 训练数据合法 | 平台不训练模型（用现成 LLM 供应商），供应商负责训练数据合规 | — |
| 生成内容标识 | AI 产出的 artifact 标注"AI 生成"（t_artifact frontmatter 加 generated_by 字段）| M2 |
| 违法内容拦截 | 输入/输出内容过滤（接入供应商的内容安全 API + 平台关键词库）| M3 |
| 用户实名 | auth 落地实名认证（M2 JWT+RBAC 接企业 LDAP）| M2 |
| 算法备案 | 生成式 AI 服务需向网信办备案（企业侧责任，平台提供技术支撑）| 客户侧 |
| 抽检机制 | GRC + Security 定期抽检 AI 产出内容合规性 | M3 |

**GRC 责任**：AI 生成内容合规是平台商用的**红线**。RISK-006（AI 生成内容违规）直接关联。GRC 建立抽检机制，重大违规内容立即拦停并上报。

### 5.4 合规落地优先级

| 合规项 | 优先级 | 理由 |
|---|---|---|
| 多租户隔离（等保+GDPR）| P0 | 商用底线，RISK-004 最高危 |
| 安全审计链（等保）| P0 | 合规硬要求，RISK-007 |
| 身份认证（等保+AI 办法）| P0 | M2 auth 落地 |
| AI 生成内容标识（AI 办法）| P1 | M2 frontmatter 强化 |
| 内容过滤（AI 办法）| P1 | M3 接入供应商内容安全 |
| 数据导出/删除（GDPR）| P2 | M3 数据导出接口 |

## 6. 持续改进

> GRC 不是一次性审计，是持续闭环。基于 COBIT 持续改进驱动。

### 6.1 治理审计周期

| 审计类型 | 周期 | 范围 | 产出 |
|---|---|---|---|
| **case 级审计** | 每个 case 闭环时 | 该 case 是否遵守 4 道防线、人工锁是否经确认、产出是否独立校验 | case 治理评分（入 t_artifact frontmatter）|
| **周度审计** | 每周 | 本周所有 case 的成功率/门禁通过率/成本/安全事件 | 周度治理简报 |
| **里程碑审计** | 每里程碑（M2/M3/M4）| 该里程碑交付物的治理符合性（防线落地/合规达标/审计链完整）| 里程碑治理审计报告 |
| **季度审计** | 每季度 | 企业级系统性风险复评 + 控制有效性复验 + 合规基线对照 | 季度治理审计报告（含风险登记册更新）|
| **事件驱动审计** | 重大变更/生产事故/合规检查触发 | 针对性审计 | 专项审计报告 |

**法定人责**：所有审计报告的"结论"段落保留人工签字栏，GRC 生成草稿，人工签字生效。

### 6.2 治理指标（GRC 监控的 KPI）

基于 system-observability skill 的埋点，GRC 监控以下指标：

| 指标类别 | 指标 | 健康阈值 | 预警阈值 | 数据来源 |
|---|---|---|---|---|
| **可靠性** | case 成功率 | ≥ 90% | < 80% | t_case.status='done' / 总 case |
| **可靠性** | 门禁一次通过率 | ≥ 85% | < 70% | G1-G10 门禁结果 |
| **可靠性** | 假通过率（防线 4）| 0 | > 0 | 2 轮失败后仍通过的 case |
| **可靠性** | 不可逆操作确认率 | 100% | < 100% | t_checkpoint confirmed/total |
| **数据安全** | 跨租户访问尝试数 | 0 | > 0 | 拦截器日志 |
| **数据安全** | 不带 tenant_id 的 SQL 数 | 0 | > 0 | 慢查询日志 + 代码扫描 |
| **成本** | 单 case 平均 token | 在预算内 | > 预算 100% | t_derivation token 汇总 |
| **成本** | 项目群 token 周环比 | < 20% | > 50% | t_quota 周汇总 |
| **合规** | 审计日志完整率 | 100% | < 100% | t_governance_log 写入成功率 |
| **合规** | 合规审计通过率 | 100% | < 100% | 季度审计 |
| **效率** | 阶段平均耗时 | 在 SLA 内 | > SLA 150% | t_derivation duration |

### 6.3 改进闭环（发现问题→记录→分析→改进→验证）

```
GRC 审计/评估/预警
     │
     ▼ 发现缺陷/风险/控制失效
记录到治理审计报告 + 风险登记册
     │
     ▼ 分析根因
是标准未遵循？ → 反馈 team-standards 强化门禁
是门禁漏判？   → 反馈 team-standards 补门禁清单
是数据失控？   → 反馈 team-steward 强化数据治理
是流程走样？   → 反馈 team-ea/team-pgm 调整流程
是原则过时？   → 反馈 team-ea 修订架构原则
是控制无效？   → 反馈对应角色补强控制
     │
     ▼ 整改（执行层）
对应角色整改 + GRC 跟踪
     │
     ▼ 复验
GRC 下一周期审计复验整改有效性
     │
     ▼ 闭环
缺陷关闭 + 经验沉淀（knowledge-management）
```

**改进反哺示例**：
- 若审计发现 Reviewer 多次抄 Dev 报告 → 反馈 Standards 强化"Reviewer 必须独立跑 diff"门禁
- 若审计发现某 case 部署未留回滚方案 → 反馈 Standards 把"回滚方案"设为 t_checkpoint 必填项门禁
- 若审计发现租户隔离有漏洞 → 反馈 Security 补渗透测试 + 反馈 EA 评估是否升级隔离模式（共享 schema→独立 schema）

## 9. 本次经验沉淀

1. **GRC 框架必须基于 EA 蓝图的实证资产，不能凭空设计治理要求**。本次先读 EA 蓝图发现 t_checkpoint 表已建（M1）、t_governance_log 已规划（M3）、P11 多租户拦截器已落地，使本框架的防线 1（人工锁）能直接绑定 t_checkpoint 状态机而非另起炉灶，使 G13 门禁能直接对应 P11 而非泛泛而谈"要做隔离"。教训：治理要求必须落到平台已有的表/SPI/拦截器上，否则就是空谈，L2 无法翻译为门禁。

2. **AI vs 人的职责边界是 GRC 的红线，必须反复声明**。本次在 §1.4 用表格明确"AI 可自主做采集/检查/预警/报告，但审计签字/内控认证/处罚决定/重大风险处置保留人工"。每份审计报告末尾都标注"结论待人工签字"。教训：GRC 的权威性来自"AI 支撑、人定夺"——AI 越权裁定会引发法定人责风险，AI 不敢拦停又会让治理形同虚设。边界要清晰到每一条治理活动。

3. **风险登记册要区分"可能性低但影响极高"的红线风险**。本次 RISK-003（不可逆操作自治执行）和 RISK-004（多租户越权泄露）都是"可能性低、影响极高"——这类风险不能用"概率低"接受，必须用人工锁/渗透测试把可能性压到接近零。教训：风险矩阵不能只看等级（红/黄/绿），要看"影响维度是否触及商用底线"——触及底线的影响极高类，无论可能性多低都要用最强控制（规避而非减轻）。
