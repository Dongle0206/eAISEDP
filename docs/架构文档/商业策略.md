## 0. 阅读指引（怎么用这份策略）

本策略不是技术方案，而是**回答企业决策层的四个商业问题**：做不做、投多少、先做哪个、怎么变现。四类读者按需取用：

| 读者 | 必读章节 | 怎么用 |
|---|---|---|
| **决策层（CEO/CFO/CTO）** | §3 ROI 测算 + §5 投资优先级 + §6 风险评估 | 据此做立项/预算终决。ROI 是估算，看置信区间而非单点数字 |
| **销售团队** | §1 市场定位 + §2 商业模式 + §6 合规风险 | 据此对客户讲价值主张、定价、风险兜底 |
| **team-pgm** | §5 投资优先级 | 据此给 7 个子项目（SP-1~SP-7）排资源投入顺序 |
| **team-standards** | §4 技术雷达 | 据此把 Adopt/Trial/Assess/Hold 翻译为技术选型门禁 |

**诚实声明（贯穿全篇）**：本策略所有成本/收益数字均为**估算**，基于传统软件服务企业的真实场景假设。不夸大收益、不隐藏成本、不为了"让项目通过"美化 ROI。每个估算标注假设来源与置信区间（高/中/低）。

## 1. 市场定位（Positioning）

> 市场定位层回答：平台解决什么核心问题？卖给谁？跟谁竞争？凭什么赢？

### 1.1 核心问题：传统软件服务企业怎么用 AI 转型

**一句话定位**：eAISEDP 不是又一个 AI 编程工具，而是**让传统软件服务企业把"散落的 AI 能力"变成"可治理的工程体系"的运行时平台**。

传统软件服务企业（做外包/项目交付/行业软件）当前面对的真实痛点（EA 蓝图 §1.1 已映射，此处聚焦商业含义）：

| 企业痛点（商业语言） | 当前损失（隐形成本） | eAISEDP 解法（商业价值） |
|---|---|---|
| 团队各自买 Copilot/Cursor，能力不复用 | 每团队重复采购 + 经验不沉淀，人均工具费 200-500 元/月但 ROI 不可见 | 体系 markdown 驱动，22 角色/26 skills 全企业共享，**一次定义全企业复用**——工具费集中投，ROI 可度量 |
| 交付项目质量参差，靠老师傅经验 | 返工率 15-30%，项目利润率被返工吃掉 | 14 角色 case 流水线标准化交付，过程资产全链路追溯，**返工率可下降**（估算，需 case 数据验证） |
| 过程不透明，客户验收靠吵架 | 项目延期索赔，丢单风险 | 过程资产入平台数据，**管理者看得到每一步**，验收有据 |
| AI 协作无治理，模型成本失控 | 一个项目 LLM token 费 1-5 万，无人监控 | 内置 model-registry 档位 + cost-governance + 配额强校验，**token 成本可度量可管控** |
| 企业已有 GitLab/Jira/Confluence，换不掉 | 换工具迁移成本 50-200 万，阻力极大 | 适配器 SPI 零侵入接入，**企业工具零改动**，销售阻力最低 |

**核心洞察**：竞品卖"工具"（让程序员写得快），eAISEDP 卖"体系"（让企业交付得稳、管得住、复用得起）。这是**B2B 企业级**定位，不是 B2D 开发者工具定位。

### 1.2 目标市场（TAM/SAM/SOM 估算）

**目标市场**：企业级软件工程 AI 化。

| 层级 | 定义 | 规模估算（中国为主） | 置信度 |
|---|---|---|---|
| **TAM 总可服务市场** | 中国所有用 AI 做软件工程的企业 | 约 500-1000 亿元/年（含 AI 编程工具 + 服务）（2026 估算，行业报告外推）| 低——市场快速变化，口径不一 |
| **SAM 可服务细分** | 其中 100 人以上、有多项目协同需求、需要治理的企业级客户 | 约 80-150 亿元/年 | 中 |
| **SOM 可获取市场** | eAISEDP 3 年内能触达：传统软件服务商 + 行业软件企业 + 大型 IT 部门 | 约 3-8 亿元/年（占 SAM 3-6%）| 中——取决于销售能力与产品成熟度 |

**关键判断**：TAM 大但分散，eAISEDP 不打"全市场"，聚焦**有软件交付业务、被返工/治理/资产沉淀痛点驱动、且已有 IT 资产不舍得换**的传统企业。这是 SaaS 通用工具（Copilot/Cursor）覆盖不到、而定制方案又太贵的中间地带。

### 1.3 竞品分析（它们是工具，我们是体系+平台）

| 竞品 | 定位 | 优势 | 对 eAISEDP 的威胁 | eAISEDP 的差异化 |
|---|---|---|---|---|
| **GitHub Copilot** | 开发者个人 AI 编程助手 | IDE 集成深、品牌强、个人付费顺畅 | 高——心智占领，"AI 编程=Copilot" | Copilot 是个人工具，eAISEDP 是企业体系：Copilot 提效个人写代码，eAISEDP 治理全交付流程（需求→设计→开发→评审→测试→部署），过程资产可追溯 |
| **Cursor / Windsurf** | AI-first IDE | 体验好、上下文理解强、开发者喜爱 | 中——偏个人/小团队，企业级治理弱 | 同上。且 Cursor 强绑定自家 IDE，eAISEDP 适配企业已有 IDE/工具链 |
| **Cognition Devin / 国产 Devin 类** | 自主软件工程师 Agent | 端到端任务自动完成能力强 | 中高——概念重叠"AI 做软件" | Devin 是单 Agent 自动化，eAISEDP 是多 Agent 协同 + 人机边界明确（AI 主导分析，人掌握资源终决）。Devin 黑盒，eAISEDP 过程透明可治理 |
| **通义灵码 / 文心快码 / CodeGeeX** | 国产 AI 编程助手 | 国产合规、免费/低价、大厂背书 | 中——国产企业采购倾向 | 同 Copilot 维度的差异化：个人工具 vs 企业体系。eAISEDP 国产化友好（GLM 已接通，多供应商可换） |
| **企业自建 AI 平台** | 大企业自研 | 深度定制、数据不出域 | 高——大型企业倾向自建 | eAISEDP 卖 License + 实施服务给自建企业，做"体系方法论 + 平台底座"，比从零自建省 1-2 年 |
| **Jira/Confluence + Copilot 拼装** | 工具拼凑 | 企业已有，零迁移 | 中——能用但治理碎 | eAISEDP 通过适配器接 Jira/Confluence，不是替代而是编排它们，过程资产统一治理 |

### 1.4 差异化优势（凭什么赢——3 条核心）

**优势 1：端到端体系（L3 战略→L2 项目群→L1 实施），不是点状工具**
- 竞品止步于"写代码"这一个点。eAISEDP 覆盖从战略规划（EA/Strategy/GRC）、项目群协同（PgM/Standards/VSM）、到单项目实施（14 角色流水线）的**完整软件工程链路**。
- 商业含义：客户买的不是"让程序员快 20%"，而是"让整个交付组织可治理、可复用、可度量"。这是 CTO/CIO 关心的层级，不是程序员关心的层级——**决策者和使用者的购买动机不同，eAISEDP 卡决策者**。

**优势 2：多 Agent 协同 + 过程资产沉淀，把"一次性"变"资产"**
- 竞品的 AI 输出用完即弃（代码写了就过去了）。eAISEDP 每个角色的产出（PRD/方案/评审/测试报告）结构化入平台数据（t_artifact），全链路追溯（case→derivation→artifact），可检索可复用。
- 商业含义：用得越久，过程资产库越厚，企业越离不开（**数据护城河**）。这是 SaaS 续费率的根本驱动——客户沉淀的资产越多，流失成本越高。

**优势 3：企业已有资产零侵入适配，销售阻力最低**
- 竞品要么要求换 IDE（Cursor）、要么要求换工作流。eAISEDP 通过 7 大适配器 SPI（Git/LLM/DocStore/Ticket/CICD/IM/MCP），企业已有 GitLab/Jira/Confluence/Jenkins/钉钉**零改动**接入，只提供 token/webhook。
- 商业含义：**销售周期短**。客户不需要"换工具"这个大决策，只需"接一个平台"这个小决策。这对传统企业（决策保守、迁移敏感）是关键卖点。

## 2. 商业模式（Business Model）

> 商业模式层回答：怎么收费？卖给谁收？开源还是闭源？服务怎么算钱？

### 2.1 收费模式总览（3 种模式 + 开源策略）

eAISEDP 采用**分层收费 + 开源引流**的混合模式，覆盖从个人尝鲜到大型企业集团的三档客户（对应 EA 蓝图 §1.4 三档用户画像）：

| 模式 | 目标客户 | 收费方式 | 启用里程碑 | 预期客单价（估算） |
|---|---|---|---|---|
| **模式 A：SaaS 订阅** | 小团队（<100 人）+ 中小企业（100-1000 人） | 按 tenant 配额计费（token/case/派生/存储，t_quota 驱动）+ 按用户数分档 | M2（Web 工作台上线后）| 小团队：500-3000 元/月；中小企业：1-5 万元/月 |
| **模式 B：私有部署 License** | 大型企业（1000+ 人）+ 强合规行业（金融/政务/医疗） | 一次性 License 费（按事业部/用户数）+ 年度维护费（License 的 15-20%） | M3（协同治理 + 治理闭环后）| License：50-300 万元/套；维护：8-60 万元/年 |
| **模式 C：实施服务** | 所有私有部署客户 + 需深度定制的 SaaS 客户 | 按项目计费（适配器定制 + 体系裁剪 + 培训） | M1（已有，dogfooding 即实施服务能力证明）| 30-150 万元/项目 |
| **（底层）开源策略** | 全市场（引流 + 信任建立） | 核心体系 markdown 开源（eAISEDP-system 仓库），平台增值收费 | 持续 | 免费（引流成本） |

### 2.2 模式 A：SaaS 订阅（中小型企业主力）

**定价机制**：基于 t_quota 表（已建，EA 蓝图 §3.1）的四维配额——token（LLM 调用量）/ case（案件数）/ 派生（角色调用次数）/ 存储（artifact 体积）。

**分档定价（估算，需 M2 上线后用真实用量校准）**：

| 档位 | 月费（估算） | 包含 | 适用 |
|---|---|---|---|
| Starter（免费版）| 0 | L1 单项目实施，100 case/月，10 万 token/月，1GB 存储 | 个人/小团队尝鲜，激活 edition=starter |
| Pro | 2,000-5,000 元/月 | L2+L1，1000 case/月，100 万 token/月，10GB 存储 | 100-300 人中小企业 |
| Team | 1-5 万元/月 | L2+L1，无限 case，500 万 token/月，100GB 存储 | 300-1000 人中型企业 |
| Enterprise（SaaS 版）| 议价 | L3+L2+L1，定制配额，专属支持 | 大型企业的非核心业务上 SaaS |

**关键假设（影响定价合理性）**：
- GLM token 成本（估算）：输入约 0.5-5 元/百万 token，输出约 0.5-15 元/百万 token（按档位）。假设 Pro 档 100 万 token 月成本约 500-3000 元，售价 2000-5000 元，**毛利率约 40-75%**（中置信度，需真实账单验证）。
- 续费率假设：70-85%（行业 SaaS 中位数，eAISEDP 因过程资产沉淀，预期续费率高于中位数）。

**计费落地**：M1/M2 仅埋点不计费（DESIGN §7），t_quota 已预留配额字段；SP-7（配额强校验）M2 落地后启用计费拦截。规则留接口，未来加配置即可启用——**避免 M1 过度工程化计费**。

### 2.3 模式 B：私有部署 License（大型企业主力）

**定价机制**：License 费（一次性，按事业部数或用户数）+ 年度维护费（License 的 15-20%，含升级/补丁/远程支持）。

**License 定价（估算，参考国产企业级软件定价区间）**：

| 版本 | License 费（估算）| 年维护费 | 适用 |
|---|---|---|---|
| Enterprise 单事业部 | 50-100 万元 | 8-20 万元/年 | 大型企业单一事业部 |
| Enterprise 集团版 | 150-300 万元 | 25-60 万元/年 | 多事业部集团，不限用户数 |
| 强合规版（等保/GDPR 审计增强）| +30-50% 溢价 | +30-50% | 金融/政务/医疗 |

**关键假设**：
- 私有部署边际成本低（一套代码多次卖），License 费主要是**前期研发成本摊销 + 实施服务利润**。
- 大型企业决策周期长（6-12 个月），但单笔回款大，**是 1-3 年内的主要营收支柱**（高置信度判断）。
- 私有部署的 deploy_mode=private（EA 蓝图 §3.5），独立 MySQL，数据主权完全归客户——这是强合规行业采购的硬门槛，eAISEDP 已在架构层支持。

### 2.4 模式 C：实施服务（高利润 + 客户粘性）

**服务内容**：
- **适配器定制**：客户用 GitLab/Jira/Confluence，平台实现对应 Adapter（GitlabGitAdapter/JiraTicketAdapter/ConfluenceDocStoreAdapter），按适配器数量计费（估算 5-15 万元/个）。
- **体系裁剪**：基于本企业架构蓝图，裁剪到客户行业（金融/政务/制造），team-ea + team-strategy 出行业版蓝图（估算 20-50 万元/行业）。
- **培训与赋能**：14 角色 + 治理角色的方法论培训，教客户团队用体系（估算 5-15 万元/批次）。
- **年度陪跑**：客户首批 3-5 个项目，平台团队陪跑交付，沉淀最佳实践（估算 30-80 万元/年）。

**商业含义**：实施服务是**高利润 + 高粘性**业务——既赚服务费，又把客户深度绑定（适配器定制=技术债转移，客户换平台成本极高）。参考传统软件服务企业的业务模式，这是本企业**最擅长**的变现路径。

### 2.5 开源策略（核心体系开源，平台增值收费）

**参考 GitLab CE/EE 模式**：

| 仓库 | 开源/闭源 | 内容 | 商业目的 |
|---|---|---|---|
| `eAISEDP-system`（体系配置仓库）| **开源**（Apache 2.0 或类似）| 22 角色 markdown + 26 skills + 4 commands + 编排方法论 | 建立标准、引流、社区贡献角色/skill。体系是方法论，开源建立行业影响力 |
| `eAISEDP`（后端平台）| **核心闭源，部分模块开源** | 核心闭源：runtime/capability/data（派生引擎、热加载、多租户）。可选开源：common/adapter 默认实现 | 平台增值能力闭源收费，基础适配器开源降低接入门槛 |
| `eAISEDP-web`（前端）| 闭源 | Web 工作台 | 平台产品化部分闭源 |

**开源策略的商业逻辑**：
- **体系开源**建立"行业标准"心智——当企业谈"AI 软件工程体系"时引用 eAISEDP 的角色/铁律定义，就是护城河。
- **平台闭源**保证变现——体系免费引流，平台承载体系运作并收费。
- **风险**：竞品 fork 体系自己做平台。缓解：平台 + 实施服务 + 过程资产沉淀构成完整壁垒，单 fork 体系无法复制。

## 3. ROI 测算（Return on Investment）

> ROI 层回答：投多少？赚多少？多久回本？所有数字是估算，标注假设与置信区间。

### 3.1 投入侧（成本估算）

**投入构成**：M1-M4 总工时（基于 EA 蓝图 §5 演进路线 + PgM 7 子项目 SP-1~SP-7）× 团队成本 + 基础设施 + LLM 费用 + 机会成本。

**团队成本假设**：
- 全栈工程师综合成本（含五险一金/管理摊销）：估算 **15,000-25,000 元/人月**（二三线城市传统软件服务企业口径，中置信度）。
- 设核心团队 5-8 人（架构师 1 + 后端 3-4 + 前端 1-2 + QA 0.5-1 + 产品 0.5）。

**工时估算（基于 EA 蓝图 §5 + §9 子项目）**：

| 里程碑 | 子项目 | 工时估算（人天）| 折合人月 | 团队成本（万元，估算）| 置信度 |
|---|---|---|---|---|---|
| **M1（已完成）** | 9 模块骨架 + 8 表 + DerivationEngine + GLM + 热加载 | 已投入约 1-2 人月 | 1-2 | 3-5 | 高（已发生）|
| **M2 核心闭环** | SP-1 Web 工作台 + SP-2 auth + SP-3 状态机 + SP-4 资产结构化 + SP-5 档位激活 + SP-6 模型路由 + SP-7 配额校验 | 148-234 人天（EA §5.3 + PgM 拆解）| 7-12 | 10-30 | 中（范围大，取决于 jQuery 前端工作量）|
| **M3 协同治理** | SP-8~SP-13（项目群/可观测/GRC/检索/适配器/微服务评估）| 200-400 人天 | 10-20 | 15-50 | 低（微服务拆分不确定性高）|
| **M4 生态扩展** | 适配器全覆盖 + CICD + MCP + IDE 插件 + 多 LLM 灰度 + K8s | 300-600 人天 | 15-30 | 22-75 | 低（远期，范围模糊）|
| **M1-M4 研发总投入** | | | **33-64 人月** | **50-160 万元** | 中 |

### 3.2 回报侧（收益估算）

**双轨收益**（eAISEDP 的独特性：既对内降本，又对外增收）：

#### 对内价值（本企业自己用它交付项目）

| 收益项 | 估算逻辑 | 年节省/增收（万元）| 置信度 |
|---|---|---|---|

### 3.3 ROI 指标计算（盈亏平衡分析）

**基于上述估算，构建三种情景**（保守/中性/乐观）：

| 指标 | 保守情景 | 中性情景（推荐基准）| 乐观情景 |
|---|---|---|---|
| M1-M4 总投入 | 250 万元 | 165 万元 | 80 万元 |
| 年化总收益（对内+对外，稳态）| 200 万元 | 550 万元 | 1200 万元 |
| **投资回报率（年化，稳态）** | 80%/年 | 333%/年 | 1400%/年 |
| **回收期** | 约 1.5 年（含建设期约 2.5-3 年）| 约 6-9 个月（含建设期约 1.5-2 年）| 约 3 个月（含建设期约 1-1.5 年）|
| **3 年累计净收益** | 约 350 万元 | 约 1485 万元 | 约 3520 万元 |
| **3 年 NPV（折现率 10%）** | 约 210 万元 | 约 1080 万元 | 约 2620 万元 |
| **置信度** | 高（最坏情况也能回本）| 中（合理基准）| 低（需多个假设同时兑现）|

**关键结论**：
1. **即便保守情景，eAISEDP 也能在 3 年内回本并盈利**——核心原因是"对内降本"这条腿不依赖外部市场，本企业自己用就能产生 140-750 万/年收益。这是**最抗风险的底盘**。
2. **中性情景下 ROI 约 333%，回收期约 1.5-2 年**——对战略投资项目属于优秀水平。
3. **乐观情景的高额回报依赖 License + 实施服务的企业级销售突破**，不确定性高，不应作为决策基准。

**反方观点（诚实声明——为什么不支持推进）**：
- **提效假设可能高估**：AI 编程行业宣称的 20-40% 提效多基于简单代码，eAISEDP 覆盖完整流程，实际端到端提效可能只有 10-20%。若提效仅 10%，对内收益腰斩。
- **SaaS 获客极难**：企业级 SaaS 新品牌获客成本高，第 1 年可能远低于预期。不能把 SaaS 营收当确定性收入。
- **License 周期长**：大型企业采购决策 6-12 个月，M3（2026-Q4）后才有产品，License 营收可能 2027 下半年才规模化。
- **团队机会成本**：5-8 人核心团队 1.5-2 年投入，若同期做传统交付项目，机会成本约 200-500 万元（按每人月创收 3-8 万元计）。

**综合结论**：**建议推进**。保守情景下仍能回本（对内价值托底），中性情景 ROI 优秀。最大不确定性在对外营收，但即便对外为零，对内降本也能在 2-3 年覆盖投入。建议**分阶段投入**（见 §5 投资节奏），不一次性 all-in。

### 3.4 敏感性分析（关键假设波动对 ROI 的影响）

对中性情景做单变量敏感性（其他条件不变）：

| 变量 | 基准值 | 波动 | 对 3 年 NPV 影响 |
|---|---|---|---|
| AI 提效幅度 | 20% | ±5%（即 15%-25%）| ±180 万元（高敏感）|
| 团队综合成本 | 2 万元/人月 | ±0.5 万 | ±50 万元（中敏感）|
| SaaS 客户数（第 2 年）| 100 家 | ±50 家 | ±120 万元（中敏感）|
| License 客单价 | 100 万 | ±50 万 | ±100 万元（中敏感）|
| LLM token 成本 | 估算基准 | 翻倍 | -30 万元（低敏感，已有 cost-governance 兜底）|

**最敏感变量**：AI 提效幅度。这是整个商业案例的命门——**M2 上线后必须用真实 case 数据验证提效**，若实测低于 15%，需重新评估对外扩张节奏。

### 4.6 技术雷达治理规则

- **Adopt 项**：team-standards 写入 CLAUDE.md 作为默认技术选型，新项目强制遵循。
- **Trial 项**：允许在非关键路径试用，试用结果反馈给 team-strategy + team-ea，决定转 Adopt 或降级。
- **Assess 项**：禁止生产采用，仅允许 POC/调研，由 team-ea 牵头评估。
- **Hold 项**：禁用，除非触发条件满足并经新 ADR 裁决解除。

**节奏原则**：对内降本类先行（托底收益），对外可售类紧跟（打开增长），治理类穿插（控风险）。**绝不一次性投入 M1-M4 全部预算**，按里程碑 gate 评审，达标才放下一笔。

```

├── 第 2-3 月：SP-3（状态机）+ SP-5（档位激活）并行
├── 第 3-4 月：SP-1（Web 工作台）—— SaaS 销售入口，集中投入前端

M3（2026-Q4，协同治理）投入条件：
├── 前提：M2 Gate 通过 + SaaS 至少 5 家付费租户（验证市场）
├── SP-8（项目群协同）+ SP-9（可观测）—— 大型企业 License 卖点
├── SP-10（GRC 审计链）—— 强合规行业（金融/政务）License 卖点
├── SP-11（检索）+ SP-12（新适配器）—— 增强竞争力
└── SP-13（微服务拆分评估）—— 仅评估，不强制拆

M4（2027+，生态扩展）投入条件：
├── 前提：M3 营收达标（License 至少 2 单）+ 团队规模扩展
└── 按客户需求驱动投入（哪个适配器有客户买单先做哪个）
```

### 5.4 投资优先级核心结论

1. **SP-6（模型路由配置化）是最佳速赢项**——低成本（迁移配置）、高价值（立即降 token 成本 + 解 P8 技术债 + 为多供应商铺路），**建议在 M2 第 1 月与 SP-2 并行投入**。
2. **SP-1（Web 工作台）是 SaaS 变现的命门**——无 Web 工作台就无法卖 SaaS，是 M2 投资重心，但前端工作量风险高，需重点保障。
3. **SP-2/SP-3 是商用底线**——auth（多租户隔离）+ 状态机（可靠性），缺一则平台不可商用。
4. **SP-13（微服务拆分）严格 Hold**——遵循 ADR-001 §5.3，不达触发条件不投入，避免过度工程化烧钱。

## 6. 风险评估（Risk Assessment，商业层）

> 商业风险评估层回答：哪些风险会让投资打水漂？怎么缓解？区别于 EA 蓝图 §5.6 的技术风险（面向 team-dev），本节是商业层风险（面向决策层）。

### 6.1 风险矩阵总览

| 风险类别 | 风险项 | 概率 | 影响 | 综合等级 | 缓解措施 |
|---|---|---|---|---|---|
| **技术** | AI 能力上限（复杂任务 LLM 做不好）| 高 | 高 | **极高** | 人机边界（AI 主导分析，人掌握资源终决）；14 角色流水线拆解降低单步复杂度；reliability-governance 兜底校验 |
| **技术** | LLM 成本失控 | 中 | 高 | 高 | cost-governance（token 预算/计量/降级）+ SP-6 模型路由档位（贵任务用贵模型，简单任务用便宜模型）+ SP-7 配额强校验 |
| **技术** | 微服务拆分过早烧钱 | 低 | 高 | 中 | ADR-001 §5.3 严格 gate，技术雷达 Hold 微服务全拆 |
| **市场** | 竞品碾压（Copilot/Cursor 下沉企业级）| 中 | 极高 | **极高** | 差异化（体系 vs 工具）；适配器零侵入护城河；过程资产沉淀锁定客户；开源体系建标准 |

| **市场** | 大厂自建（大型企业倾向自研平台）| 中 | 中 | 中 | 卖 License + 实施服务给自建企业做底座；强调"体系方法论"比"平台代码"更稀缺 |
| **合规** | 数据安全（多租户泄露/客户数据出域）| 低 | 极高 | 高 | P11 多租户隔离铁律 + MyBatis-Plus 拦截器 + 渗透测试 + GRC 审计；私有部署（数据主权归客户）满足强合规 |
| **合规** | AI 生成内容合规（代码版权/生成内容责任）| 中 | 高 | 高 | artifact 全链路追溯（产出可审计）；人工检查点（关键产出人审）；合规法务审查开源协议与客户合同 |
| **合规** | 等保/行业合规（金融/政务准入）| 中 | 中 | 中 | GRC 审计链（SP-10）+ 强合规版溢价产品 + 等保测评投入 |
| **运营** | 团队机会成本（核心团队被占用）| 中 | 中 | 中 | 分阶段投入（不全员 all-in）；dogfooding 本身产生交付收益对冲机会成本 |
| **运营** | dogfooding 失败（体系造平台跑不通）| 低 | 极高 | 高 | M1 已部分验证（capability 热加载 + DerivationEngine 端到端跑通）；M2 Gate 评审验证全链路 |

### 6.2 三大最大商业风险（详述）

**风险 1：AI 能力上限（综合等级：极高）**
- **场景**：复杂软件工程任务（架构设计/复杂业务逻辑/跨系统调试）LLM 当前能力不足，导致 14 角色流水线产出质量差，过程资产不可用，平台沦为"演示能跑、生产不敢用"。
- **影响**：对内提效假设（15-30%）无法兑现 → 对内收益腰斩；对外客户用后失望 → 续费率崩塌。
- **缓解**：①人机边界设计（AI 主导分析产出草案，人掌握终决权，关键检查点人工锁）；②角色流水线拆解（把复杂任务拆成小步，降低单步 AI 负担）；③reliability-governance（不可逆操作人工锁 + 输出兜底校验 + 全链路可回滚）；④诚实标注能力边界（不宣称"全自动"，宣称"AI 辅助 + 人工治理"）。
- **残余风险**：仍高。AI 能力是外部变量，eAISEDP 只能适配不能控制。

**风险 2：竞品碾压 + 客户不买单（综合等级：极高）**
- **场景**：GitHub Copilot/Cursor 下沉做企业级治理版，或国产大厂（阿里/百度/字节）推免费企业版，挤压 eAISEDP 生存空间；同时 SaaS 新品牌获客难，License 周期长，对外营收远低于预期。
- **影响**：对外营收（SaaS + License）三条腿可能断两条，只剩实施服务。
- **缓解**：①对内降本托底（即便对外为零，本企业自用 140-750 万/年收益也能覆盖 80-250 万投入，2-3 年回本）；②实施服务先行（本企业最擅长，M1 起即能产生现金流，不等 SaaS 规模化）；③差异化卡位（体系 vs 工具，竞品短期难补齐 L3→L2→L1 完整方法论 + 过程资产沉淀）；④分阶段投入（M3 预算需 SaaS 至少 5 家付费租户验证才放行，不盲目扩张）。
- **残余风险**：中。对内价值是底盘，但增长天花板取决于市场竞争。

**风险 3：数据安全与合规（综合等级：高，概率低但影响极高）**
- **场景**：多租户 SaaS 模式下租户数据泄露（tenant_id 隔离漏洞）；或客户私有部署后 AI 生成内容涉及版权/合规问题（如生成代码抄袭开源 GPL）。
- **影响**：数据泄露是商用致命风险（信誉崩塌 + 法律责任 + 监管处罚）；版权问题影响客户采购决策。
- **缓解**：①P11 多租户隔离铁律（MyBatis-Plus 拦截器自动注入 tenant_id，禁止手写不带 tenant_id 的 SQL）；②渗透测试（M2 验收标准含跨租户数据不可见测试）；③私有部署优先强合规客户（数据主权完全归客户，规避 SaaS 数据持有风险）；④artifact 全链路追溯（AI 产出可审计）+ 人工检查点（关键产出人审）；⑤合规法务审查（开源协议/客户合同/AI 生成内容免责条款）。
- **残余风险**：低（架构层已强隔离），但需持续审计。

### 6.3 风险应对总策略

1. **对内价值托底**：无论外部市场如何，本企业自用 eAISEDP 交付项目即产生收益。这是整个商业案例的抗风险底盘，确保最坏情况也能回本。
2. **分阶段 gate 评审**：M2→M3 需"SaaS 至少 5 家付费租户"验证，M3→M4 需"License 至少 2 单"验证。不达标不追加投资，止损可控。
3. **实施服务先行**：不等 SaaS/License 规模化，M1 起即用 dogfooding 能力接定制项目，快速产生现金流。
4. **差异化避正面竞争**：不打"Copilot 替代品"的仗（必输），打"企业级体系平台"的仗（竞品短期难补齐）。

## 7. 决策建议（给决策层的结论）

### 7.1 总体结论：建议推进（分阶段，不 all-in）

**建议推进的依据**：
1. **保守情景仍能回本**：即便对外营收为零，对内降本（140-750 万/年）也能在 2-3 年覆盖 80-250 万投入。
2. **中性情景 ROI 优秀**：333% 年化 ROI，回收期 1.5-2 年，3 年 NPV 约 1080 万元。
3. **战略价值**：传统软件服务企业向 AI 工程体系转型，eAISEDP 是载体，不建平台则转型无抓手。
4. **抗风险底盘**：对内价值 + 实施服务 + dogfooding，三重保障，不依赖单一变现路径。

**分阶段投入的建议（不 all-in）**：
- M2（核心闭环）：投入约 30-50 万元（10-30 万研发 + 其他），目标是 Web 工作台 + 多租户闭环可用。
- M3 gate：M2 达标（Web 端到端跑通 + SaaS 5 家付费租户）才放行 M3 预算。
- M4 gate：M3 达标（License 2 单 + 实施服务现金流）才放行 M4 预算。
- **任何阶段不达标即止损**，最大暴露损失约 M2 投入（30-50 万）。

## 本次经验沉淀

1. **商业策略必须基于 EA 蓝图，不能凭行业通识编造数字**。本次 ROI 投入侧的 M1-M4 工时直接引用 EA §5 + §9 的子项目拆解（148-234 人天），回报侧的对内价值源自 DESIGN §8 dogfooding（本企业自用），对外价值源自 EA §6 三档用户收费模型。每个数字都能追溯到架构资产的某个具体结论。教训：战略分析师的价值不是"会算 ROI"，而是"能把架构能力翻译成商业价值"——脱离架构谈商业就是空中楼阁。

2. **ROI 测算必须双轨（对内+对外）+ 含反方观点**。传统软件服务企业做平台最大的商业特点是"自己用 + 对外卖"双轨。对内价值（本企业用它交付项目降本）是抗风险底盘，即便对外营收为零也能回本——这是说服保守决策层推进的关键论据。同时必须主动列反方观点（提效假设可能高估、SaaS 获客难、License 周期长、机会成本），不能只说好处。教训：诚实的商业案例比美化的商业案例更有说服力，决策层更信任标注了不确定性的估算。

3. **技术雷达要从 EA 已确认技术栈生长，不是另起炉灶**。本次 Adopt 项完全来自 EA 蓝图 §4.1 技术栈确认表，Trial/Assess/Hold 项来自 EA 在 §4.3（LangChain4j 版本冲突）、ADR-001 §5.3（微服务 Hold）中的明确判断。战略分析师不自己评估技术（那是 EA 的职责），而是把 EA 的技术判断"分级化"（Adopt/Trial/Assess/Hold）并给出演进触发条件，供 team-standards 写入门禁。教训：L3 战略层与 L3 架构层协同的关键是"职责不重叠"——EA 判断技术合理性，Strategy 判断技术投资节奏。

4. **投资优先级要区分"技术依赖视角"和"商业投资视角"**。EA 的 P0/P1/P2（SP-1~SP-7 优先级）是从技术依赖排的（谁依赖谁），但商业投资视角可能不同——例如 SP-6（模型路由配置化）在 EA 视角是 P1，但商业视角是"速赢项"（低成本立即降 token 成本），应提前投入。教训：同一个子项目，技术优先级和商业优先级可能不同，PgM 排资源时应综合两方视角，而 Strategy 的职责是补充商业视角这一维度。
