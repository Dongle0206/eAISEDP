## 1. 背景与目标

### 1.1 业务背景

PRJ-002 已交付三层贯通骨架：战略→项目群→项目→Case 四级模型、下行约束注入（架构原则+门禁规则进每次编排）、上行进度汇总（Case done 自动重算项目进度）、分层独立开关。但骨架只是"管道"，L2 治理的深度功能仍然缺位，这正是 PRJ-002 PRD 范围外清单 #3/#4/#5/#6 所指、PRG-001 规划的 PRJ-003/PRJ-004 内容：

- **效能靠感觉**：项目群经理无法回答"我们团队交付效率是升是降"，没有任何量化看板；DORA 四指标（部署频率/变更前置时间/变更失败率/恢复时间）是业界共识的交付效能度量，但平台数据（派生记录、审计、Case 生命周期）从未被组织成指标。
- **里程碑是死表**：t_milestone 在 V1 建表后无页面、无 API、无数据（且以旧 VARCHAR program_id 弱关联，与新三层模型错位）；项目群经理的里程碑管理仍靠人肉。
- **跨项目依赖靠脑子**：项目 A 等项目 B 的接口才能联调，这类信息没有任何系统承载，项目群协调会上反复口头同步；依赖成环更是要到排期撞车才暴露。
- **架构决策散落**：ADR（架构决策记录）散落在 markdown/聊天记录里，新成员查不到"当年为什么这么定"；ADR 变更了架构原则时无人知道要同步原则库。
- **技术选型无统一视图**：哪些技术该用（adopt）、该试（trial）、该观望（assess）、该停用（hold），没有技术雷达，各项目重复踩坑。

本期 Case 交付上述五块（PRJ-003 主体 + PRJ-004 中数据模型轻、与架构原则联动价值高的 ADR/雷达两项拆分提前；PRJ-003 的标准库/数据治理与 PRJ-004 的 GRC/投资决策分析仍留原项目，见 §7）。

### 1.2 业务目标与成功指标

| 目标 | 衡量指标 | 验收口径 |
|---|---|---|
| 效能可量化 | DORA 四指标按项目/项目群维度可查，口径可从现有数据计算（恢复时间含一处微型埋点） | AC-F1.1~F1.6 |
| 口径透明可信 | 每指标展示样本数；不可精确回溯的历史数据有"近似/不完整"标注，不冒充精确值 | AC-F1.5 |
| 里程碑死表激活 | 项目群/项目两级里程碑 CRUD+状态+达成日期；项目进度页时间线 | AC-F2.1~F2.3/F2.6 |
| 达成由人确认 | 项目全部 Case done 时提示可达成，**不自动置达成**（可靠性治理：状态变更人责） | AC-F2.4/F2.5 |
| 依赖可视且无环 | 依赖 CRUD+blocked 判定+循环依赖创建即拒 | AC-F3.1~F3.5 |
| 决策可追溯 | ADR 五段式 CRUD+状态机+原则联动提示 | AC-F4.1~F4.4 |
| 技术有共识视图 | 技术项 CRUD+四象限可视化+环变更留痕 | AC-F5.1~F5.4 |
| 分层语义正确 | L2 关：DORA/里程碑/依赖降级隐藏；ADR/雷达不受任何层开关影响 | AC-SWITCH.1~SWITCH.3 |
| 多租户与权限 | 五类新数据全隔离；编辑权分级、审计全覆盖 | AC-ISO / AC-RBAC |

### 1.3 功能层级归属结论（ADR/雷达不限层的评估，强制）

判定方法：**按"治理对象是什么"归类，而非功能出现在哪个菜单**。

| 功能 | 治理对象 | 归属结论 | 依据 |
|---|---|---|---|
| DORA 看板 | 项目/项目群的交付效能 | **L2**：受 `program_project_enabled` 约束 | 指标维度=项目（project_id）；无项目关联的 Case 不计入；L2 关闭即无统计对象 |
| 里程碑 | 项目群/项目的关键节点 | **L2**：受 `program_project_enabled` 约束 | API 挂 programs/projects 前缀，天然被 LayerGuard 43002 覆盖 |
| 跨项目依赖 | 项目间关系 | **L2**：受 `program_project_enabled` 约束 | 同上（新前缀需注册，见 Q2） |
| **ADR 库** | **企业架构决策（知识资产）** | **不限层**：不挂 LayerGuard 拦截，不随任何层开关隐藏 | 与架构原则同域。**关键先例**：PRJ-002 SE 裁决"原则/门禁是 L1 治理配置（关 L2 的场景B 客户仍需门禁）"，LayerGuardInterceptor 注释明确不拦原则/门禁接口。同理：只用 L1 的轻量客户（场景C）同样有架构决策要记录；把 ADR 挂到 L2/L3 开关下违背 P13"上层存在不得成为下层运行的前置条件" |
| **技术雷达** | **企业技术选型共识（知识资产）** | **不限层**：同 ADR | 轻量客户（场景C）仅跑 Case 也会做技术选型；雷达与战略层（L3）无数据依赖（不关联战略/项目群/项目任何实体） |

结论：ADR 库与技术雷达作为**租户级治理知识资产**，独立菜单入口，任何层开关组合下均完整可用（AC-SWITCH.2）。

## 2. 用户故事（INVEST 原则）

### US-1 项目群经理（PgM，tenant_admin 兼任，同 PRJ-002 Q4 先例）

- 作为「项目群经理」，我希望「打开 DORA 看板就能看到群下各项目的部署频率/前置时间/失败率/恢复时间和趋势分档」，以便「效能复盘不再靠感觉，改进有基线可对比」。
- 作为「项目群经理」，我希望「给项目群和项目两级登记里程碑（标题/计划日期/负责人），在项目进度页看到里程碑时间线，谁逾期一目了然」，以便「跨项目节点协调不再靠口头同步」。
- 作为「项目群经理」，我希望「登记项目 A 依赖项目 B，看板自动标出哪些项目因上游未交付被阻塞，新建依赖若成环立即被拒绝」， 以便「排期冲突在登记时就暴露，而不是联调时撞车」。

### US-2 项目经理（project_manager 角色）

- 作为「项目经理」，我希望「给我负责的项目创建里程碑并维护其状态（planned/achieved/delayed）与达成日期」，以便「项目节奏对项目群透明」。
- 作为「项目经理」，我希望「项目下全部 Case 完成时，页面提示我'可达成里程碑'并让我人工确认（而不是系统自动达成）」，以便「交付确认的责任在人，系统只做提醒」。
- 作为「项目经理」，我希望「查看我项目的 DORA 指标并知道样本数与口径」，以便「向项目群汇报时数据有依据、不夸大」。

### US-3 企业架构师（EA，本期由 tenant_admin 兼任，见开放问题 Q5）

- 作为「企业架构师」，我希望「用五段式（编号/上下文/决策/后果/关联原则）记录每个架构决策，并用状态（proposed/accepted/deprecated/superseded）管理其生命周期」，以便「任何架构决策可追溯、可交接」。
- 作为「企业架构师」，我希望「一个 ADR 废弃或被取代且它关联了某架构原则时，系统提示我检查原则内容是否需要同步」，以便「决策库与原则库不打架」。

### US-4 技术委员会/技术负责人

- 作为「技术负责人」，我希望「把技术项登记到雷达（象限 techniques/tools/platforms/languages + 环 adopt/trial/assess/hold + 理由 + 评审日期），并在四象限图上一眼看全公司技术共识」，以便「新项目选型有依据，危险技术（hold）人人可见」。
- 作为「技术负责人」，我希望「环移动（如 trial→adopt）留下审计记录，评审日期过久的技术被标'待复审'」， 以便「雷达是活文档不是一次性墙纸」。

### US-5 高管（executive 角色）

- 作为「高管」，我希望「只读查看项目群 DORA 看板、里程碑时间线与依赖阻塞情况」，以便「战略执行的健康度有量化视图，不用层层要报表」。

### US-6 实施顾问（交付 eAISEDP 的售前/实施人员）

- 作为「实施顾问」，我希望「给只用 L1 的轻量客户（场景C，关 L2+L3）开通平台后，ADR 库和技术雷达仍然可用」， 以便「轻量客户也能治理自己的架构决策与技术选型，后续深化使用时有存量知识资产」。

**INVEST 自检**：每个故事独立可验收（对应 §5 各 AC）；可协商（页面形态可由 UX 调整，口径/状态机/环检测语义不可）；对六类角色各自有价值；规模适合单 story；可测（AC 全部 Given-When-Then 且含构造数值）；时间 box 在本 Case 内。

## 4. 功能需求详述

> **数据基线**：t_case（V1，project_id 由 V4 增列）/ t_derivation（V1）/ t_governance_log（V1）/ t_orchestration.steps_json（V1/V2）/ t_milestone（V1 死表）均为既有资产；**本期新增数据需求三处**：① t_derivation 增 gate_result 埋点列（F1 恢复时间精确化）；② t_milestone 激活增列（F2）；③ t_project_dependency / t_adr / t_tech_radar_item 三张新表（F3/F4/F5）——均由 SE 落 V5 迁移，本 PRD 只约束语义。

### 4.1 F1 DORA 效能看板

#### 4.1.1 数据源盘点（口径可计算性的依据，QA 构造数据照此）

| 数据源 | 关键字段 | 已核实的事实 |
|---|---|---|
| t_governance_log | action、resource_type、resource_id、detail(JSON)、create_time | `case_transit` 是 t_case 状态**唯一写路径**的留痕：`POST /api/v1/cases/{caseId}/transit`（CaseStateController）每次流转成功后写一条，detail 含 `{"targetStatus":"done","operator":...}`；CaseStatus 状态机保证 done 只能由 deploying 流转而来（无需 from_status 埋点）。注意：幂等重放（已是 done 再 transit done）也会写审计，**统计须按 Case 去重取最早一条** |
| t_case | project_id、status、create_time | create_time 即 Case 创建时刻（变更前置时间起点）；project_id 关联项目 |
| t_orchestration | case_id、status(pending/running/awaiting_approval/done/failed)、steps_json、created_at/finished_at | steps_json 内每个步骤含 role/status(pending/running/success/failed/skipped)/**gateResult(PASS/FAIL/FAIL_WARN)**/gateReason/rerunCount/gateRuleId/gateStage/startedAt/finishedAt；**步骤重跑会覆盖该步骤时间戳，中间次 FAIL 时间不可从 steps_json 复原** |
| t_derivation | case_id、role、status、retry_count、started_at/finished_at/duration_ms | 每次 LLM 调用一行（门禁打回重做产生同 case_id+role 的**多条**记录，时间可差分）；**status 记录 LLM 调用成败，不记录 GATE 判定**（判定解析在编排层）——这是恢复时间需补埋点的根因 |

#### 4.1.2 四指标口径定义（唯一权威，前端文案与 QA 断言照此）

**通用**：统计维度=项目（必选过滤：单项目 / 项目群聚合=成员项目合并 / 全部项目）；统计周期默认近 30 天，可切 7/30/90 天；**未关联项目（project_id 为空）的 Case 不计入任何维度**（L1-only Case 不属于 L2 效能）；每指标卡必须展示样本数 N。

**① 部署频率（Deployment Frequency, DF）**
- 口径：周期内该项目平均**每日**完成 deploying→done 流转的 Case 数。
- 公式：`DF = 周期内首次流转至 done 的 Case 数（按 Case 去重） / 周期自然日天数`（周期内无数据的天计 0，不剔除）。
- 数据源：t_governance_log（action='case_transit' 且 detail.targetStatus='done'）的 create_time，按 resource_id=case_id 关联 t_case.project_id；同 Case 多条 done 记录取最早一条。
- 可计算性：**现有数据完全可算**。

**② 变更前置时间（Lead Time for Changes, LT）**
- 口径：Case 从创建到完成（done）的时长分布，按项目取 **P50 与 P90**（长尾分布不用均值）。
- 公式：`LT(case) = done 流转时间戳 − t_case.create_time`；项目 LT = 该周期内 done Case 的 LT 分位数（P50/P90）；展示单位自适应（<24h 显示小时，否则显示天）。
- 数据源：同①的 done 时间戳减 t_case.create_time。
- 可计算性：**现有数据可算**；风险标注：升级部署前已 done 且无对应 case_transit 审计记录的历史 Case，**排除出统计**（不得用 t_case.update_time 冒充精确值——update_time 会被任何更新改写），看板显示"样本 N（另有 M 条历史数据不可回溯，已排除）"。

**③ 变更失败率（Change Failure Rate, CFR）** —— 代理指标，必须明示
- 口径：周期内该项目**终态编排 Case** 中，出现"质量门禁终判失败"的占比。
- 公式：`CFR = 门禁终判失败 Case 数 / 终态编排 Case 数`。
  - 分子：t_orchestration.steps_json 中存在 `status='failed' 且 gateResult='FAIL'` 步骤的 Case（含 llm_review 终判超限与 auto_check 的 block 阻断，二者即为编排层定义的"终判"，见 OrchestrationService finalFailedGateInRange）；
  - 分母：t_orchestration.status ∈ {done, failed} 且其 case 归属该项目的 Case 数（按 Case 去重）。
- 语义边界（写进看板 tooltip）：业界 DORA 原义是"引发生产故障/回滚的变更比例"；平台暂无生产故障回流数据，以**门禁终判失败作为交付质量的前置近似（代理指标）**；FAIL_WARN（warn 放行）不计入失败；打回重做后最终通过的不计入失败，其规模另以"门禁打回率"参考值展示（打回过且最终 PASS 的 Case / 终态 Case，非四指标之一）。
- 可计算性：**现有数据完全可算**（steps_json 解析）。

**④ 恢复时间（Time to Restore, RT）** —— 含一处微型埋点
- 口径：门禁 FAIL 打回到该门禁最终 PASS 的时长（Case×门禁步骤粒度），项目维度取 P50/均值。
- 公式：`RT(case, gate) = 最终 PASS 派生记录的 finished_at − 首次 FAIL 派生记录的 finished_at`；仅统计"发生过打回且最终通过"的样本；终判失败 Case 无恢复，不计入。
- **需补充埋点（本 Case 交付物，P0）**：t_derivation 新增 `gate_result` 列（PASS/FAIL/FAIL_WARN/NULL），在编排层门禁判定解析处（parseGateResult 之后）随派生记录写入——一处写入即可精确区分每个派生记录的判定。
- 埋点前历史数据的回溯近似口径（必须标注"近似"）：同 case_id+同 gate 角色 存在多条派生记录时，取首条 started_at 至末条 finished_at——该口径把打回间隙的等待时间也计入，**系统性偏大**，看板对近似样本加"≈"角标。
- 可计算性：埋点后完全可算；埋点前近似可算。

**业界分档（展示参考，数据来自 Google DORA 研究，非验收断言项）**：

| 指标 | 精英 | 高 | 中 | 低 |
|---|---|---|---|---|
| 部署频率 | 按需多次/天 | 天~周 | 周~月 | 月~半年 |
| 变更前置时间 | <1 天 | 1 天~1 周 | 1 周~1 月 | >1 月 |
| 变更失败率 | <15% | 16%~30% | 16%~30% | >30% |
| 恢复时间 | <1 小时 | <1 天 | <1 天 | >1 天 |

### 4.2 F2 里程碑激活

**现状**：t_milestone 为 V1 死表——无页面、无 API、无数据；且以旧 VARCHAR `program_id` 弱关联（与 V4 新 t_program BIGINT id 错位），status 默认值 not_started 与本期状态词汇表不符。

**激活语义（数据模型约束，具体列形态由 SE 定，见 Q3）**：

1. **两级归属**：每条里程碑归属一个**项目群**或一个**项目**（归属维度+归属 ID，二选一非空）。旧 `program_id`(VARCHAR)/`milestone_id`(VARCHAR) 列保留只读不写（同 t_case legacy 字段 PRJ-002 Q6 先例）；新增用户可见编号（如 MS-0001，租户内唯一）。
2. **字段**：标题（必填 ≤200）、描述、计划日期 target_date、负责人、状态、达成日期 achieved_date、阻塞说明（复用 V1 既有 blocker 列：该里程碑当前阻塞原因，人工填写）。项目群级里程碑可选填"涉及项目"多选（复用 V1 subprojects 列语义，仅展示，不参与自动判定）；V1 `integration_points` 列保留不启用。
3. **状态机**：`planned → achieved`（人工确认达成，必填达成日期=当天，可修改）；`planned → delayed`（人工标记，或系统在"计划日期已过且未达成"时给出一键标记入口）；`delayed → achieved`（逾期后达成，达成日期必填）；`achieved → planned`（撤销误确认，清空达成日期，留审计）。**系统永不自动置 achieved/delayed**——逾期仅自动展示"逾期"高亮提示（计划日期 < 今天 且 status=planned），状态变更一律人工（对齐 PRJ-002"进度 100% 不自动 delivered"的可靠性治理语义；里程碑自动达成 AI 属范围外）。
4. **项目进度页时间线**：项目详情页新增里程碑时间线区块——按计划日期排序的横向时间线，状态色：planned 蓝 / achieved 绿 / delayed 红，逾期未标记（planned 且过期）加黄色"逾期"角标；点击里程碑进详情/编辑。
5. **项目群聚合时间线**：项目群详情页展示群直属里程碑 + 群下项目里程碑合并时间线（按日期排序，标签区分层级）。
6. **上行达成提示（人工确认）**：当项目满足 `case_total > 0 且 case_done = case_total`（全部未删除 Case 均 done，数据来自 PRJ-002 F8 汇总字段）且该项目存在 status=planned 的里程碑时 → 项目详情页顶部出现提示条"项目全部 Case 已完成，可达成里程碑 X"，点击进入"确认达成"（填达成日期，默认当天）；不满足条件时不出现提示条。**提示是唯一联动，确认永远人工**。
7. CRUD 与审计：增删改+状态流转全部进 t_governance_log；删除为逻辑删；达成日期仅在 achieved/delayed→achieved 状态下有值。
8. **L2 降级**：API 挂 `/api/v1/programs/**` 与 `/api/v1/projects/**` 前缀（天然被 LayerGuard 43002 覆盖）；关闭时项目详情页时间线区块随 L2 菜单一并隐藏，数据保留。

### 4.3 F3 跨项目依赖

**新表 t_project_dependency**（本期新增，V5 迁移）：tenant_id、from_project_id（依赖方）、to_project_id（被依赖方）、dependency_type、备注、创建/更新审计字段、逻辑删；同一对项目同类型依赖唯一（防重复登记）；from≠to（禁止自依赖）。

1. **依赖类型语义（关键，防 Dev 混淆）**：
   - `depends_on`：A 依赖 B——B 未交付则 A 进度受阻（**强依赖，计入 blocked 判定**）；
   - `blocks`：A 阻塞 B——语义等价于 B depends_on A；**存储规范向：一律存"依赖方→被依赖方"**，登记界面提供"A 阻塞 B"快捷录入时自动换向存为 from=B,to=A（列表统一依赖方视角，避免双向语义并存）；blocks 与 depends_on 在 blocked 判定上等价（均强依赖），仅文案区分（"硬阻塞"/"受阻"）；
   - `relates_to`：A 与 B 相关（弱关联，**不计入 blocked 判定，不参与环检测**）。
2. **blocked 判定（看板核心）**：项目 P 的任一强依赖（blocks/depends_on）指向的项目 status ∉ {delivered, closed}（delivered=已交付、closed=已完结，均视为解除阻塞）→ P 标记 blocked，并列出阻塞来源链（"P 被 Q 阻塞：Q 未交付"）；被依赖项目交付后 blocked 自动解除（展示层实时判定，不落库）。
3. **循环依赖检测（P3 治理落地）**：新建/编辑时实时检测——在既有强依赖图（blocks/depends_on 边）上从 to 出发 DFS 能否回到 from，能则拒绝创建并返回成环路径（400 业务错误，提示"A→B→C→A 成环，禁止登记"）；依赖看板提供"全图体检"入口，列出当前全部成环链路（正常情况下应为空，历史脏数据可见可治）。relates_to 边不参与检测。
4. **依赖看板**：以项目卡片/列表呈现——每项目显示"依赖谁（等待项）"“被谁依赖（责任项）"两组 + blocked 徽标；筛选"仅看被阻塞项目"；点击穿透项目详情；统计条（项目总数/blocked 数/依赖边总数）。
5. **联动清理**：项目逻辑删时，其参与的依赖边由应用层同步逻辑删（同 t_project_principle 先例）；删除项目详情页的依赖区块显示"对方项目已删除"的边不出现在看板。
6. 权限：登记/编辑限 tenant_admin、project_manager；删除限依赖双方项目经理或 tenant_admin。
7. **L2 降级**：前缀归属见 Q2（约束：必须受 program_project_enabled 约束）。

## 5. 验收标准（Given-When-Then，QA 直接用）

> 通用前置：测试租户 T1（tenant_admin/pm/executive/engineer 账户齐备）；第二租户 T2 用于隔离验证。DORA 断言均指看板接口返回值；时间构造允许 ±1 分钟误差；所有"审计含 X"断言查 t_governance_log。

### AC-F1 DORA 效能看板

**AC-F1.1 部署频率计算正确**
- Given 项目 P（关联 3 个 Case），在近 30 天内的不同日期分别通过 transit 接口将 3 个 Case 流转至 done（其中一个 Case 重复调用 done transit 两次）
- When 查询 DORA 看板（项目=P，周期=30 天）
- Then 部署频率 = 3/30 = 0.1 次/天（重复 done 调用按 Case 去重不重复计数）；样本数 N=3；分档徽标按 §4.1.2 分档表渲染

**AC-F1.2 变更前置时间分布**
- Given 项目 P 的 Case A（create_time=8月1日 10:00，8月2日 10:00 流转 done，LT=24h）与 Case B（create 8月1日 10:00，8月3日 10:00 done，LT=48h）
- When 查询 DORA 看板（项目=P，周期=30 天）
- Then LT P50=36h、P90=48h（两点分布 P90 取较大值），展示单位为小时；样本数 N=2

**AC-F1.3 变更失败率口径**
- Given 项目 P：Case X 的编排终态 failed 且 steps_json 存在 status=failed、gateResult=FAIL 的步骤（门禁终判失败）；Case Y、Z 编排终态 done
- When 查询 DORA 看板（项目=P）
- Then 变更失败率 = 1/3 ≈ 33.3%；tooltip 明示"门禁终判失败口径（代理指标）"；另构造一个 warn 放行（gateResult=FAIL_WARN 且编排 done）的 Case，断言其不计入分子

**AC-F1.4 恢复时间与埋点**
- Given 项目 P 的 Case C：门禁角色 team-reviewer 首次派生判定 FAIL（打回），重做后第二次派生判定 PASS，两次派生记录 finished_at 分别为 10:00 与 10:45；第二次派生后编排最终 done
- When 查询 DORA 看板（项目=P）
- Then 恢复时间样本 = 45 分钟（第二次 PASS 记录 finished_at − 首次 FAIL 记录 finished_at）；且 t_derivation 中这两行记录的 gate_result 列分别为 FAIL、PASS（埋点生效）；构造一个终判失败无恢复的 Case，断言其不计入恢复时间样本

**AC-F1.5 历史数据回溯透明化**
- Given 项目 P 存在一条升级前遗留的 done Case（无对应 case_transit 审计记录）与两条有审计记录的 done Case
- When 查询 DORA 看板（项目=P）
- Then 前置时间样本数 N=2（遗留 Case 被排除而非用 update_time 冒充），页面显示"M 条历史数据不可回溯已排除"（M=1）；恢复时间对无 gate_result 埋点的样本加"≈"近似角标

**AC-F1.6 过滤与空态**
- Given 租户 T1 有项目群 G（成员 P1、P2）与独立项目 P3；P1 有 done 数据、P3 无任何数据；另有无项目关联的 done Case C9
- When 分别切换过滤维度（P1 / G / 全部项目）与周期（7/30/90 天）
- Then P1 维度仅含 P1 数据；G 维度=P1+P2 合并；全部项目=P1+P2+P3；**任何维度都不含 C9**（未关联项目 Case 不计入）；P3 单选时显示空态引导文案

### AC-F2 里程碑激活

**AC-F2.1 两级里程碑创建**
- Given 以 project_manager 登录，项目群 G 与其下项目 P 均存在
- When 分别创建项目群级里程碑 M1（G）与项目级里程碑 M2（P），各填标题/计划日期/负责人
- Then 两条里程碑创建成功、状态均为 planned、达成日期为空；各自出现在对应详情页的归属列表；审计含 milestone_create ×2

**AC-F2.2 状态流转与达成日期**
- Given 项目级里程碑 M（planned）
- When 执行"确认达成"（达成日期默认当天）
- Then M.status=achieved、achieved_date=当天；再执行"撤销"，则 M 回到 planned 且 achieved_date 清空，两次流转均在审计日志有记录

**AC-F2.3 逾期提示与 delayed 标记**
- Given 里程碑 M（planned，计划日期=昨天）
- When 查看其所属项目进度页时间线
- Then M 显示"逾期"黄色角标且 status 仍为 planned（系统不自动改状态）；执行"标记延期"后 M.status=delayed；delayed 状态下执行"确认达成"成功且达成日期必填

**AC-F2.4 全部 Case done 提示可达成（人工确认）**
- Given 项目 P（case_total=2, case_done=2，即全部 Case done）且 P 有 planned 里程碑 M
- When 查看 P 的详情页
- Then 页面出现"项目全部 Case 已完成，可达成里程碑"提示条并指向 M；对提示条上的 M 执行确认达成后提示条消失

**AC-F2.5 未全部完成不提示**
- Given 项目 P（case_total=3, case_done=2）且有 planned 里程碑
- When 查看 P 的详情页
- Then 不出现任何"可达成"提示条；case_total=0 的空项目同样不出现提示

**AC-F2.6 时间线展示与项目群聚合**
- Given 项目群 G 下项目 P1 有里程碑（planned/achieved/delayed 各一），G 自身有群级里程碑
- When 查看 P1 进度页时间线与 G 详情页聚合时间线
- Then P1 时间线按计划日期排序、三种状态色与逾期角标正确渲染；G 聚合时间线包含群级与 P1 的全部里程碑且带层级标签区分

### AC-F3 跨项目依赖

**AC-F3.1 依赖创建与规范向**
- Given 项目 A、B 存在，以 project_manager 登录
- When 用"A 阻塞 B"快捷入口登记依赖（类型 blocks）
- Then 存储为 from=B、to=A 的强依赖（规范向换向），依赖列表以依赖方视角展示 B → A；再用"B depends_on A"登记一次
- Then 第二次被唯一约束拒绝（同对项目同类型重复）

**AC-F3.2 blocked 判定与解除**
- Given 依赖 B depends_on A，A.status=in_progress（未交付）
- When 查看依赖看板
- Then B 标记 blocked 且阻塞来源显示"被 A 阻塞：A 未交付"；将 A 置为 delivered 后刷新
- Then B 的 blocked 自动解除（无需人工操作）；A 置为 closed 同样解除

**AC-F3.3 循环依赖创建即拒**
- Given 依赖 B depends_on A 已存在
- When 登记 A depends_on B（两节点环）
- Then 返回 400 业务错误并提示成环路径 A→B→A；再构造三节点链 B→C、C→A 已存在后登记 A depends_on C
- Then 同样被拒并提示 A→C→B→A（或等价环路径）；已存在的依赖数据不受影响

**AC-F3.4 relates_to 豁免**
- Given 依赖 A relates_to B 与 B depends_on A 并存
- When 查看依赖看板并执行全图体检
- Then A 不因 relates_to 边被判 blocked（弱关联不计入）；体检不报环（relates_to 不参与环检测）；A 因 depends_on→B 且 B 未交付仍正常判 blocked

**AC-F3.5 看板穿透与项目删除联动**
- Given 依赖 B depends_on A，A 下有 Case 与进度数据
- When 逻辑删除项目 A（二次确认）
- Then 该依赖边同步逻辑删，依赖看板不再出现该边；B 的 blocked 随之解除且 Case 回归"无项目"状态不受影响（回归 PRJ-002 删除语义）

### AC-F4 ADR 库

**AC-F4.1 CRUD 与编号唯一**
- Given 以 tenant_admin 登录（ADR 编辑权）
- When 创建 ADR：编号 ADR-001、五段式字段齐全、关联原则 P11，再次创建同编号 ADR
- Then 第一次成功（状态 proposed）；第二次返回唯一性冲突错误；列表可按状态=proposed 筛出该条

**AC-F4.2 状态机约束**
- Given ADR-001 处于 proposed
- When 直接将其状态改为 superseded（跳过 accepted）
- Then 返回 400 非法流转；先流转 accepted 成功后再流转 superseded 而不填 superseded_by
- Then 返回 400（superseded_by 必填）；填入已 accepted 的 ADR-002 后成功；对已 superseded 的 ADR-001 再改回 proposed 被拒（终态不可回退）

**AC-F4.3 原则联动提示（提示而非自动）**
- Given ADR-001（accepted）关联原则 P11
- When 将 ADR-001 置为 deprecated 并保存
- Then 保存成功后页面出现"该 ADR 关联原则 P11，请检查原则内容是否需要同步"提示条并附原则管理直达链接；t_architecture_principle 中 P11 内容**未被系统自动修改**；原则 P11 的管理/编辑页显示关联 ADR 列表含 ADR-001（deprecated）

**AC-F4.4 筛选与详情**
- Given 租户 T1 有 3 条不同状态的 ADR，其中 2 条关联原则 P11
- When 按状态=accepted、按关联原则=P11 分别筛选
- Then 列表结果正确；打开任一详情页五段式（编号/上下文/决策/后果/关联原则）完整展示且关联原则可点击穿透

### AC-F5 技术雷达

**AC-F5.1 CRUD 与枚举校验**
- Given 以 tenant_admin 登录（雷达编辑权）
- When 创建技术项：名称=Redis、象限=tools、环=adopt、理由与评审日期齐全；再分别尝试①同名再建 ②象限=hardware（非法枚举）

**AC-F5.2 四象限渲染与列表保底**

- When 打开技术雷达页
- Then 四象限图正确渲染（4 扇区×4 同心环，各技术项落在对应扇区环内，hold 环视觉警示），点击任一技术项可进入编辑；切换到列表视图

**AC-F5.3 环移动审计留痕**
- Given 技术项 Redis 当前环=trial
- When 编辑为 adopt 并保存
- Then 保存成功；审计日志新增记录，detail 含 trial→adopt 的环变更信息；技术项当前环=adopt

**AC-F5.4 待复审提示**

### AC-ISO 多租户隔离

**AC-ISO.1 五类新数据隔离**
- Given 租户 T1 有里程碑/依赖/ADR/雷达数据（各至少 1 条），T2 无上述数据
- When T2 用户查询里程碑、依赖、ADR、雷达列表及 DORA 看板
- Then 所有结果为空（不含 T1 任何数据，tenant_id 自动过滤）

**AC-ISO.2 跨租户直达被拒**
- Given 租户 T2 用户持有合法 token，T1 存在里程碑 M1/依赖 D1/ADR A1/雷达项 R1
- When 用 T1 资源 id 直调各详情/编辑接口
- Then 返回 404 或 403，不泄露资源存在性与内容

**AC-ISO.3 DORA 数据隔离**
- Given T1 与 T2 各有项目与 done Case 数据
- When T2 用户查询 DORA 看板（全部项目维度）
- Then 指标仅由 T2 的 Case/编排/审计数据计算，T1 数据完全不可见不可计入

### AC-RBAC 权限分级

**AC-RBAC.1 编辑权限矩阵**
- Given engineer 与 project_manager 用户并存
- When 两人分别调用里程碑/依赖/ADR/雷达的 create 与 edit 接口
- Then project_manager：里程碑、依赖 create/edit 200，ADR/雷达 create/edit 403；engineer：八类编辑接口全部 403

**AC-RBAC.2 view 级开放**
- Given engineer 用户
- When 调用 adr:view、radar:view 对应查询接口
- Then 200（ADR/雷达只读向 engineer 开放）；调用 dora:view 接口为 403（DORA 属管理层视图）

**AC-RBAC.3 审计全覆盖**
- Given 任意有权限用户对里程碑/依赖/ADR/雷达执行增删改、状态流转、环移动操作
- Then 每次操作在 t_governance_log 有记录（操作类型+资源+操作者+时间，状态流转与环移动的 detail 含变更前后值）

### AC-SWITCH 分层开关（L2 降级与不限层结论）

**AC-SWITCH.1 L2 关闭：DORA/里程碑/依赖降级隐藏**
- Given 租户 T1 program_project_enabled=0（strategy 开关任意），此前已有 DORA 数据、里程碑、依赖数据
- When T1 任意用户登录使用平台
- Then DORA 看板/里程碑/依赖入口（含项目详情页的时间线与依赖区块）全部隐藏；对应 API 返回 HTTP 200 + 业务码 43002（非 500）；数据未做任何清理

**AC-SWITCH.2 ADR/雷达不限层（P13 结论验收）**
- Given 租户 T1 strategy_enabled=0 且 program_project_enabled=0（场景C 只用 L1）
- When T1 用户使用 ADR 库与技术雷达
- Then 两功能完整可用（CRUD/状态流转/四象限渲染/筛选全部通过对应功能 AC）；L1 既有功能（Case/编排/门禁/检查点/产物）回归不受任何影响

**AC-SWITCH.3 开关可逆、数据保留**
- Given 租户 T1 关闭 L2 时已有里程碑 M、依赖 D、DORA 统计源数据
- When 重新开启 L2
- Then M、D 原样恢复展示；DORA 指标按保留数据重新可算且数值与关闭前一致

## 6. 非功能需求

### 6.1 权限与安全
- 全部新接口挂 @RequirePermission（权限原子见 §4.6），禁止裸奔；权限矩阵对齐 AC-RBAC。
- t_milestone 激活涉及旧列保留：旧 program_id(VARCHAR) 只读不写，前端不提供编辑入口（防 legacy 数据被新功能污染）。
- detail JSON 写入沿用 safeJson 转义先例（CaseStateController），防 JSON 注入。

### 6.2 性能
- DORA 聚合接口：P95 ≤ 1s（单项目 1000 Case / 5000 派生记录 / 10000 审计行量级）；实现方式（实时聚合 vs 定时预聚合表）由 SE 定（开放问题 Q7），PRD 只约束时效：**数据延迟 ≤ 5 分钟**（done 流转后 5 分钟内看板可见）。
- 依赖环检测：新建校验 ≤ 100ms（100 项目 / 500 依赖边量级）；全图体检 ≤ 1s。
- 里程碑时间线/依赖看板/ADR/雷达列表：P95 ≤ 500ms（单租户 500 项目 / 5000 ADR / 1000 雷达项量级）；雷达四象限渲染 ≤ 2s（100 项）。

### 6.3 可靠性与升级兼容
- V5 迁移幂等可重放（CREATE TABLE IF NOT EXISTS / ADD COLUMN 容错 / INSERT IGNORE），不破坏既有功能——**回归范围：PRJ-002 全部 AC（开关/注入/汇总/下钻）+ Case 全生命周期 + 编排门禁**。
- t_derivation 新增 gate_result 列可空默认 NULL：不影响既有派生链路读写；埋点写入失败仅记 ERROR 日志，**绝不影响编排主流程**（打回/重做/终判行为不变）。
- DORA 看板为只读消费端：统计源数据异常（steps_json 解析失败等）降级显示"该项暂不可用"，不得抛 500 影响整个看板页。
- 里程碑达成提示、依赖 blocked 判定均为展示层计算：计算异常不阻塞项目/看板主渲染。

### 6.4 成本治理
- DORA 聚合不得在每次页面刷新时全量重扫审计表——按项目+周期缓存或预聚合（SE 定，Q7）；雷达/ADR 为纯 CRUD 无额外 LLM 成本；本期五功能**不引入任何新增 LLM 调用**。

### 6.5 兼容性
- 浏览器与分辨率同 M2 Phase 1（Chrome/Edge/Firefox 100+，≥1024×768）；雷达图禁用外部 CDN/在线服务（离线部署约束），自包含渲染。
- 前端沿用 jQuery + menu.js 菜单机制增量接入，不重构既有框架；DORA/里程碑/依赖菜单受 L2 开关控制（menu.js 增量），ADR/雷达菜单恒显。

### 6.6 可观测
- DORA 口径计算打结构化日志（tenantId/projectId/指标名/样本数/耗时）；埋点写入（gate_result）失败告警。
- 五类资源治理操作全量审计（AC-RBAC.3）；环检测拒绝事件打 WARN 日志（含成环路径）。

## 本次经验沉淀

1. **行业指标（DORA 类）进 PRD 必须先做"口径可计算性盘点"，把每条公式拆到表.字段级，才能发现数据缺口并及时定义最小埋点**。本次盘点发现三处硬事实：t_derivation.status 记录的是 LLM 调用成败而非 GATE 判定、steps_json 重跑会覆盖步骤时间戳、升级前历史 Case 无 case_transit 审计——若不盘点就写"四指标看板"，恢复时间会在 Dev 阶段才发现算不出来，历史数据回溯会在 QA 造数时才发现口径含糊。教训：**指标类需求的 PRD 必须为每个指标写"数据源+公式+可计算性结论（可算/近似/需埋点）"三段式，近似口径必须显式标注而非默默降级**。
2. **"死表激活"与"全新建表"要区别对待数据模型策略：激活优先继承 legacy 治理先例，新建优先锚定既有枚举与原则**。t_milestone 激活沿用 t_case.program_id(VARCHAR) 的"保留只读不写"先例（V1 列不迁移不破坏），blocked 判定直接复用 t_project.status 既有四态而非发明新字段，环检测直接把架构原则 P3 翻译成产品约束——三者都让新功能"长在旧资产上"。教训：激活/扩展类需求先找同类先例（哪怕是别的表的），一致性本身就是 PRD 质量的护城河。
3. **功能层级归属要用"治理对象是什么"判定，而不是"功能像哪层"**。ADR/技术雷达表面上"很 L3"（架构决策、技术战略），但治理对象是租户级知识资产、不依赖任何战略/项目群/项目实体，且有关键先例（PRJ-002 SE 裁决原则/门禁不随 L2 开关拦截）——据此得出"不限层"结论并用否定性 AC（关 L2+L3 后全功能可用，AC-SWITCH.2）钉死。教训：层级/开关归类题先问"关掉这层，这个功能的统计对象还存在吗"，存在即不应被开关绑架，否则就是给 P13 埋雷。
