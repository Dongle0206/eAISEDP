**前置约束（不可违背）**：
- 架构原则 P13 灵活接入（**本 PRD 第一约束**）：每层可独立启用；Case 可不属于任何项目；项目可不属于任何项目群；项目群可不关联战略；不用上层功能不影响下层运行。
- P11 多租户隔离：三/四层所有新表与查询必须带 tenant_id，注入与门禁规则按租户生效。
- P6 零硬编码：质量门禁角色集合、流水线注入内容不得写死在 Java 常量里，必须由租户可配置数据驱动。
- P13 API 版本化 `/api/v1/`；P3 依赖单向：L3→L2→L1 单向引用，L1 编排不得反向依赖 L3 存在。

**一句话需求**：把已经跑通的 L1（Case 编排/门禁/检查点/产出落地）装进「战略→项目群→项目」的治理骨架里——下行把企业的架构原则和质量门禁规则注入每次 Case 编排，上行把 Case 完成自动汇总成项目进度，且企业可以从任意一层接入而不被强制全层使用。

## 1. 背景与目标

### 1.1 业务背景

eAISEDP 平台 M1/M2 已完成 L1 执行引擎完整闭环：Case 全生命周期状态机（drafting→deriving→reviewing→testing→deploying→done）、流水线编排（智能规划 + 门禁打回 + 检查点人工锁 + 断点续跑）、产出落地 Git/CI、多租户/RBAC/审计/配额。

但平台目前只有"执行层"：**Case 与企业战略、项目群、项目之间没有数据与管理上的贯通**。企业的真实管理链条是「战略目标 → 项目群 → 项目 → 具体交付件」，当前每一段都是断裂的：

- 高管看不到"我的战略目标推进到哪了"；
- 项目群经理看不到"群下各项目的真实进度"（只能靠人肉汇报）；
- 企业既有的架构原则、质量门禁要求停留在 Word/Confluence 文档里，**约束不进 AI 编排**，AI 产出的代码可以完全无视企业规范；
- Case 完成了，进度需要人工去 Excel 里改。

与此同时，eAISEDP 作为对外商用的智能化软件工程平台，客户形态三种（见 §1.3），**平台不能假设客户全层使用**——这也是架构原则 P13 的来源。

本需求（PRJ-002）交付**三层贯通骨架**：四级数据模型 + 管理页面、下行约束注入机制、上行进度汇总机制、三场景灵活接入能力。骨架的含义是：打通主链路与两个机制，治理深度功能（DORA 看板、依赖管理、ADR 库、真实工具对接等）留给 PRJ-003/004/005。

### 1.2 业务目标与成功指标

| 目标 | 衡量指标 | 验收口径 |
|---|---|---|
| 四级联动可管理 | 战略/项目群/项目均可 CRUD，Case 可关联项目 | AC-F1/F2/F3/F4 |
| **下行约束真实生效** | 项目配置的架构原则出现在该 Case 编排每个角色的 LLM 上下文中，可追溯 | AC-F7 |
| **门禁规则企业可配置** | 门禁规则增/删/改/启/停后编排行为随之变化，无硬编码门禁角色集合 | AC-F6 |
| **上行汇总自动准确** | Case 状态变 done 后项目进度无需人工干预自动更新 | AC-F8 |
| 三级看板可下钻 | 战略→项目群→项目→Case 逐级点击可达，URL 直达 | AC-F9 |
| **灵活接入（P13）** | 三场景各自可用：只开 L1 全功能可用；Case 不关联项目正常执行；项目群不关联战略正常运作 | AC-F10、AC-F4.3 |
| 多租户隔离 | 四层数据、原则、门禁规则、注入行为全部按租户隔离 | AC-ISO |
| 权限分级 | 战略层限高管、项目群/治理配置限管理员/项目经理，兼容现有 RBAC | AC-RBAC |

### 1.3 三场景适配说明（P13 灵活接入，强制）

| 场景 | 客户形态 | 接入方式 | 平台行为 | 本骨架支撑点 |
|---|---|---|---|---|
| **场景A 全层** | 大型企业（少数）| L3→L2→L1 端到端，按体系重建管理链 | 全部功能启用：战略拆解项目群、项目群含项目、项目挂 Case、原则/门禁全局注入 | F1~F10 全部 |
| **场景B 从 L2 接入**（主流）| 中型企业，已有 Jira/Confluence 等资产 | 从项目群/项目层接入，映射现有资产 | 关闭 L3 开关：项目群可不关联战略；项目/Case/注入/汇总/门禁全部可用；现有 Jira 项目以"项目"承载（名称/描述手工映射）| F10 关 L3 + F2 项目群 strategy_id 可空 + F4~F8 照常 |
| **场景C 只用 L1** | 轻量场景 | 直接用 Case 执行 | 关闭 L3+L2 开关：只剩 Case 功能；Case 不关联项目；无下行注入、无上行汇总，全部 L1 能力（编排/门禁/检查点/产物/Git/断点续跑）不受影响 | F10 关 L3+L2 + AC-F4.3/AC-F10.2 |

**P13 验收总纲（各功能不可违背）**：任一层关闭或数据为空，下层功能必须完整可用；上层存在不得成为下层运行的前置条件。

## 2. 用户故事（INVEST 原则）

### US-1 战略管理员（高管，executive 角色）

- 作为「战略管理员」，我希望「在平台上创建战略目标、定义 KPI（目标值/当前值）并按季度/年度/三年维度管理」，以便「战略不再只存在于 PPT，而是可追踪的活数据」。
- 作为「战略管理员」，我希望「把项目群挂到某个战略目标下，并在战略看板看到每个项目群的进度汇总」，以便「不用开项目汇报会就知道战略推进到哪了」。
- 作为「战略管理员」，我希望「战略目标有 draft/active/achieved/archived 生命周期」，以便「规划中的战略不干扰在管战略的看板」。
- 作为「战略管理员」，我希望「战略层页面只有我这样的高管角色可以进入和编辑」，以便「战略信息不越权扩散」。

### US-2 项目群经理（PgM，当前由 tenant_admin 兼任，见开放问题 Q4）

- 作为「项目群经理」，我希望「创建项目群、编写项目群章程（从战略继承的目标/边界），并把项目群关联到战略目标」，以便「项目群始终对齐战略」。
- 作为「项目群经理」，我希望「项目群可以不关联任何战略（客户从 L2 接入的场景）」，以便「对接已有管理模式的企业也能用」。
- 作为「项目群经理」，我希望「在项目群下创建/管理多个项目，并看到每个项目的进度与 Case 完成情况汇总」，以便「跨项目进度一目了然」。
- 作为「项目群经理」，我希望「配置租户级的架构原则（must/should/may 分级）和质量门禁规则（类型/阶段/失败动作/重做上限），并随时启停」，以便「企业治理要求一次配置、全体 Case 编排生效」。

### US-3 项目经理（project_manager 角色）

- 作为「项目经理」，我希望「创建项目（可属于某项目群，也可独立）、填写项目描述与约束」，以便「把一组相关 Case 组织成项目」。
- 作为「项目经理」，我希望「创建 Case 时选择所属项目，或在 Case 详情里事后挂接/解除挂接」， 以便「灵活归组，不强制先建项目再跑 Case」。
- 作为「项目经理」，我希望「项目下的 Case 状态变为 done 后，项目进度（已完成/总数/百分比）自动更新，不需要我手工去改」，以便「进度数据永远真实」。
- 作为「项目经理」，我希望「给项目选定要注入的架构原则集」，以便「不同客户项目遵守不同的企业规范（如金融项目强制安全原则）」。

### US-4 平台管理员（platform_admin / tenant_admin 角色）

- 作为「平台管理员」，我希望「按租户配置三层功能的启用开关（战略/项目群+项目/执行）」，以便「给场景B 客户关掉战略层、给场景C 客户只留 L1」。
- 作为「平台管理员」，我希望「关闭某层后相关菜单对租户用户不可见、API 返回'功能未启用'而非报错，重新开启后数据原样恢复」，以便「开关是安全可逆的」。
- 作为「平台管理员」，我希望「架构原则和质量门禁规则的每次增删改启停都进审计日志」， 以便「治理配置变更有据可查」。

### US-5 企业客户实施顾问（交付 eAISEDP 的售前/实施人员）

- 作为「实施顾问」，我希望「给中型客户开通平台后只启用 L2+L1，把客户已有的 Jira 项目清单整理成平台项目（手工录入名称/描述），Case 照常编排」， 以便「客户不用推翻现有工具就能先享受 AI 执行效率」（场景B）。
- 作为「实施顾问」，我希望「给轻量客户只启用 L1，客户直接创建 Case 跑编排，界面上完全看不到战略/项目群/项目字样」，以便「轻量客户零学习成本上手」（场景C）。
- 作为「实施顾问」，我希望「客户成熟后随时帮它打开上层开关、把存量项目归入新建的项目群与战略，历史 Case 归组不丢失」， 以便「客户可以渐进式深化使用」。

**INVEST 自检**：每个故事独立可验收（对应 §5 各 AC）；可协商（页面形态可由 UX 调整，联动语义不可）；对五类角色各自有价值；规模适合单 story；可测（AC 全部 Given-When-Then）；时间box 在 PRJ-002 内。

## 4. 功能需求详述

> **数据基线**：四级数据模型已由既有迁移草案定义（`eaiselp-runtime/src/main/resources/db/migration/V4__three_tier_model.sql`：t_strategy / t_program / t_project / t_case.project_id / t_architecture_principle / t_quality_gate_rule），本 PRD 直接以它为数据基线，字段语义以该文件 COMMENT 为准；本期新增数据需求仅 §4.3/§4.7 标注的两处（项目-原则关联、分层开关存储），由 SE 落到迁移脚本。

### 4.1 F1 战略目标管理（L3）

**功能要素**：
1. 列表页：按状态筛选（默认 active），展示 title / horizon（1q/1y/3y）/ status / owner / 关联项目群数 / 整体进度（关联项目群进度均值，展示层实时计算）。
2. 新建/编辑：title（必填 ≤200）、description（背景/价值/衡量标准）、horizon、owner、KPI（可多条：指标名 + 目标值 + 当前值 + 单位；当前值本期人工维护，自动回写见开放问题 Q5）。
3. 生命周期：draft → active（激活）→ achieved（达成）/ archived（归档）；achieved/archived 后不可再编辑 KPI 之外的字段；删除为逻辑删，**有关联 active 项目群时拒绝删除并提示先解除关联**。
4. 战略看板（并入 F9 下钻链）：每条 active 战略一张卡片，含 KPI 表与关联项目群进度。

### 4.2 F2 项目群管理（L2）

**功能要素**：
1. 列表页：name / status（planning/active/suspended/closed）/ pgm_manager / 起止日期 / 项目数 / 进度均值（群下项目 progress 算术平均，展示层实时计算）。
2. 新建/编辑：name（必填）、charter（章程文本，承载从战略继承的目标/边界）、strategy_id（**允许为空**——场景B 必需）、pgm_manager、起止日期、状态。
3. 章程展示：项目群详情页可查看完整章程；章程的"注入编排"属于 P1 增强项（见 F7）。
4. 删除：逻辑删；群下有关联项目时提示并将项目 program_id 置空（解除挂接）后删除，操作需二次确认。

### 4.3 F3 项目管理（L2）

**功能要素**：
1. 列表页：name / status（planning/in_progress/delivered/closed）/ priority（1 高~9 低）/ progress 进度条 / case_done/case_total。
2. 新建/编辑：name（必填）、description（项目描述/约束，**非空时下行注入**，见 F7）、program_id（**允许为空**——独立项目）、priority、status。
3. **原则集绑定**：项目编辑页可选择本租户启用的架构原则（多选）；语义见 F7 注入规则；**本期新增数据需求：项目-原则多对多关联**（V4 草案未含，由 SE 补迁移）。
4. 进度字段（progress/case_total/case_done）为系统自动汇总字段，**页面只读**，不允许手工编辑。
5. 删除：逻辑删；项目下有关联 Case 时提示并将 Case.project_id 置空后删除（Case 保留，回归"无项目"状态），二次确认。

### 4.4 F4 Case 关联项目

**功能要素**：
1. Case 创建（现有 POST /api/v1/cases 流程扩展）：新增可选参数所属项目；项目下拉仅列本租户未删除项目，默认"不关联"。
2. Case 详情：新增"所属项目"字段展示；提供「挂接项目」/「解除挂接」操作（**需要新增 Case 更新能力——现状仅有创建接口，BA 拆解注意**）。
3. Case 列表：支持按项目过滤（project_id 参数）。
4. **project_id 恒可空**（P13）：不关联任何项目的 Case 在创建、编排、检查点、产物、断点续跑全流程中与已关联 Case 行为完全一致（AC-F4.3）。
5. 兼容：t_case 既有 legacy 字段 program_id(VARCHAR)/subproject 保留只读展示，本期所有新功能一律使用 project_id（开放问题 Q6）。

### 4.5 F5 架构原则管理

**功能要素**：
1. 列表页：code（如 P3/P6/P11）/ title / principle_type（tech/data/security/governance）/ enforce_level（must/should/may）/ enabled 开关。
2. 新建/编辑：code 租户内唯一、title、content（注入编排的正文，建议单条 ≤2000 字符，前端提示不强制）、类型、强制级别、启停。
3. **Seed 数据**：部署时预置 P3 依赖单向 / P6 零硬编码 / P7 唯一调度入口 / P8 模型解耦 / P11 多租户隔离 / P13 灵活接入 六条（内容对齐战略地图 §4），enabled=1——这是"平台自身 dogfooding"要求（PRG-001 §3 下行约束）。
4. 删除：逻辑删；已被项目绑定的原则删除时同步清理绑定关系。
5. 语义约束：enforce_level=must 的原则，在注入文案中标注"违反将被 Reviewer 门禁拦截"（提示性文案，实际拦截依赖门禁规则配置，见 F6）。

### 4.6 F6 质量门禁规则管理

**功能要素**：
1. 列表页：name / gate_type / stage / applies_to / fail_action / max_retries / enabled，按 priority 排序。
2. 规则字段语义（对齐 V4 草案）：
   - gate_type：`auto_check`（程序化检查，check_key 对接现有 CodeValidationService 等检查项）/ `llm_review`（LLM 门禁角色审查，gate_role 如 team-reviewer）/ `human_approval`（人工审批，对接现有 Checkpoint 检查点机制）；
   - stage：`post_dev`（开发完成后）/ `post_test`（测试完成后）/ `pre_deploy`（部署前）；
   - fail_action：`block`（阻断：打回重做，超过 max_retries 编排失败，问题产出不部署）/ `warn`（告警放行：记录但不阻断）；
   - applies_to：all / code / design / doc（按产物类型生效）。
3. **替换硬编码**：现状 OrchestrationService 中 `GATE_ROLES`（team-reviewer/team-qa/team-security/team-performance）为 Java 常量硬编码——本期必须改为由本租户启用的 t_quality_gate_rule 驱动；部署 seed 预置与现状等价的规则（team-reviewer、team-qa 两条 llm_review 规则，enabled=1），保证升级后默认行为不变。
4. **租户级生效**：编排执行时只读本租户 enabled=1 的规则；规则参数（如规则级 max_retries）优先于全局 yml 默认值（`eaiselp.orchestration.gate-max-retries` 保留为兜底默认）。
5. 增删改启停即时生效：对**新创建**的编排生效；已在运行的编排不受影响（快照语义，避免运行中规则漂移）。
6. human_approval 类型规则：编排执行到对应阶段创建 pending 检查点并等待，复用现有检查点审批页面与超时（30 分钟）机制。

### 4.7 F7 下行注入编排（核心机制一）

**注入内容**（发送给编排中每个角色 LLM 的最终上下文，载体为 ContextAssembler 渲染的 prompt，新增独立章节"## 架构原则与项目约束（必须遵循）"）：
1. 项目约束：Case 所属项目的 description（非空时注入）。
2. 架构原则：按 F3 绑定关系解析出的启用原则列表（code + title + enforce_level + content；must 级标注拦截提示）。

**注入规则（默认语义，开放问题 Q2 确认）**：
- Case 未关联项目（project_id 为空）→ **不注入任何下行约束**（场景C 天然满足）；
- 项目绑定了原则集 → 注入绑定集中 enabled=1 的原则；
- 项目未绑定原则集 → 注入该租户全部 enabled=1 的原则（企业全局强制语义，对齐战略地图 §5"架构原则注入 L1 每次编排"）；
- 租户无任何启用原则且项目描述为空 → 注入章节整体省略，不产生空标题。

**注入时机与成本**：编排启动时按 case.project_id 解析一次，全部步骤复用同一份约束文本；单条原则截断 ≤2000 字符，注入总量 ≤8000 字符（超出按 priority 截断并日志告警）。

**注入留痕（P0，QA 验收依据）**：
- 服务端日志输出注入摘要（caseId + 注入的原则 code 列表 + 是否含项目约束）；
- 编排详情（t_orchestration 或等价载体）持久化本次编排的注入清单，前端编排详情页可见——否则"注入生效"不可测试。

### 4.8 F8 上行进度汇总（核心机制二）

**触发事件**（三处，均自动）：
1. Case 状态流转为 done（CaseStatus 终态）；
2. Case 挂接/解除挂接项目（含创建时带 project_id）；
3. Case 逻辑删除。

**汇总算法（确定可测）**：
- case_total = 项目下未删除 Case 总数；case_done = 其中 status=done 的数量；
- progress = ⌊case_done / case_total × 100⌋（向下取整；case_total=0 时 progress=0）；
- 项目群/战略的进度为展示层实时聚合（群=成员项目 progress 算术平均向下取整；战略=关联项目群进度算术平均向下取整），不落库。

**可靠性**：汇总失败**不得阻塞**Case 主流程（状态保存/编排收尾照常），记 ERROR 日志；提供「重新汇总」按钮（P1）修复漂移数据。

**语义边界**：项目状态与进度独立——进度 100% 不自动把项目置 delivered（避免隐性状态变更，由 PM 手动确认交付）。

### 4.9 F9 三级下钻看板

**下钻链**：战略看板（L3 卡片列表）→ 点击项目群 → 项目群详情（章程 + 项目列表 + 进度）→ 点击项目 → 项目详情（进度条 + 原则绑定 + Case 列表）→ 点击 Case → 现有 Case 详情页。
1. 每级为独立 URL（含 id），可收藏/直达/分享。
2. 项目详情的 Case 列表复用现有 case-list 页面按 project_id 过滤形态。
3. 各级空态引导：无战略→"从战略目标开始，或直接创建项目群（可不关联战略）"；无项目→"创建项目，或直接创建 Case（可不关联项目）"——空态文案必须体现 P13 不强制。
4. P1 增强项：燃尽图/甘特/里程碑视图（不做，PRJ-003）。

### 4.10 F10 分层独立启用开关

**配置模型**：租户级三层开关——`strategy_enabled`（L3）/ `program_project_enabled`（L2：项目群+项目一体）/ L1 恒开不可关。**本期新增数据需求：存储位置由 SE 定**（t_tenant 加列 / 独立配置表均可，PRD 只约束语义）。存量租户升级后默认全开（不改变 dogfooding 现状）。

**开关语义（每层独立、可逆）**：
1. 关闭某层 → 该租户用户菜单隐藏对应入口（menu.js 增量）、对应 API 返回统一业务错误（HTTP 200 + 业务码"该层功能未启用"，具体码值 SE 定义；**禁止 500**）；
2. 数据保留：关闭只影响入口可见性，不做数据清理；重新开启数据原样恢复；
3. **下层无感**：关 L3 → 项目群 strategy_id 可空性更显性（创建表单不出现战略选择）；关 L2 → Case 页面不出现项目选择与项目字段；L1 全功能（Case CRUD/编排/门禁/检查点/产物/断点续跑/工作区）不受任何影响；
4. 上行/下行联动降级：关 L2 时项目进度汇总入口不可见（数据保留）；关 L3 时战略看板接口拒绝。

## 5. 验收标准（Given-When-Then，QA 直接用）

> 通用前置：测试租户 T1（tenant_admin/pm/exec 工程师账户齐备）；构造第二租户 T2 用于隔离验证。进度断言均指数据库值或项目详情接口返回值。

### AC-F1 战略目标管理

**AC-F1.1 创建战略**
- Given 以 executive 身份登录，战略层已启用
- When 提交 title="智能化转型"、horizon="1y"、KPI=[{名称:平台化收入占比,目标值:10%,当前值:0%}]
- Then 创建成功；列表出现该战略且 status=draft；审计日志含 strategy_create 记录

**AC-F1.2 生命周期流转**
- Given 战略 S 处于 draft
- When 执行"激活"
- Then S.status=active；对 achieved 后的 S 再编辑 KPI 以外字段被拒绝（400 业务错误）

**AC-F1.3 有关联项目群不可删**
- Given 战略 S（active）下有关联项目群 G
- When 删除 S
- Then 返回业务错误提示"存在关联项目群，请先解除关联"；S 未被删除

**AC-F1.4 非高管不可管理战略**
- Given 以 project_manager 身份登录
- When 访问战略管理页面/API（strategy:create）
- Then API 返回 403；前端菜单不展示战略管理入口（详见 AC-RBAC.1）

### AC-F2 项目群管理

**AC-F2.1 项目群可不关联战略（场景B）**
- Given 租户 T1 战略层已关闭（或无任何战略数据）
- When 创建项目群 G，strategy_id 留空
- Then 创建成功；G.strategy_id 为空；项目群详情/列表正常展示

**AC-F2.2 章程编辑与状态**
- Given 项目群 G（planning）
- When 编辑章程文本并保存，状态改为 active
- Then 章程全文在详情页可见；G.status=active；审计含 program_update

**AC-F2.3 删除项目群解除项目挂接**
- Given 项目群 G 下有项目 P
- When 删除 G（二次确认）
- Then G 逻辑删除；P.program_id 置空且 P 保留可访问；P 的 Case 与进度不受影响

### AC-F3 项目管理

**AC-F3.1 项目可独立于项目群**
- Given 租户 T1
- When 创建项目 P，program_id 留空
- Then 创建成功；P 独立出现在项目列表，进度 0/0、progress=0

**AC-F3.2 进度字段只读**
- Given 项目 P（case_total=3, case_done=1, progress=33）
- When 通过编辑界面/API 尝试修改 progress 为 100
- Then 修改被忽略或拒绝（progress 为系统汇总字段）；数据库值仍为 33

**AC-F3.3 原则绑定**
- Given 租户 T1 有启用原则 P3、P6、P11
- When 编辑项目 P，勾选 P3、P11 保存
- Then P 的原则绑定集=[P3,P11]（project 无 P6）；绑定变更进审计日志

### AC-F4 Case 关联项目

**AC-F4.1 创建时挂接**
- Given 项目 P 存在
- When 创建 Case C 时选择所属项目 P
- Then C.project_id=P.id；P.case_total +1（自动汇总）；项目详情 Case 列表出现 C

**AC-F4.2 事后挂接/解除**
- Given Case C 未关联项目，项目 P（case_total=2）
- When 在 Case 详情执行「挂接项目 P」
- Then C.project_id=P.id，P.case_total=3；再执行「解除挂接」，则 C.project_id 为空，P.case_total 回到 2，case_done 同步重算

**AC-F4.3 未关联项目的 Case 全流程正常（P13 核心之一）**
- Given Case C 的 project_id 为空
- When 对 C 执行编排直至完成（含门禁打回、检查点审批）
- Then 编排状态 done、产出落地 Git、产物可查；全程无下行注入章节、无上行汇总调用、无任何 ERROR 日志——即"不关联项目"不是任何 L1 功能的前置条件

### AC-F5 架构原则管理

**AC-F5.1 原则 CRUD 与唯一性**
- Given 以 tenant_admin 登录
- When 新建原则 code=P13、enforce_level=must，再次新建同 code 原则
- Then 第一次成功；第二次返回唯一性冲突错误（uk_principle_code）

**AC-F5.2 启停即时生效于注入解析**
- Given 原则 PA enabled=1 且被项目 P 绑定
- When 将 PA 停用（enabled=0）
- Then 新启动的 P 项目 Case 编排注入清单中不含 PA（绑定关系保留，重新启用后恢复注入）

**AC-F5.3 Seed 六原则**
- Given 全新部署（迁移执行后）
- When 查询 t_architecture_principle
- Then 存在 P3/P6/P7/P8/P11/P13 六条，enabled=1，enforce_level=must（P13 等按 seed 定义）

### AC-F6 质量门禁规则可配置（非硬编码，核心验收）

**AC-F6.1 新增规则生效**
- Given 租户 T1 无任何 enabled=1 的 llm_review 规则；新增规则 R：gate_type=llm_review、gate_role=team-reviewer、stage=post_dev、fail_action=block、max_retries=2、enabled=1
- When 租户 T1 新建 Case 并启动编排
- Then 编排步骤中包含该门禁（post_dev 阶段出现 team-reviewer 门禁步骤，带 GATE:PASS/FAIL 判定要求）；判定 FAIL 时按 block 语义打回重做，重做超过 2 轮编排失败且不执行部署

**AC-F6.2 停用规则失效**
- Given 规则 R（AC-F6.1）enabled=1
- When 停用 R（enabled=0）后再次新建编排
- Then 新编排不再包含 R 对应门禁步骤；运行中的旧编排不受影响（快照语义）

**AC-F6.3 零规则不拦截（替换硬编码的证明）**
- Given 租户 T2 删除/停用其全部门禁规则
- When 租户 T2 的 Case 编排执行
- Then 编排正常完成，**不出现任何因内置硬编码门禁角色集合（GATE_ROLES 常量）产生的拦截**——代码中不存在按角色常量集合的固定门禁逻辑，门禁完全由租户规则数据驱动

**AC-F6.4 参数修改生效**
- Given 规则 R max_retries=2
- When 修改 R 的 max_retries=0 并保存，新建编排触发门禁 FAIL
- Then 编排立即终判失败（不再打回重做），fail_action=block 阻止部署；审计含 gate_update

**AC-F6.5 human_approval 规则走检查点**
- Given 新增规则 gate_type=human_approval、stage=pre_deploy、enabled=1
- When 编排执行到 pre_deploy 阶段
- Then 生成 pending 检查点、编排状态转为等待审批；审批通过后继续、拒绝后跳过部署——复用现有检查点页面与 30 分钟超时

**AC-F6.6 auto_check 规则走程序校验**
- Given 新增规则 gate_type=auto_check、check_key=code_validation、fail_action=block、enabled=1
- When 编排收尾触发代码校验且校验不通过
- Then 按 block 语义编排终判失败、产出不进入 Git push/部署链路；fail_action=warn 时仅记录告警并放行

### AC-F7 下行注入（核心验收）

**AC-F7.1 项目配置的原则注入编排上下文**
- Given 项目 P 绑定启用原则 PC（code=P11，content 含"多租户隔离"字样），项目描述非空
- When 创建 Case 关联 P 并启动编排（走完任一步骤）
- Then 发送给该编排**每个角色**的 LLM 上下文中，包含以"架构原则与项目约束"为题的章节：含 P11 的 code、标题、内容（含"多租户隔离"字样）与 must 级拦截提示，以及 P 的项目描述；且编排详情的注入清单记录 [P11]，日志含注入摘要——以上三处（上下文/清单/日志）任一可复核即判注入发生，三处须同时存在

**AC-F7.2 未绑定原则继承租户启用原则**
- Given 项目 P 未绑定任何原则；租户 T1 有启用原则 P3、P6
- When 启动 P 的 Case 编排
- Then 注入清单=[P3,P6]（租户全局强制语义）

**AC-F7.3 停用原则不注入 / 租户隔离**
- Given 租户 T1 原则 PA enabled=1、租户 T2 原则 PB enabled=1
- When T2 的无绑定项目 Case 编排启动
- Then 注入清单仅含 T2 的 PB，绝不含 T1 的 PA（注入按租户隔离）

**AC-F7.4 注入体积防护**
- Given 租户启用原则总内容 20000 字符
- When 编排启动
- Then 实际注入文本 ≤8000 字符（按优先级截断），日志出现截断告警；编排不因注入失败而中断

### AC-F8 上行进度汇总（核心验收）

**AC-F8.1 Case done 自动更新项目进度**
- Given 项目 P 下 3 个 Case（1 个 done、2 个非 done），即 case_total=3、case_done=1、progress=33
- When 其中 1 个 Case 状态流转为 done
- Then 查询项目 P：case_done=2、case_total=3、progress=⌊2/3×100⌋=66；全程无需人工操作；审计/日志可查汇总发生时间

**AC-F8.2 关联变化触发重算**
- Given 项目 P（2 Case）与项目外 Case C（done）
- When 将 C 挂接到 P
- Then P：case_total=3、case_done+1、progress 重算正确；再解除挂接，数值回到挂接前

**AC-F8.3 删除触发重算**
- Given 项目 P 下 3 个 Case，其中 1 个 done（progress=33）
- When 逻辑删除该 done Case
- Then P：case_total=2、case_done=0、progress=0

**AC-F8.4 汇总失败不阻塞主流程**
- Given 人为使汇总写库失败（如模拟异常）
- When Case 状态流转为 done
- Then Case 状态保存成功、编排收尾正常；ERROR 日志记录汇总失败；项目数据待重算修复（P1 手动重算）

**AC-F8.5 项目群/战略聚合展示**
- Given 项目群 G 下项目 P1(progress=40)、P2(progress=80)；战略 S 关联 G
- When 查看项目群 G 详情与战略 S 看板
- Then G 进度显示 ⌊(40+80)/2⌋=60；S 卡片进度显示 60（均为展示层实时计算，不落库）

### AC-F9 三级下钻看板

**AC-F9.1 逐级下钻链路**
- Given 战略 S → 项目群 G → 项目 P → Case C 链路数据齐备
- When 从战略看板点击 G，再点击 P，再点击 C
- Then 依次打开项目群详情、项目详情、现有 Case 详情；每级 URL 含对应 id，直接输入 URL 可直达同级页面

**AC-F9.2 空态引导不强制上层**
- Given 租户 T1 无任何战略/项目群/项目数据
- When 打开 Case 管理页
- Then Case 创建不要求选择项目（默认"不关联"）；空态文案引导而非阻断

### AC-F10 分层独立启用开关（P13 核心验收）

**AC-F10.1 只用 L1 层全功能可用（场景C）**
- Given 租户 T1 配置 strategy_enabled=false、program_project_enabled=false
- When T1 任意用户登录并使用平台
- Then 菜单仅含 L1 功能（Case 管理/看板/工作区/产物/检查点/搜索等既有 COMMON_MENUS+角色菜单），无战略/项目群/项目入口；Case 创建→编排→门禁→检查点审批→产物查看→断点续跑全部功能验证通过（回归既有 L1 用例集）；调用 L2/L3 API 返回"该层功能未启用"业务错误（HTTP 200 + 业务码），非 500

**AC-F10.2 关闭战略层不影响 L2/L1（场景B）**
- Given 租户 T1 strategy_enabled=false、program_project_enabled=true
- When 创建项目群（不关联战略）、创建项目挂 Case、跑编排、看进度
- Then 全流程成功；项目群表单不出现战略选择项；战略相关 API/菜单不可见

**AC-F10.3 开关可逆、数据保留**
- Given 租户 T1 关闭 L2 时已有项目 P 及其 Case
- When 重新开启 L2
- Then P 及 Case 关联、进度数据原样恢复展示

**AC-F10.4 存量租户默认全开**
- Given 执行升级迁移（已有 dogfooding 租户）
- When 迁移完成
- Then 该租户三层开关均为开启，现有 L1 使用行为无任何变化

### AC-ISO 多租户隔离

**AC-ISO.1 四层数据隔离**
- Given 租户 T1 有战略 S1/项目群 G1/项目 P1/Case C1
- When 租户 T2 用户查询战略、项目群、项目列表及项目详情的 Case 列表
- Then 所有结果不含 T1 的任何数据（tenant_id 自动过滤）

**AC-ISO.2 跨租户直达被拒**
- Given 租户 T2 用户持有合法 token
- When 用 T1 的 P1.id/S1.id 直调详情接口
- Then 返回 404 或 403，不泄露资源存在性与内容

**AC-ISO.3 原则与门禁规则隔离**
- Given T1 配置原则 PA 与门禁规则 RA，T2 配置 PB、RB
- When 分别查看两租户的原则/规则列表并各跑一个 Case 编排
- Then T1 列表只含 PA/RA、注入只含 PA；T2 只含 PB/RB、门禁只按 RB 执行；互不可见互不影响

**AC-ISO.4 开关隔离**
- Given T1 关闭 L3，T2 全开
- When T2 用户访问战略功能
- Then T2 正常访问——T1 的开关配置对 T2 无任何影响

### AC-RBAC 权限分级

**AC-RBAC.1 战略层限高管**
- Given executive 用户与 project_manager 用户并存
- When 两人分别访问战略管理
- Then executive 菜单可见、strategy:create/edit 接口 200；project_manager 菜单不可见、接口 403（code=40301）

**AC-RBAC.2 项目群/治理配置分级**
- Given engineer 用户
- When 调用 program:edit、principle:edit、gate:edit、tenant:layer:edit 对应接口
- Then 全部 403；project_manager 可 project:create/edit 但 program:edit 403

**AC-RBAC.3 兼容现有菜单与授权**
- Given 升级部署后（未做任何角色调整）
- When 既有 5 角色用户登录并访问原有全部功能
- Then 原 COMMON_MENUS/ROLE_MENUS 菜单与原授权行为完全不变（新增菜单项为增量）；既有 Case/看板/工作区等功能回归通过

**AC-RBAC.4 审计覆盖治理配置**
- Given 任意管理员执行战略/项目群/项目/原则/门禁规则/开关的增删改启停
- Then 每次操作在审计日志有记录（操作类型+资源+操作者+时间）

## 6. 非功能需求

### 6.1 权限与安全
- 权限分级见 §4.11；所有新接口必须挂 @RequirePermission，禁止裸奔。
- 战略层数据（战略/KPI）默认仅 executive + platform_admin 可见；审计沿用 AuditService。
- 分层开关关闭后的 API 响应不得暴露内部实现（统一业务码，非堆栈 500）。

### 6.2 性能
- 三级列表/看板接口：P95 ≤ 500ms（单租户 100 项目群 / 500 项目 / 5000 Case 量级）。
- 上行汇总（单项目重算）：≤ 200ms，且不得阻塞 Case 状态流转主事务（同步失败降级日志）。
- 下行注入解析：编排启动时一次性完成（≤ 100ms），不在每个角色步骤重复解析。

### 6.3 可靠性与升级兼容
- V4 迁移幂等可重放（IF NOT EXISTS / ALTER 容错），升级不破坏既有 L1 功能——**回归范围：Case 全生命周期、编排（含智能规划降级）、门禁打回、检查点审批、Git/CI 落地、断点续跑、多租户、RBAC、审计**。
- 运行中编排使用规则快照（启动时解析），规则修改不影响在跑实例。
- 门禁规则为空时编排行为 = 无门禁直通（不得出现 NPE/流程卡死）。

### 6.4 成本治理
- 注入体积上限 8000 字符（§4.7），防 prompt 膨胀推高 token 成本；截断必须留痕。

### 6.5 兼容性
- 浏览器与分辨率要求同 M2 Phase 1（Chrome/Edge/Firefox 100+，≥1024×768）。
- 前端沿用 eaiselp-web-separate 的 jQuery + menu.js 菜单机制，新增页面与菜单项增量接入，不重构既有框架。

### 6.6 可观测
- 下行注入摘要、上行汇总结果、门禁规则命中与打回、开关变更均打结构化日志（含 tenantId/caseId/projectId/原则code/规则id）。
- 治理配置变更全量审计（AC-RBAC.4）。

## 本次经验沉淀

1. **PRD 的"骨架"类需求必须先盘点数据模型草案再写功能点，否则会重复设计或漏掉关键缺口**。本次先读到 V4__three_tier_model.sql 已把六张表全部定义好（含字段 COMMENT），功能点直接"正式化"它即可；但盘点同时发现两个草案缺口——项目与原则之间没有绑定载体、租户没有分层开关存储位——它们恰好都是编排者点名验收标准（"Given 项目配置架构原则"）的必要前提。若不盘点就写 PRD，这两处缺口会在 Dev 阶段才暴露并引发返工。教训：写贯通类 PRD 前必须先做"数据模型 vs 验收标准"的交叉核对，缺口显式列为开放问题而不是默默带过。

2. **"灵活接入"类架构原则要翻译成否定性验收标准才算落地**。P13"每层可独立启用"如果只写成正向功能（做开关页面），Dev 很容易做出"开关存在但 Case 页面仍然报项目不存在错误"的实现。本次把它拆成一组否定性 AC：Case 不关联项目必须全程无错且无注入无汇总（AC-F4.3）、租户零门禁规则必须不拦截且代码无硬编码门禁（AC-F6.3）、关 L3 后项目群表单不出现战略选择（AC-F10.2）。教训：非功能性的架构原则进入 PRD 时，必须为它写"不做 X 时 Y 仍正常"的反向用例，这类用例是防止耦合回归的最有效护栏。

3. **不可见机制（注入/汇总）的验收标准必须指定"留痕载体"，否则 QA 无从下笔**。"原则注入到 LLM 上下文"在黑盒上不可观测——本次因此把"注入清单持久化 + 编排详情可见 + 日志摘要"升格为 F7 的 P0 子需求，让 AC-F7.1 有三个可复核的落点；同理上行汇总指定了断言数据库字段与具体数值（3 Case 1 done → 33，再 done → 66）。教训：凡是发生在系统内部、对用户不可直接感知的机制，PRD 必须同时定义"机制生效"与"生效证据"两件事，证据载体（日志/记录/页面字段）要与功能点一起交付。
