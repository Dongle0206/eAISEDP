## 1. 背景与目标

### 1.1 业务背景

**（A）L3 层还差两个角色没有平台落点。** 平台三层体系（L3 战略 → L2 项目群 → L1 Case）已完成：L3 战略目标/架构原则/ADR/技术雷达（V4/V5）、L2 项目群/项目/里程碑/依赖/DORA + L2 治理四域（case-20260818/20260820）、L1 编排与门禁（V1/V2）。对照体系角色清单，L3 层还有两个角色"有方法论、无平台落点"：

- **team-grc（治理/风险/合规）**：enterprise-grc 方法论（ISO 31000/COSO ERM 裁剪）要求风险登记册、合规检查台账、风险热力图——现状全部靠线下 Excel：风险没编号没状态机、概率×影响靠心算、复评日期靠人记；合规检查（等保 2.0/ISO27001/GDPR）证据散在邮件和 wiki，"哪条条款上次检查是什么结果"说不清。高管要风险量化视图（US-7），现在给不出。
- **team-strategy（战略投资）**：tech-radar 方法论要求投资决策有商业案例支撑（成本/收益/回收期/ROI/RICE 优先级）——现状战略目标（t_strategy）只有 KPI，**从战略到投入的钱没有决策记录**：为什么投这个不投那个、预期多久回本、优先级排序依据，全靠会议纪要。商业案例与战略目标（t_strategy）零关联，战略执行情况无法下钻到投资。

**（B）三层闭环的最后一环。** PRJ-004 主体（战略/ADR/雷达）已交付，尾巴即 GRC + 投资决策两块。本 Case 交付后：L3 五角色（EA/Strategy/GRC/…）全部有平台承载，L2/L1 亦然——平台"用体系自身开发"的 dogfooding 闭环完整，商用客户的三层全角色场景可完整演示。

## 2. 用户故事（INVEST 原则）

### US-1 风险管理员（team-grc 角色落点，本期由 tenant_admin 兼任，见 Q5）

- 作为「风险管理员」，我希望「登记风险（名称/类别/概率 1-5/影响 1-5），系统自动算风险值（1-25）与等级（低/中/高/极高），并沿 open→mitigating→closed 管理其生命周期、closed 必填处置说明」，以便「风险台账一张清单，量化分级一目了然，处置留痕不再靠记忆」。
- 作为「风险管理员」，我希望「把风险关联到项目群/项目/Case（可空多选），并设置复评日期、逾期红标」，以便「风险挂到具体交付对象上，复评不遗漏」。

### US-2 合规检查员（team-grc 兼任）

- 作为「合规检查员」，我希望「按框架（等保 2.0/ISO27001/GDPR/自定义）登记检查项、条款引用、检查结果（pass/fail/partial/na）与证据说明、复检日期」， 以便「合规台账可追溯——哪条条款、谁查的、什么结论、何时复检，一目了然」。

### US-3 高管（executive）

- 作为「高管」，我希望「打开风险看板看到 5×5 风险热力图、等级分布与高风险清单，打开投资组合视图看到按优先级排序的商业案例与总投入/总预期收益」， 以便「风险敞口与投资盘子一张图上会，不用等人拼 Excel」。

### US-4 战略投资经理（team-strategy 角色落点，本期由 tenant_admin 兼任，见 Q5）

- 作为「战略投资经理」，我希望「创建商业案例：填一次性成本/年运营成本/量化收益，系统自动算投资回收期、ROI（3 年口径）与 RICE 评分，关联战略目标」， 以便「每个投资决策有量化依据，战略目标可下钻到具体投入」。

### US-5 决策审批人（tenant_admin 兼任，创建与审批分离）

- 作为「决策审批人」，我希望「批准（draft→approved）或拒绝（draft→rejected，必填原因）商业案例，而被审批的案例不是我自己无法决定的东西——起草人（如 PM）不能自我批准」， 以便「投资决策权责分离，提案与审批两道锁」。

### US-6 项目经理（project_manager）

- 作为「项目经理」，我希望「登记和更新我项目相关的风险（含缓解进展 open→mitigating），起草商业案例」， 以便「一线风险及时上台账、投资提案有起草入口，但合规检查登记与案例审批不归我（防自查自登/自我批准）」。

### US-7 工程师（engineer）

- 作为「工程师」，我希望「只读查看风险登记册与商业案例」， 以便「知道团队在管哪些风险、投入从哪来，知识传播」。

**INVEST 自检**：每个故事独立可验收（对应 §5 各 AC）；可协商（页面形态/热力图实现可由 UX/SE 调整，计算口径/状态机/审批分离不可）；对七类角色各自有价值；规模适合单 story；可测（AC 全部 Given-When-Then 且含构造数值）；时间盒在本 Case 内。

## 4. 功能需求详述

### 4.1 F1.1 风险登记册

#### 4.1.1 数据契约（语义，SE 定稿表名/列名）

风险名（uk：租户内唯一，同门禁规则 uk_gate_tenant_name 先例）/ 描述 / 类别（枚举 strategy/compliance/operations/technical/security，展示名：战略/合规/运营/技术/安全）/ 概率 probability（TINYINT 1~5）/ 影响 impact（TINYINT 1~5）/ 风险值 risk_value（服务端算，=P×I，1~25）/ 等级 risk_level（服务端算，low/medium/high/critical）/ 缓解措施 / 应急预案 / owner（自由 VARCHAR，本期不联动 t_user，同资产责任人先例）/ 状态 status / 处置说明 resolution_note（closed 必填）/ 关联对象 related_objects（JSON 数组可空，元素 {type, id}，type∈{program,project,case}，见 §4.1.4）/ 复评日期 review_date（DATE 可空）/ 常规审计列（create_time/update_time/create_by/update_by/is_deleted，同 V4/V6 惯例）。

#### 4.1.2 风险值与等级口径（唯一权威，QA 照此构造）

| 口径项 | 定义 | QA 构造示例 |
|---|---|---|
| **风险值** | `risk_value = probability × impact`，服务端保存时计算落库；P、I 各为 1~5 整数 → 值域 1~25 | P=4, I=3 → 12 |
| **等级映射** | 低 low：1≤v≤6；中 medium：7≤v≤12；高 high：13≤v≤19；极高 critical：20≤v≤25 | v=12→中；v=13→高 |
| **等级边界** | 6=低、7=中、12=中、13=高、19=高、20=极高（闭区间左端点归属上一档的下一档，即 [1,6]/[7,12]/[13,19]/[20,25] 四段闭区间） | P=2,I=3→6→低；P=3,I=5→15→高；P=5,I=4→20→极高 |
| **概率/影响边界校验** | 0、6、负数、非整数（如 1.5）→ 400（应用层校验，TINYINT 存储） | probability=6 → 400 |
| **已知语义（非缺陷）** | P=1,I=5 → v=5 → 低：低概率×高影响按本公式属"低"——纯数学映射，缓解依赖复评日期与人工判断（写入产品口径，不接受"为什么不是高"类质疑工单） | — |
| **重算时机** | create 与 update（含 P/I 变更）均服务端重算并覆盖；客户端提交的 risk_value/risk_level 字段一律忽略 | 提交 risk_value=999 → 库中仍为 P×I |
| **逾期口径** | `review_date < CURRENT_DATE`（DATE 精度，不含时刻；到期当日不算逾期，次日红标）且风险状态 ≠ closed | review_date=昨天 → 红标；=今天 → 不标 |
| **排序口径** | 列表默认风险值降序；并列按 id 降序（写死，QA 断言用） | 两条 v=20 → 新建的在前 |

#### 4.1.3 状态机（应用层校验，非法流转 400，同 ADR/标准先例）

```
open ──开始缓解──> mitigating ──关闭(必填处置说明)──> closed（终态）
mitigating ──回退(缓解无效/风险复燃)──> open
其余流转（closed→任何、open→closed 跳级等）一律 400
```

- closed 必填处置说明：流转请求缺 resolution_note → 400；closed 后全字段只读（编辑 → 400，AC-F1.4）。
- open/mitigating 全字段可编辑（含 P/I，编辑即触发重算）；每次合法流转写一条审计（action 含 from→to 与操作者，同标准状态机先例）。
- closed 是否可 reopen：本期**不可**（终态；复燃风险新建条目并互链描述），Q2 待确认。

#### 4.1.4 关联对象

- 可空多选；JSON 数组，元素 `{type: program|project|case, id: BIGINT}`——**存 id**（t_program/t_project/t_case 均无 code 列；V4 t_program.strategy_id 存 id 先例）。type 非法值或 id 在租户内不存在 → 400（存在性校验）。
- 展示：详情页解析为"对象类型+名称"列表；被关联侧（项目群/项目/Case 详情）**本期不做反向展示区**（展示级打通最小闭环，反向聚合属后续 case，§7-8）。
- 被关联对象逻辑删后：风险侧条目展示"已删除"占位，**不影响风险任何行为**（同标准删除占位先例）。

### 4.2 F1.2 合规检查

**数据契约（语义）**：检查项名（uk：租户内唯一）/ 框架 framework（枚举 djba2.0/iso27001/gdpr/custom，展示名：等保 2.0/ISO27001/GDPR/自定义）/ 自定义框架名 framework_name（VARCHAR，**framework=custom 时必填**，其余框架时忽略/须为空）/ 条款引用 clause_ref（VARCHAR，如"ISO27001 A.9.4.1"）/ 检查描述 / 结果 result（枚举 pass/fail/partial/na）/ 证据说明 evidence_note / 检查日期 check_date（DATE，登记时可选默认当天）/ 复检日期 recheck_date（DATE 可空）/ owner（自由 VARCHAR）。

**手动登记制（本期不做自动扫描，§7-2）**：结果与证据由登记人判定填写，平台不做探测、不做条款符合性自动判定（§7-6）；结果修改为覆盖式单值当前态（历史唯一留痕 = t_governance_log 审计 detail，同质量规则先例）。

**复检逾期口径**：同风险复评口径（§4.1.2：`recheck_date < CURRENT_DATE` 红标；na 结果是否豁免逾期——**不豁免**，统一口径）。

**枚举校验**：framework/result 非法值 → 400；custom 未填 framework_name → 400；framework≠custom 但填了 framework_name → 400（防脏数据）。

### 4.3 F1.3 风险看板

- **热力图**：5×5 矩阵，**X 轴=影响（I1~I5）、Y 轴=概率（P1~P5）**（写死，QA 断言用）；每格计数 = 该 (P,I) 组合的**未 closed** 风险数（closed 不计入看板，AC-F1.12）；格子底色按该格风险值等级四档色阶（低→极高递进，形态 UX 定，AC 只断言计数与轴）。
- **等级分布**：低/中/高/极高四档计数（口径同上，仅未 closed）。
- **高风险清单**：等级∈{高, 极高} 的未 closed 风险列表，按风险值降序（并列 id 降序），含名称/P/I/等级/owner/复评日期（逾期红标透传）。
- **数据源**：单一聚合读 API（risk:view 权限即达，无独立权限原子）；无任何写操作（AC-F1.15）。

### 4.4 F2.1 商业案例

#### 4.4.1 数据契约与计算口径（唯一权威，QA 照此构造）

**输入字段**（用户填）：案例名（uk：租户内唯一）/ 描述 / 关联战略 related_strategy_ids（JSON 数组可空，存 **t_strategy.id**，见 Q3 裁决）/ 一次性成本 onetime_cost（DECIMAL，≥0）/ 年运营成本 annual_op_cost（DECIMAL，≥0）/ 量化收益（年）annual_benefit（DECIMAL，≥0）/ RICE 四因子：reach（INT 1~10）/ impact（INT 1~10）/ confidence（DECIMAL(2,1)，**0.1 步进离散：合法值恰为 0.1,0.2,…,1.0 共 10 档**）/ effort（INT 1~10）/ 状态 status / 拒绝原因 rejected_reason（rejected 必填）/ 决策记录 decision_note（自由文本，随流转可更新）。

**计算字段**（服务端算，客户端提交值一律忽略重算）：

| 字段 | 公式 | 边界与舍入 | QA 构造示例 |
|---|---|---|---|
| **年净收益** net_benefit | `annual_benefit − annual_op_cost` | 中间量，可负 | 60−20=40 |
| **投资回收期** payback_period | `onetime_cost ÷ net_benefit`，单位"年" | **net_benefit ≤ 0 → 值为 N/A（含 0，防除零）**；net_benefit>0 且 onetime_cost=0 → **0.0**；其余保留 1 位小数 HALF_UP | 100÷40=2.5；100÷30=3.3（3.333→3.3）；净收益 0 或 −10 → N/A；成本 0/净 30 → 0.0 |
| **ROI（3 年口径）** roi | `(net_benefit × 3 − onetime_cost) ÷ onetime_cost × 100%` | **onetime_cost = 0 → N/A（防除零）**；负 ROI 合法（3 年净收益<一次性成本）正常展示；保留 2 位小数 HALF_UP，带 % 展示 | (40×3−100)/100=**20.00%**；(10×3−100)/100=**−70.00%**；成本 0 → N/A |
| **RICE 评分** rice_score | `reach × impact × confidence ÷ effort` | effort≥1 恒正，**无除零路径**；保留 2 位小数 HALF_UP | 10×10×1.0÷1=**100.00**；5×3×0.8÷6=**2.00** |

**输入边界校验**：三个金额任一为负 → 400；金额=0 合法（onetime_cost=0 触发上表边界）；reach/impact/effort：0、11、非整数 → 400；confidence：0、1.1、**0.05/0.15（非 0.1 步进）**、两位小数 → 400。

**金额单位**：单一货币、单一单位（建议"元"或"万元"，SE 定稿并全局一致，Q1）；多币种/汇率换算范围外（§7-5）。

#### 4.4.2 状态机（应用层校验，非法流转 400）

```
draft ──批准──> approved ──启动执行──> executing ──完成──> done（终态）
draft ──拒绝(必填 rejected_reason)──> rejected（终态）
其余流转（rejected/done→任何、approved→rejected 撤销、draft→executing 跳级等）一律 400
```

- **批准/拒绝操作需 bizcase:approve 权限**（独立原子，§4.6）——创建与审批分离：起草人（PM）可 create/edit 但不可自我批准（AC-F2.9）。
- approved→rejected（批准后撤销）本期**不允许**（要拒走新案例或执行后复盘），Q2 待确认。
- 每次流转写审计（action 含 from→to、操作者、rejected_reason/decision_note）；拒绝原因与决策记录随流转落审计 detail。

#### 4.4.3 编辑限制

- draft：全字段可编辑（编辑触发计算字段重算）。
- approved/executing：输入字段（成本/收益/RICE 四因子/关联战略/名称/描述）只读，修改 → 400 业务错误（"已批准，输入不可改，请复盘或新建案例"）；**决策记录 decision_note 可更新**（200）——执行期进展记录。
- rejected/done：全只读（仅查看），任何编辑/流转 → 400。
- 逻辑删：draft 可删；**非 draft 不可删**（已进入决策/执行流的案例是合规资产，只能留痕，AC-F2.7 Then 项）。

#### 4.4.4 关联战略

- 可空多选，值域=租户内 t_strategy.id（存在性校验，无效 id → 400）；**存 id 而非 code——与 V5 ADR related_principle_codes 存 code 有意不同：t_strategy 无业务 code 列（V4:36-52 仅有 id/title），且 t_program.strategy_id 存 id 先例**（Q3）。
- 展示：案例详情展示关联战略标题列表；战略详情反向展示"关联商业案例"列表（**本期做反向**：战略→投资是战略执行度下钻的商用演示场景，一个只读查询；成本低于风险的四对象反向，故风险侧不做、战略侧做——不对称是有意的，Q3 备注）。
- 战略逻辑删后：案例侧条目"已删除"占位，计算与流转不受影响。

### 4.5 F2.2 投资组合视图

- **案例清单**：全部案例（含 rejected/done，标注状态）按 **rice_score 降序**（并列 id 降序）展示名称/状态/RICE/回收期/ROI/一次性成本/年净收益。
- **汇总卡（投资口径，仅统计 status∈{approved, executing, done}——draft 未决策、rejected 已否决，均不计入投资盘子）**：
  - 总一次性投入 = Σ onetime_cost
  - 总年运营成本 = Σ annual_op_cost
  - 总年化净收益 = Σ net_benefit（**可为负**，负值正常展示）
  - 总 3 年净收益 = Σ (net_benefit × 3)（与 ROI 3 年口径一致）
- **状态分布**：draft/approved/rejected/executing/done 五态计数（全量口径，与汇总卡的投资口径**有意不同**——分布看流程漏斗、汇总看钱，QA 注意区分断言）。
- **数据源**：单一聚合读 API（bizcase:view 权限即达）；只读。

## 5. 验收标准（Given-When-Then，34 条）

### F1 风险登记册

**AC-F1.1 风险 CRUD 与唯一性**
- **Given** 租户 A 的 tenant_admin 已登录
- **When** 创建风险 {名称"数据泄露", 类别 security, P=4, I=5, owner, 缓解措施} → 成功（200）；再创建同名"数据泄露" → 被拒（uk 冲突）；创建"权限蔓延" → 成功
- **Then** 列表两条可见，默认按风险值降序；风险名/类别/owner 缺失 → 400

**AC-F1.2 风险值与等级自动计算（数值断言）**
- **Given** tenant_admin 依次创建 6 条风险：{P=1,I=1}、{P=2,I=3}、{P=4,I=3}、{P=3,I=5}、{P=5,I=4}、{P=5,I=5}
- **When** 保存后读取各条详情
- **Then** risk_value/risk_level 依次为：1/低、6/低、12/中、15/高、20/极高、25/极高（边界 6/12/20 命中档位左端点断言）

**AC-F1.3 概率/影响边界校验**
- **When** 分别提交 probability=0、=6、=1.5（及 impact 同组）
- **Then** 均 400（明确字段错误提示）；P=1 与 P=5 均合法保存

**AC-F1.4 风险状态机**
- **Given** 风险 R 处于 open
- **When** 依次执行 open→mitigating → 成功；mitigating→closed（填处置说明"已转移供应商"）→ 成功；closed→open → 被拒（400 终态）；另建 open 风险直接 open→closed → 被拒（400 跳级非法）；再建 mitigating 风险 mitigating→open → 成功（回退合法）；closed 流转缺处置说明 → 400
- **Then** 每次合法流转一条审计；closed 后编辑任意字段 → 400

**AC-F1.5 编辑重算与防伪造**
- **Given** 风险 R={P=2, I=3}（v=6 低）
- **When** 编辑为 {P=5, I=4} 并在请求体同时携带 risk_value=1、risk_level=low → 保存成功
- **Then** 详情 risk_value=20、risk_level=极高（**客户端提交的计算字段被服务端重算覆盖**）

**AC-F1.6 关联对象**
- **Given** 租户 A 存在项目群 PG1、项目 PJ1、Case C1
- **When** 风险 R 关联 [{program,PG1},{project,PJ1},{case,C1}] → 成功且详情回显三条对象名；提交 [{project, 不存在 id}] → 400；提交 [{type:"task",…}]（非法 type）→ 400；提交空数组/不填 → 成功（可空）
- **Then** 逻辑删 PJ1 后，R 详情该条目显示"已删除"占位，R 其余行为不变

**AC-F1.7 复评日期与逾期口径**
- **Given** 三条 open 风险 review_date 分别为昨天、今天、+30 天
- **When** 打开列表/详情
- **Then** 仅昨天的展示逾期标识（今天/未来不标）；筛选"仅看逾期"命中且仅命中该条；风险转 closed 后逾期标识消失（口径=状态≠closed）

### F1 风险看板

**AC-F1.12 热力图计数**
- **Given** 租户 A 存在 open 风险 {P2,I3}、{P4,I5}、mitigating 风险 {P5,I4}、closed 风险 {P2,I3}

- **Then** 格子 (P=2,I=3)=1、(P=4,I=5)=1、(P=5,I=4)=1，其余 25-3=22 格为 0（**closed 不计入**）；轴定义 X=影响/Y=概率

**AC-F1.13 等级分布统计**
- **Given** AC-F1.12 数据集（v：6 低、20 极高、20 极高）

## 本次经验沉淀

1. **计算类字段必须在 PRD 给"公式+舍入+除零/零值/离散化边界+构造数值表"四件套，且必须写死"服务端重算覆盖"**：本次回收期（净收益≤0 与成本=0 两种 N/A 语义不同——前者不可投、后者零成本）、ROI 负值、RICE Confidence 0.1 步进离散（0.15 这类"合法小数但非步进值"最易漏）都是 QA 无法自行推断的口径；"客户端提交计算字段一律忽略重算"单独成 AC（AC-F1.5/F2.4）防前端伪造评分。建议沉淀为 PRD 模板触发规则：凡出现"自动算"字样的需求即强制四件套。
2. **"创建与审批分离"类需求应设独立 approve 权限原子，而非应用层角色判断**：虽然 V6 F3.2 有"应用层角色校验、无新增原子"先例，但那是低频运营操作；审批是高频业务操作且有独立配置/审计诉求，独立原子让 403 断言直接走权限链。判断准则沉淀：**操作频率高 + 未来可能下放给非 admin 角色 → 独立原子；一次性运营兜底 → 应用层判断**。
3. **引用键选 code 还是 id，取决于被引实体有无稳定业务键，不要沿袭先例形式**：V5 ADR 关联原则存 code 是因为 t_architecture_principle 有 code 列；本次战略存 id 是因为 t_strategy 只有 id/title（V4 代码级证据）。PRD 写关联契约前必须先查被引表结构，先例只继承"存稳定标识"的原则而非具体键型。
