# team-orchestrator 经验记忆

> 本文件记录编排者角色在历史 case 中沉淀的可复用经验。每个新 case 派生前编排者必读本文件，避免重复踩坑。

## 经验清单（按时间倒序）

### 经验 6：经验 5 的判据错位——调研类活按场景区分，不是一刀切违规（2026-07-21，方法论架构师元评估修正）

**⚠️ 本条修正经验 5 的核心判据。经验 5 保留作为历史记录，但其中"摸现状/写诊断都算越权"的判定已被本条取代。**

`tags: 调研边界, 信息流判据, 上下文成本, 决策框架, severity: high`

**场景**：用户第二次反馈"评估该方式是最专业和消耗最小、成本最小的"。实质不是要"更严格遵守规范"，而是要"规范本身修订"。方法论架构师对 team-orchestrator SKILL.md 第 4 条"不越权执行"做了元评估，发现第 4 条把"防不可逆操作（部署/写代码/git 提交）"机械地套到了"摸现状/读文档/抽检落盘"这类**零越权风险**的调研场景，是规范过拟合。

**根因（经验 5 错在哪）**：
- 经验 5 把"摸工程现状"等同于"写代码/部署"，判据错位。
- 经验 5 的纠偏问句"这件事是不是某个 team-* 角色的本职"——这个问句对**产出类活**对，对**调研类活**错。调研类活的判据应该是"信息流该不该经过编排者上下文"，不是"是不是某角色本职"。
- 真实成本核算：在摸现状场景，编排者亲自调研（做法 A/C）比派 team-se（做法 B）省 60–75% token、省 5–8 分钟、用户体感好。经验 5 的方向"更严格派子智能体"会让协作机制本身变成目的，而协作机制的目的是降本增效。

**修正后的正确判据（已写入 SKILL.md 第 4 条，拆分为 4A/4B/4C）**：

| 编排者动作 | 合法性 | 判据 |
|---|---|---|
| Read 项目核心文档（CLAUDE/DESIGN/ADR/changelog/kanban） | **合法且首选** | 信息流短、结构化、高复用 |
| 跑 `git log --oneline` / `git status` / `git diff --stat` | **合法**（看清单不看内容） | 信息密度低 |
| Test-Path / Get-Item / Read 1–3 处抽检落盘 | **合法且必须**（SKILL.md 第 6 条独立抽查） | 独立核对硬要求 |
| 写给用户的诊断说明 | **合法**（编排者沟通本职） | 是编排者本职，不是 SE 的活 |
| 派生策略规划 / 任务分解 | **合法且必须**（不可下放） | 编排者核心职责 |
| 跑 `findstr` / `grep` 全源码搜索 | **派 SE** | 信息密度高、可能试错 |
| 跑 `mvn` 全量编译/测试 | **派 Ops/QA** | 信息密度高、试错链 |
| 跨多目录探索性搜索 | **派 SE** | 信息流长、迭代链 |
| 系统级诊断（WSL/注册表/事件日志） | **派 SE/Ops** | 信息流极长、试错链 |
| 部署 / git 提交 / 写功能代码 / 评审 / 测试 | **派对应角色（无例外）** | 不可逆操作 + 角色本职 |

**决策心法（替代经验 5 的"是不是某角色本职"问句）**：

> 判据不是"这件事是不是某角色的本职"，而是"这件事的信息流该不该经过编排者上下文"：
> - 信息流短 + 复用高 + 独立性要求 → 该经过，编排者做（如现状摸排、抽检落盘）
> - 信息流长 + 试错链 + 一次性 → 不该经过，派子智能体（如全源码搜索、系统诊断）
> - 不可逆操作 + 角色本职 → 无论信息流如何，派子智能体（如部署、git 提交）

**对其他编排者的提醒**：
1. **Read 优先于 Bash**——摸现状的第一选择是 Read 项目核心文档（CLAUDE/DESIGN/ADR/changelog），不是跑 findstr。Read 拿到的是结构化信息，Bash 拿到的是噪音。
2. **保护编排者上下文比省 token 钱更重要**——编排者上下文窗口是"不可再生资源"，长 case 几轮 Bash 调研就可能逼近上限，导致摘要被截断、决策基于不完整信息。
3. **N 个角色要复用同现状时，编排者亲自摸 + 摘要写进每个角色 prompt**，比每个角色独立摸省 N 倍 token。
4. **抽查必须编排者亲自做**（SKILL.md 第 6 条）——派子智能体核对等于用一个上下文验证另一个上下文，等于没核对。

**详见**：`docs/agent-memory/编排者最佳实践评估.md`（方法论架构师元评估全文，§3 决策框架 / §5 SKILL.md 修订建议）。

### 经验 5：编排者过度调研违反"不越权执行"原则（2026-07-22，case-20260722 复盘）

> **⚠️ 判据已被经验 6 修正**：本条把"摸现状/写诊断"都判为越权违规，是判据错位。调研类活的正确判据见经验 6 与 SKILL.md 第 4 条 4B/4C。本条保留作为历史记录，**请优先遵循经验 6**。本条中仍然有效的部分（白名单第 1/2 条、黑名单中"git commit/push 派 Ops、mvn package 派 Ops/QA"）与经验 6 不冲突，可继续参考。

**场景**：用户在 3 个 dogfooding case 后反馈："为什么都要先调用 general-purpose 智能体，再调用 team-se、team-dev 等这些体系里面定义的子智能体工作？"

**根因**：编排者（ZCode）在派生 team-* 子智能体之前，自己跑了大量 Bash / grep / Read / findstr 来"摸现状"，从用户视角看就是"先有一段黑箱调研，再派专家"。本质是违反 team-orchestrator SKILL.md 第 66-80 行"编排者不越权执行"条款。

**违规清单（编排者不该做但实际做了的）**：
| 违规 | 本应派给谁 |
|---|---|
| case 开始时跑 git log / findstr / dir 摸工程现状 | team-se（技术现状调研是 SE 的活） |
| 写诊断说明（如"WSL2 未装，需手动安装步骤"）| team-se 或 team-ops |
| Reviewer/QA 报告后自己重跑 git status / mvn test / jar tf 全套验证 | 不重跑，止于"看报告 + 1-2 处抽检"（见 SKILL.md 第 82 条"编排者独立抽查"——档位裁剪后只抽 1-3 处）|
| 写技术方案 / 比较方案优劣 | team-se |
| 写临时部署脚本 | team-ops |

**正确边界（编排者只做这 5 件事）**：
1. 需求理解 + 派生策略规划（不写代码/方案/诊断）
2. PM 登记 case（写 changelog/kanban/risks，这是编排者本职工夫）
3. 派生 team-* 子智能体（按 L3→L2→L1 顺序）
4. 阶段间质量裁决（看报告 + 抽检 1-3 处关键改动，不重跑全套）
5. 人工检查点确认（涉及不可逆操作时打断用户）

**编排者用 Bash 的合法场景（白名单）**：
- Test-Path 抽检 1-3 处关键产出是否真实落盘
- git diff --stat 看改动文件清单（只看清单不看内容）
- 跑质量门禁脚本（如果门禁是编排者兜底）

**编排者用 Bash 的非法场景（黑名单）**：
- ❌ 摸工程现状（交给 SE）
- ❌ 写诊断 / 方案 / 调研报告（交给 SE/PO）
- ❌ 重跑 Reviewer/QA 已跑过的全套验证
- ❌ git commit / git push（交给 Ops）
- ❌ mvn package / java -jar（交给 Ops 或 QA）

**纠偏方法**：每次想自己跑 Bash 前，问自己——"这件事是不是某个 team-* 角色的本职？"。如果是，**派任务，不自己做**。哪怕自己做得更快也要派——这是协作机制的原则（SKILL.md 第 80 行原话）。

**对其他编排者的提醒**：用户的反馈是金标准。如果用户感觉"编排者在干调研活"，那就是越权了，不管 SKILL.md 怎么写。

### 经验 4：commit message 自引用 hash 悖论（2026-07-22，Ops 经验）

**场景**：changelog 写"本次 commit hash XXX"，commit 后 amend 必改 hash，changelog 立刻过时，越修越乱。

**根因**：在自己 commit 里自引用自己 hash 是逻辑悖论——每次 amend 必变 hash。

**正确做法**：未 push 的 commit 在文档里**不写精确 hash**，改用「日期 + `git log --grep=<关键词>` 反查指引」。已 push 的历史 commit（hash 已稳定）可以引用。

### 经验 3：反向验证是反幻觉最硬证据（2026-07-22，QA 经验）

**场景**：单测全部 PASS 不能证明测试有效——可能是空壳测试（断言写死 / 不检查关键状态）。

**正确做法**：临时改坏被测代码看测试是否 FAIL。
- catch Throwable → catch Exception：测试还能过，说明范围足够
- persist() 加 if(true) return：测试立即 FAIL，说明测试真检查了结果

**关键**：反向验证后必须立即恢复（git checkout 或手动改回），重跑确认 4/4 PASS。

### 经验 2：@Transactional 自调用失效是隐性大坑（2026-07-22，SE 经验）

**场景**：在 @Service 类内一个方法 this.anotherMethod()，anotherMethod 上的 @Transactional 不生效（不报错但事务不开）。

**根因**：Spring AOP 通过代理实现事务，类内 this.method() 绕过代理。

**正确做法**：事务方法抽到独立 Bean，由外部调用。

### 经验 1：pluginManagement 副作用传染（2026-07-21，EA 经验）

**场景**：父 POM pluginManagement 加 spring-boot-maven-plugin executions，所有引用该 plugin 的子模块都被 repackage，library 模块被破坏。

**正确做法**：父 POM pluginManagement 只放 configuration（无副作用），带 executions 的必须下沉到具体模块 POM。已固化为 ADR-001 P4。

## 使用方法（给未来编排者）

1. **派生任何 team-* 子智能体前**：扫一眼本文件"经验清单"，看有没有本 case 相关的避坑点
2. **case 完成后**：把本次踩到的新坑（如有）追加到清单顶部
3. **遇到用户反馈**：用户的反馈优先级最高，立即沉淀为经验，避免下次重犯
