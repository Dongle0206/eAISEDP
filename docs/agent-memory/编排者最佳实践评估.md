# 编排者最佳实践评估：亲自调研 vs 派子智能体调研

> 评估人：方法论架构师（临时虚拟角色，非体系 team-* 角色，专做体系元评估）
> 评估日期：2026-07-21
> 评估对象：team-orchestrator SKILL.md 第 4 条「编排者不越权执行」（第 66–80 行）
> 评估背景：dogfooding 3 个 case 后用户两次反馈"编排者做了太多调研"，本质诉求不是"遵守规范"，而是"找全局最优协作模式"

---

## 0. 评估前提（先校正一个认知误区）

team-orchestrator SKILL.md 第 4 条把"不越权执行"写成绝对原则，并用一句"哪怕自己做得更快也必须派角色——这是协作机制的原则"压死所有讨论。

但用户第二次反馈已经升级诉求：**"你应该评估该方式是最专业和消耗最小、成本最小的"**。这意味着——

> "不越权"是**协作机制的设计目标**（防编排者越权做部署、写代码这类高风险活），不是**调研类低风险活的判据**。把"不越权"机械地套到"摸工程现状"这类**零越权风险**的调研场景，是规范过拟合。

本评估的核心结论会落在这一点上：**第 4 条对"写代码/部署/git 提交"是对的，对"摸现状/读文档/抽检落盘"是错的**。下面用真实成本核算论证。

---

## 1. 三种做法的成本对比表

> 基准场景：以"摸 M1.0 工程现状"为代表任务。估算口径：编排者上下文（GLM-5.2/opus）= 0.02 USD/1K token 的等价价值，子智能体（如 team-se）= sonnet/opus 独立上下文。**编排者上下文窗口是稀缺且不可再生资源**——这是隐藏成本，单独列一列。

| 维度 | 做法 A：编排者跑 Bash | 做法 B：派子智能体调研 | 做法 C：编排者只读关键文档 |
|---|---|---|---|
| **token 消耗（绝对值）** | 中。5–10 个 Bash 输出（git log 2K、findstr 3K、dir 1K、pom 节选 5K）≈ **10–15K token** 进编排者上下文 | 高。子智能体全程 token（输入 5K + 工具调用 30K + 输出 3K）+ 编排者接收摘要 2K ≈ **35–40K token**（但分散在两上下文） | 低。Read 3–5 个核心文档（DESIGN/CLAUDE/changelog）≈ **5–8K token** 进编排者上下文 |
| **编排者上下文消耗（致命成本）** | **高**。Bash 原始输出（含日志、报错、目录树）吃编排者窗口，长 case 几轮就逼近上限 | **低**。子智能体工具调用输出**不进编排者上下文**，只回 final message（天然上下文隔离） | **中**。文档原文进上下文，比 Bash 输出干净，但仍占空间 |
| **时间成本（用户体验）** | 30 秒–2 分钟（编排者几轮 Bash，用户看见 Bash 在跑） | 3–8 分钟（编排者派生 → 子智能体独立调研 → 摘要回灌 → 编排者消化） | 10–30 秒（编排者直接 Read） |
| **质量风险** | 编排者上下文有完整现状，**派生 prompt 更精准**；但带编排者偏见（只看到自己 grep 出来的） | 子智能体独立摸现状，**避免编排者偏见**，但**重复摸现状**（若多角色都派一遍，5 个角色各跑一遍 = 5 倍 Bash） | 编排者信息不全，**可能派错任务**（基于过时文档）；子智能体拿到不全现状，做错决策 |
| **可重入性**（多角色复用） | 编排者摘要写进 prompt 可复用，**N 个角色共享 1 次调研** | 每个角色独立摸，**N 个角色 = N 次调研**；除非编排者把第一个角色的摘要转写 | 同 A，N 个角色共享 1 次摘要 |
| **协作机制纯净度** | 违反 SKILL.md 第 4 条字面（"不越权"） | 完全合规 | 合规（Read 不算 Bash 工具链操作） |
| **可观测性** | 编排者上下文里 Bash 输出可被用户看到，**透明** | 子智能体调研过程黑箱，编排者只拿到摘要，**不透明**（用户两次反馈的体感来源） | 编排者 Read 哪几个文件可被用户看到，**透明** |
| **失败兜底**（编排者理解错） | 编排者亲见原始输出，错可自查 | 编排者看不到原始数据，错被摘要掩盖（典型幻觉路径） | 编排者只看文档，文档与代码 drift 时必错 |

### 1.1 反直觉发现（先剧透，详见第 4 节）

1. **做法 B 不是"全局最优"**。它是"协作机制最纯净"的做法，但在调研类活上 token 浪费 2–4 倍、时间多 5–10 倍，且**用户体感最差**（两次反馈的根本原因）。
2. **做法 A 在"摸工程现状"和"抽检落盘"两类场景反而是最优的**——前提是控制 Bash 输出量（≤ 15K token）。
3. **做法 C 是被严重低估的甜区**。Read 关键文档比 Bash 更精准、更省 token、上下文更干净，且不违反规范字面。用户两次反馈的真实诉求大概率是"你们怎么不用 Read，老跑 Bash"。
4. **SKILL.md 第 4 条对调研类活的禁令需要重写**。当前条文把"摸现状"等同于"写代码"，是判据错位。

## 2. 不同场景的最优做法推荐

### 场景 A：摸工程现状（理解当前代码状态）

**典型动作**：理解 M1.0 进度、清查模块边界违规、看 changelog 里的 case 历史、判断某功能是否已实现。

**推荐做法：C（编排者 Read 关键文档）+ 受限的 A（编排者跑 1–2 个定向 Bash）**

具体策略：
1. **首选 Read**：`CLAUDE.md` / `DESIGN.md` / `docs/过程跟踪文档/changelog.md` / `docs/过程跟踪文档/kanban.md` / 最新 ADR —— 这 5 个文档 80% 现状问题都能回答。
2. **次选定向 Bash**（仅当文档不够）：`git log --oneline -20` / `git status` —— 只看清单不看内容。
3. **禁止**：跑 `findstr` 在源码里大规模搜索、跑 `mvn` 全量编译验证、跑 `git diff` 全文件比对 —— 这些是 SE/Dev 的活，且 token 消耗大。

**为什么不是 B（派 team-se）**：
- token 浪费 3–4 倍（35K vs 10K）。
- 时间多 5–8 分钟，用户体感差。
- team-se 摘要回灌后，编排者还是要"消化"一遍才能写 prompt，**信息没省**。
- 现状摸清后编排者要派 N 个角色，**摘要复用 = N 个角色共享 1 次调研**，做法 A/C 的 N 倍复用优势压倒 B 的"N 次独立调研"。

**为什么不是纯 A**：Read 比 Bash 输出干净（文档是结构化的，Bash 输出是噪音），上下文污染更小。**Read 优先于 Bash**。

### 场景 B：验证子智能体产出（核对落盘）

**典型动作**：Reviewer/QA 报告产出后，编排者要确认产出真实落盘（防虚报，SKILL.md 第 82 条"编排者独立抽查"）。

**推荐做法：A（编排者定向 Bash + Read）—— 这是 SKILL.md 第 82 条的硬要求，本来就该编排者做**

具体策略：
1. `Test-Path <产出文件绝对路径>` + `Get-Item | Select-Object Length`（确认文件存在且 > 100 字节，对应门禁 G7）。
2. `git diff --stat`（看改动文件清单，**只看清单不看内容**）。
3. fast 档：`Read` 1 处核心改动；standard 档：`Read` 2–3 处核心改动（SKILL.md 第 82 条的档位裁剪规则）。

**为什么不是 B**：抽查的本意是"编排者作为独立第三方核对"，**派子智能体核对 = 用一个上下文验证另一个上下文，等于没核对**（典型的"自审自"风险，SKILL.md 模型隔离条款的精神延伸）。**抽查必须编排者亲自做，这正是 SKILL.md 第 82 条的明文要求**。

**这一条恰好证明 SKILL.md 自身就承认"编排者有时必须亲自做调研"** —— 第 4 条和第 82 条本身就是矛盾的，第 82 条才是对的。

### 场景 C：诊断问题（如 WSL2 装不上）

**典型动作**：用户报"WSL2 装不上"，编排者要给出诊断 + 修复步骤。

**推荐做法：B（派 team-se 或 team-ops 调研）—— 这种场景派子智能体反而是最优的**

具体策略：
1. 编排者派 team-se："用户报 WSL2 装不上，请摸清当前 WSL 状态、给出诊断 + 修复步骤，落盘到 `docs/设计规划文档/<case-id>-WSL2诊断.md`"。
2. team-se 跑各种 Bash（`wsl --status` / `dism` / 注册表查询），**输出长且噪音大**，编排者上下文不应吃。
3. team-se 落盘诊断文档 + 摘要回编排者。
4. 编排者把诊断文档路径转给用户，或派 Ops 执行修复。

**为什么是 B 不是 A**：
- 诊断类 Bash 输出（注册表长字符串、dism 日志、事件日志）**噪音极大**，进编排者上下文是灾难。
- 诊断需要**试错**（跑了命令看结果再决定下一步），试错链不该在编排者上下文里展开（吃窗口）。
- 诊断结论要**落盘归档**（用户要复用、要给团队看），子智能体落盘天然合适。
- 这类活**不是"摸现状"**而是"深度调查"，**SKILL.md 第 4 条对这类活是对的**。

### 场景 D：写诊断说明给用户

**典型动作**：把诊断结果写成用户能看懂的说明，告诉用户下一步怎么做。

**推荐做法：编排者亲自写 —— 但前提是诊断（场景 C）已由子智能体完成**

具体策略：
1. 编排者 Read 子智能体落盘的诊断文档（只读结论部分，不吃原始 Bash 输出）。
2. 编排者用人类语言写给用户（这是编排者"理解需求 + 沟通"的本职，不是 SE 的活）。

**为什么编排者亲自写**：
- 写给用户的话**编排者最懂用户语境**（SE 写出来往往是技术黑话）。
- 这是编排者"汇总 + 沟通"的本职（SKILL.md 第 62 条核心职责之一）。
- 写说明不是"写诊断"——诊断是 SE 的活，说明是编排者的活。**两者要分开**。

### 场景 E：跨多个目录的探索性搜索

**典型动作**：用户说"我们体系里有没有处理支付的地方"，编排者要跨 10 个目录搜索。

**推荐做法：B（派子智能体）—— 探索性搜索天生属于子智能体**

具体策略：
1. 编排者派 team-se："请跨 N 个目录搜索 X 主题，返回找到的文件清单 + 每个文件一句话概括，落盘到 `<路径>`"。
2. team-se 跑大量 `grep` / `find` / `Get-ChildItem -Recurse`，输出极长，**绝不能进编排者上下文**。
3. team-se 落盘搜索报告 + 摘要回编排者。

**为什么是 B 不是 A**：
- 探索性搜索的 Bash 输出**长度不可控**（可能几十 K token），进编排者上下文必爆。
- 搜索过程需要**迭代**（先广搜再窄搜），迭代链不该在编排者上下文展开。
- 搜索结果要**落盘可复用**（多角色共享），子智能体落盘天然合适。

## 3. 决策框架（编排者 30 秒内决定自己做还是派子智能体）

> 核心思想：**不是"按角色分工"决定，而是按"信息密度 × 上下文成本 × 复用次数"三因子决定**。

### 3.1 三因子判据

| 因子 | 编排者亲自做有利 | 派子智能体有利 |
|---|---|---|
| **F1：信息密度**（Bash 输出 token / 摘要 token） | 低（输出短或结构化，如 git log --oneline、Test-Path、git diff --stat） | 高（输出长或噪音大，如 findstr 全源码、mvn 全量日志、注册表 dump） |
| **F2：上下文成本**（输出进编排者上下文的危害） | 低（输出 < 5K token，且对后续派生 prompt 有用） | 高（输出 > 15K token，或属于试错链不应进编排者） |
| **F3：复用次数**（同现状会被几个角色用） | 高（≥ 2 个角色要复用，编排者摘要写进 prompt 一次到位） | 低（只本角色用，调研完即丢） |
| **F4：试错性**（需要跑 → 看 → 再跑的链式） | 否（一次性命令） | 是（探索性、迭代性） |
| **F5：独立性要求**（这是不是"独立核对"性质） | 是（抽查、核对、验证 —— 派子智能体等于没核对） | 否（普通调研） |

### 3.2 30 秒决策流程图

```
编排者面临一个任务 X
   │
   ├─ Q1：X 是"写代码/部署/git 提交/数据删除"吗？
   │       是 → 派子智能体（硬约束，无例外）
   │       否 ↓
   │
   ├─ Q2：X 是"独立核对产出是否真实"吗（抽查/验证）？
   │       是 → 编排者亲自做（SKILL.md 第 82 条要求，且独立性硬要求）
   │       否 ↓
   │
   ├─ Q3：X 的 Bash 输出 token 估计 > 15K 吗（F1+F2）？
   │       是 → 派子智能体（上下文保护优先）
   │       否 ↓
   │
   ├─ Q4：X 需要试错链吗（跑→看→再跑，F4）？
   │       是 → 派子智能体（迭代链不该进编排者）
   │       否 ↓
   │
   ├─ Q5：X 的结果会被 ≥ 2 个角色复用吗（F3）？
   │       是 → 编排者亲自做（一次调研多角色共享，省 N 倍）
   │       否 ↓
   │
   └─ 编排者亲自做（默认）
```

### 3.3 决策表速查（按任务类型）

| 任务类型 | 推荐做法 | 关键判据 |
|---|---|---|
| Read 项目核心文档（CLAUDE/DESIGN/ADR/changelog） | **编排者** | F2 低、F3 高、文档是结构化的 |
| `git log --oneline` / `git status` / `git diff --stat` | **编排者** | F1 低（看清单不看内容）、F3 高 |
| `Test-Path` / `Get-Item` 抽检落盘 | **编排者** | F5 是（独立核对硬要求） |
| `Read` 1–3 处核心改动 | **编排者** | F5 是、F2 低 |
| `findstr` 全源码搜索 | **派子智能体** | F1 高、F4 可能 |
| `mvn` 全量编译/测试 | **派子智能体（Ops/QA）** | F1 高、F4 是 |
| 跨多目录探索性搜索 | **派子智能体** | F1 高、F4 是 |
| 系统级诊断（WSL/注册表/事件日志） | **派子智能体** | F1 极高、F4 是 |
| 写技术方案 / 比较方案 | **派子智能体（SE）** | 是 SE 本职（角色分工） |
| 写部署脚本 / 执行部署 | **派子智能体（Ops）** | 不可逆操作 + 是 Ops 本职 |
| 写诊断说明给用户 | **编排者** | 是编排者沟通本职 |
| 派生策略规划 / 任务分解 | **编排者** | 是编排者本职（不可下放） |

### 3.4 一条心法

> **判据不是"这件事是不是某角色的本职"，而是"这件事的信息流该不该经过编排者上下文"。**
>
> - 信息流短 + 复用高 + 独立性要求 → 该经过，编排者做。
> - 信息流长 + 试错链 + 一次性 → 不该经过，派子智能体。
> - 不可逆操作 + 角色本职 → 无论信息流如何，派子智能体。

## 4. 反直觉发现（诚实清单）

### 4.1 SKILL.md 第 4 条"哪怕自己做得更快也必须派角色"在调研类活上是错的

**原文**（第 80 行）："哪怕'自己做得更快'也必须派角色——这是协作机制的原则。"

**问题**：这句话把"不越权"原则从"防部署/防代码污染"泛化到"防调研"，是过度泛化。**调研不是越权**——编排者读自己项目里的文档、看自己项目的 git log，根本不涉及任何"越权"风险。

**真实成本核算**：在"摸工程现状"场景，编排者亲自调研（做法 A/C）比派 team-se（做法 B）省 60–75% token、省 5–8 分钟、用户体感好。**"协作机制的原则"不能凌驾于"全局成本最优"之上** —— 否则协作机制本身就成了目的，而协作机制的目的是降本增效。

### 4.2 用户的两次反馈不是要"更严格遵守规范"，而是要"规范本身需要修改"

**反思**：第一次反馈后，team-orchestrator.md 经验 5 的复盘方向是"编排者违规了，要更严格遵守不越权"。**这个复盘方向是错的**。

用户第二次反馈"评估该方式是最专业和消耗最小、成本最小的"，**实质是在说"你们的规范本身就不对"**。如果继续按经验 5 的方向纠正，只会让编排者更僵化、用户体验更差。

### 4.3 做法 C（只 Read 不跑 Bash）是被严重低估的甜区

**反直觉点**：用户两次反馈的本质可能不是"编排者做了调研"，而是"编排者做了**低质量**调研（跑 Bash 跑出大量噪音）"。

**证据**：
- Read CLAUDE.md 拿到结构化的技术栈、模块清单、质量门禁 —— 5K token，1 秒。
- 跑 `findstr` 搜源码、跑 `git log` 看 100 条记录 —— 15K token，30 秒，还要编排者自己消化。

**结论**：**编排者第一选择永远是 Read，不是 Bash**。Read 是"做法 C"，Bash 是"做法 A"。当前 team-orchestrator.md 经验 5 的"白名单"把 Bash 和 Read 混为一谈，是错的。**应该明确：Read 文档优先于 Bash 命令**。

### 4.4 做法 B（派子智能体）在"复用 N 次"场景下是 N 倍浪费

**反直觉点**：直觉上"派专家更专业"，但如果编排者要派 5 个角色（PO/BA/SE/Dev/Reviewer），每个角色都独立摸一遍现状，**就是 5 倍的 Bash 调用、5 倍的 token、5 倍的时间**。

**正确做法**：编排者**一次性摸现状 + 摘要写进每个角色的 prompt**，5 个角色共享 1 次调研。这正是做法 A/C 的 N 倍复用优势。

**这点是做法 B 最大的隐性成本**，也是 team-orchestrator.md 经验 5 没看到的。

### 4.5 编排者上下文是"不可再生资源"，比 token 钱更贵

**反直觉点**：token 是钱（可计量），但编排者上下文窗口是**容量**（不可计量但一旦爆掉整个 case 就废了）。

**核算**：一个长 case（standard 档）编排者要派生 8+ 个角色、要做 5+ 个检查点、要接收 N 份子智能体报告。如果编排者上下文已经被前期 Bash 调研吃掉 30%，后期就很容易逼近上限，导致**摘要被截断、决策基于不完整信息、长 case 失败**。

**结论**：**保护编排者上下文比省 token 钱更重要**。这一点上：
- 做法 C（只 Read 文档）—— 上下文最干净，**最优**。
- 做法 A（跑 Bash）—— 上下文中等污染，**次优**（要控制输出量）。
- 做法 B（派子智能体）—— 上下文最干净，**隔离最好**，但 token 和时间成本高。

**所以上下文维度上，做法 C 才是甜区，不是 B**。这点和 token 维度的结论一致。

### 4.6 SKILL.md 第 4 条和第 82 条自身就是矛盾的，第 82 条才是对的

**矛盾点**：
- 第 4 条（第 66–80 行）："编排者不越权执行……哪怕自己做得更快也必须派角色。"
- 第 82 条："编排者独立抽查……对本次关键改动点跑 git diff 或 grep/Read 核对几处核心改动是否真实落地。"

第 82 条**明文要求编排者亲自跑 Bash/Read 做核对** —— 这和第 4 条"必须派角色"直接冲突。

**结论**：**第 4 条的"绝对禁令"是错的，第 82 条的"按需抽查"才是对的**。第 4 条应该改成"按场景区分"，而不是"一刀切派角色"。
